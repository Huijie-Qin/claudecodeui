# AI 使用报表：首版开发与运行说明

## 2026-10-23 对接明细与 Skill 历史回补

第一个「AI 使用」Tab 直接分页读取已发布的 `ai_dashboard_integration_detail`，保留日期、用户、工作区筛选和排序，不再将这张明细表重新聚合成用户行。空值展示为 `—`，数值 0 保留；时长按毫秒转换显示，`refreshed_at` 展示发布时间。导出使用同一明细接口与筛选条件。这里的 `user_id` 是每条事实的行为用户（Skill 调用为调用者）；Skill Tab 仍按发布者统计贡献，两个页面的用户含义不同。接口为 `GET /api/ai-usage/integration-details`，沿用租户、自身范围、当前发布批次及同读事务校验。

历史 Skill 发布清单使用 [回补脚本说明](ai-skill-publication-backfill.md) 导入。无需市场 Skill ID；提供租户、发布用户、精确 Skill 名称和首次发布时间即可。人工回补以 `historical-skill-publication:` 标记可信来源，缺少真实 ID 时生成稳定本地统计 ID；不伪造工作区安装历史，不修改市场内容，不直接写报表。重复清单幂等，首次发布时间同日取较早可信时间，同一时刻仍按原来源优先级选取。

夜间原本已扫描历史会话，但调用时点缺少 `ai_skill_binding_history` 会导致调用无法进入发布者统计。现在先使用有效绑定，完全没有有效绑定时，才按同租户、精确名称、发布时间不晚于调用的人工清单匹配。竞争身份、同名多发布者、既有绑定的发布者冲突均不猜测。原生 `Skill` 工具调用、已证实的用户 slash 调用按请求与工具身份去重，重复数据库副本不累计，Hook／Graph／Top Skill 自动执行和继承历史继续按原规则排除；普通文本提及 Skill、Read 或 Bash 读取文件不算调用。

新增一层 `claude-response` 旧包装事件解析，与 SQL 历史解析对齐。计算版本追加 `skill_history_v17`，首次可领取批次会重新校验／解析旧缓存，旧版本暂停候选重新准备，正式结果保留到新批次原子发布。同日已经成功发布的批次仍不会因部署立即重开。`AI_USAGE_INCREMENTAL_ENABLED=false` 仍全量重建，人工发布事实不会被清除；后续清单变化即使处于增量模式，也会将无绑定的旧会话重新排队归因，无需修改历史文件。

`coverage_json.skillInvocationDiagnostics` 记录已形成调用事实但无法归因的原因及数量；它不包含未被证实的纯 slash 候选，也不表示所有历史文件都已存在且可读。未归因调用可在 `ai_usage_fact_rows` 的 `skill_invocations` 数据集中按 `value_json.attributionReason` 核对。只有保留的、归属可信的可读会话可以恢复调用，发布清单本身不会制造调用次数。

## 2026-10-17 全量统计来源处理性能修复

脚本只在内存计算指定用户的时长和 SQL；夜间还构建完整看板。但夜间耗时不能仅归因于指标更多或租户排队。本次使用同一租户、用户、JSONL 及数据库消息副本，对照完整夜间流程与只读 audit，并按阶段及 SQL 计时，确认 `sources` 阶段存在重复扫描。

- 原 `put(replace)` 对每条数据库副本执行旧来源的 DISTINCT 清理查询。SQLite 在样本中选择了按租户/分区或租户/轮次索引，未按 `source_key` 定位；即使该副本从未生成事实，也扫描该租户大量事实。现在先通过来源主键检查是否存在旧事实，只有存在时才执行旧轮次、旧分区清理，已有来源的撤销与脏分区语义保留。
- 可读主历史查询新增 `idx_ai_usage_native_main_session`，按租户和会话定位。查询与索引使用相同的 CASE 表达式，旧非法 JSON 不阻断索引迁移；主历史出现、消失、可读性及归属变化即时生效。
- 数据库来源改为每页最多 200 条、约 50 ms 的软时间预算事务，避免每条消息单独提交。每条来源之间仍检查停止/窗口状态，已处理前缀、按 generation 删除队列及游标同事务保存；提交成功后才推进内存游标。单条复杂来源可能超过时间预算，不声称写锁硬上限。页内处理或检查点失败回滚整页，租约失效不能提交；正常窗口停止保存已完成前缀，下次续跑。
- 已在事务中保存的来源页不再立即重复写同一检查点；窗口检查及事件循环让出保留。

这些修改不改变 AI 时长、SQL 去重、日期切片、全量重建范围及最终原子发布规则，不重开已成功发布的同日批次，也不删除原始历史。需要构建并重启实际后端，启动迁移会自动补索引；未完成批次继续原断点。

性能对比采用冻结的 `703a57a` 与本次代码、相同 Docker Node 22 环境及独立 SQLite 测试库；每个会话 20 个完成轮次，每条原始消息同时保留数据库副本。100 个会话的三次无逐条 SQL 计时运行，中位完整夜间耗时从 **6.033 秒降到 1.655 秒**，其中 `sources` 从 **4.606 秒降到 0.229 秒**。脚本与两版看板 API 均为 **120,000 秒、4,000 行 SQL**。扩大到 200 个会话的同方式单次对比，完整流程从 **20.699 秒降到 3.683 秒**，`sources` 从 **17.485 秒降到 0.444 秒**；两版及 audit 均为 **240,000 秒、8,000 行 SQL**。测试库使用 WAL/NORMAL、容器 tmpfs，audit 先读使文件缓存已热。这是固定样本对比，不是生产整晚完成时间的承诺；实际吞吐仍需用部署后的运行日志验证。

专项测试覆盖原查询的索引计划、旧库迁移、来源变化与数据库回退、已存在/不存在来源清理、分页事务、窗口停止续跑、错误回滚、租约失效和 generation 更新。独立查询微基准可用 `AI_USAGE_LOOKUP_BENCHMARK=true node --test server/services/ai-usage-source-lookup.test.js` 运行；日常回归默认跳过计时基准，避免硬件波动影响正确性测试。

## 2026-10-16 全量续跑进度与看板发布修复

修复了两条可复现的停滞／陈旧结果路径：

- 原生文件扫描恢复时，虽然跳过了已完成文件内容，仍会打开这些文件的子代理目录并检查附属文件。在慢文件系统、大量历史目录下，重复遍历可能耗尽整个窗口，导致连续几夜停在同一个 `fileCursor`。现在按持久游标跳过已经完成的运行目录、项目和主会话子树，当前主会话未完成的子代理／附属文件仍继续处理。新批次与追赶扫描从头发现来源，因此排序更早的新文件不会永久遗漏。
- 跨夜恢复旧全量批次，以前会按旧 `target_through` 发布，出现 `completed_at` 是今天而看板仍截止到几天前，并且已扫过的历史文件改写不会再检查。现在先完成保存的全量扫描，再在发布前将目标推进到实际运行窗口，重新发现来源、校验文件内容、处理新消息并重建所有候选投影；来源变化会重读。校验通过后才在同一事务替换正式报表、主题明细、会话汇总及 `active_batch_id`。

初次全量仍清理该租户全部派生缓存，原始记录与旧正式结果保留。追赶时保留已经从原始来源重建的事实及文件读取位置，经内容指纹验证后复用，避免把已经完成的全量解析再次清零。目标变更、候选清理和断点写入原子提交；追赶阶段暂停／重启后继续，不能只更新截止日期而沿用旧候选。

每个逻辑全量批次最多推进目标一次，然后固定目标完成；否则单次扫描本身跨多个窗口的大租户会不断追逐新的日期，永远无法发布。如果追赶也跨夜，最终发布可能仍落后当晚目标，此时日志仍记 `pending/backlog_remaining`，需要后续批次继续，不冒充全部赶上。不能保证任意规模的所有租户一夜完成。

`full_rebuild_target_advanced` 日志表示开始补齐旧任务的截止范围；`coverage_json.originalTargetThrough`、`targetRefreshCount` 保存追赶记录，`source_read_at` 更新为最后一轮来源扫描开始时间。只有成功发布且覆盖当前窗口目标时才写入 `coverage_json.completedWindowScheduledFor`，调度器、领取和日志均识别它，同窗口不会因为批次原计划日期较早而马上再开一轮全量。增量旧批次沿用原续跑策略；同日已经发布的批次不会因重启直接重开。

### 部署后的实际验收

在服务真实 `.env` 设置 `AI_USAGE_ENABLED=true`、`AI_USAGE_INCREMENTAL_ENABLED=false`，构建并重启后端。`GET /api/ai-usage/status` 现在返回实际加载的 `incrementalEnabled`；它为 false 才表示当前配置全量。`coverage.incrementalEnabled` 则表示当前看板已发布批次的实际模式，两者可能在尚未发布新结果时不同。若使用 `dist-server` 启动，仅替换 `server/` 源码不会让运行中的旧后端更新。

在业务数据库检查每个活跃租户的正式批次及本次执行状态；以下查询自动选择日志中最新的实际运行窗口：

```sql
WITH latest AS (SELECT MAX(scheduled_for) scheduled_for FROM ai_usage_run_logs)
SELECT t.id AS tenant_id,
       l.effective_status AS run_status, l.stage, l.reason, l.error,
       l.target_through AS expected_through,
       b.id AS active_batch_id, b.status AS active_status,
       b.target_through AS published_through,
       datetime(b.completed_at, '+8 hours') AS completed_beijing,
       json_extract(b.coverage_json, '$.incrementalEnabled') AS incremental,
       json_extract(b.progress_json, '$.fullRebuildInitialized') AS full_initialized,
       json_extract(b.coverage_json, '$.targetRefreshCount') AS target_refresh_count,
       CASE WHEN b.status='published' AND b.target_through>=l.target_through
         AND l.effective_status='published' THEN 1 ELSE 0 END AS reached_window_target
FROM tenants t
LEFT JOIN ai_usage_tenant_state s ON s.tenant_id=t.id
LEFT JOIN ai_usage_batches b ON b.id=s.active_batch_id AND b.tenant_id=t.id
LEFT JOIN ai_usage_run_log_status l ON l.tenant_id=t.id
  AND l.scheduled_for=(SELECT scheduled_for FROM latest)
WHERE t.status='active'
ORDER BY reached_window_target, t.id;
```

全量验收应同时看到 `incremental=0`、`full_initialized=1`、新批次实际发布时间及正确覆盖范围；`reached_window_target=1` 表示该租户已完成日志中最新窗口目标。若最新窗口本身是几天前，仍须先排查调度是否启动；此标志不能替代日期新鲜度检查。之后用相同用户、日期和时区的独立核算结果核对看板 API 的逐日 AI 时长与 SQL 行数。

本地端到端验证用真实 SQLite、历史 JSONL 和 HTTP 看板接口，故意写坏旧正式结果与派生缓存，再改写早期历史、加入最近日期及新会话，并经历跨日暂停和数据库重开。验证对象包括历史逐日指标、截止日期、批次切换、失败/暂停时旧快照保留，以及恢复后的单用户脚本一致性；不以任务返回 `completed` 代替数据核对。旧版本在该用例中会把今天的发布时间配上三天前的截止日期，且早期文件已改为 600 秒时接口仍给 120 秒；修复后历史时长与 SQL 行数逐日匹配原始核算。完整回归 **464 项通过**，三个真实 HTTP 端到端用例包含并发 1／2、第二次窗口耗尽及重启恢复。

## 2026-10-16 夜间执行日志与租户逐用户复核

新增 `ai_usage_run_logs`，按实际调度窗口预登记全部活跃租户，记录队列、开始/完成、执行阶段、全量/增量模式、暂停/失败原因和发布数量。查询 `ai_usage_run_log_status.effective_status` 可识别崩溃或租约过期后的异常中断；旧批次续跑归到实际执行的那一晚，补完旧批次但尚未赶上当前窗口时仍算未完成。部署前的逐晚执行历史不能追溯补造。可直接复制 [执行日志查询 SQL](ai-usage-run-logs.md)。

核算脚本省略 `--user-id` 时，按租户成员与保留历史归属逐用户输出 SQL 行数、AI 秒/小时及覆盖、错误，计算口径不变。详见 [核算脚本说明](ai-usage-user-audit.md)。

## 2026-10-16 优先补齐落后租户

租户队列按正式结果的新鲜度排序：没有有效已发布快照的租户最先，其次是 `active_batch_id` 对应批次 `target_through` 最早的租户；覆盖日期相同时，优先恢复未完成批次，再按正式批次完成时间、未完成批次计划时间和租户 ID 排序。之前固定按租户 ID 排队，全量模式下，较小 ID 租户每天重新全量运行，可能持续占满窗口，让后面的租户始终没有新批次。

此次调整只改变领取顺序。每轮仍按配置的并发上限处理，每个租户只派发一次；恢复时沿用旧批次 ID 和持久化进度，同日已发布批次不重开。窗口不足时继续暂停保存，不能据此保证所有租户在一夜完成。没有新日期的批次不等于没有尝试执行：旧 `paused`／`failed` 批次优先恢复，`scheduled_for` 不会随恢复日期改变，应结合该批次状态、进度、错误和 `batch_started`／`batch_paused` 日志判断。

排查历史结果时，先确认该租户当前 `active_batch_id`，再核对 `completed_at`、`coverage_json.incrementalEnabled` 和 `progress_json.fullRebuildInitialized`。尚未成功发布的租户继续显示旧的整份结果。全量范围只有 `target_through` 截止上限，不会仅重算最新一天；跨多个历史日期的回归覆盖了未变原始文件、错误旧缓存及正式结果替换。

配置从应用根目录的实际 `.env` 加载（不是 `.env.example`），其同名值会覆盖 PM2 注入的环境变量；配置在启动时读取一次。使用 `dist-server` 启动时，部署需包含重新构建后的后端产物，然后重启服务。以批次记录中的模式和发布结果确认线上生效。

## 2026-10-15 增量／全量配置

在后端实际运行环境设置并重启服务加载：

```dotenv
# 默认：校验历史内容后增量统计
AI_USAGE_INCREMENTAL_ENABLED=true
# 如需每个夜间批次都从原始来源全量重算，改成 false
```

设置 `false` 后，每个可执行的新批次都重新读取当前保留、归属明确的原始记录，重建该租户整套 AI 使用报表，包括 AI 时长、SQL、Skill、Hook 和活跃用户等派生指标，按批次 `target_through` 截止日期发布。若只需修复一次，确认全量批次发布成功后改回 `true` 并重启。全量扫描及派生重建通常比增量耗时，窗口结束后保存进度，下一次继续同一批次。

重算前后数据库处理：

| 数据 | 全量重算处理 |
| --- | --- |
| 原始会话文件、消息、`ai_usage_turn_facts`、Hook 原始记录、Skill 上下文及绑定历史 | 保留，重新读取 |
| `ai_usage_fact_rows`、`ai_usage_source_states`、来源变更队列及 Skill 派生分组 | 只清理当前租户的缓存，重置来源扫描进度后重新生成 |
| 当前批次各暂存表、文件遍历和 Skill 工作记录 | 清理并从空候选构建；初始化标记与清理同事务保存，暂停／重启恢复不重复清空 |
| `ai_usage_suppressed_rows`、归属冲突记录 | 保留，重算不能让已屏蔽记录重新出现 |
| 已发布的 `ai_usage_report_rows`、宽表、各 `ai_dashboard_*_detail`、`ai_session_summary` 和 `active_batch_id` | 重跑期间保留；候选全部完成后，同一事务按租户替换并切换批次，不与旧结果叠加 |

其他租户的数据不会被当前租户初始化删除。已失去原始来源的旧统计不会从旧正式结果复制到全量候选中；重算失败或暂停不会发布空表或半成品。不需要手工删除数据库记录。

模式写入批次 `coverage_json.incrementalEnabled`。暂停／失败批次在模式不变时继续执行；若修改模式，下次领取该批次会丢弃旧暂存候选、按新模式重新构建，当前正式结果仍保留。同日已发布批次不会因为切换配置或重启再次运行，窗口与 `AI_USAGE_DATA_LAG_DAYS` 规则保持不变。

`batch_started`、`history_rebuild_started`、`batch_published` 日志包含 `mode: 'full'` 或 `mode: 'incremental'`；全量初始化日志的 `reason` 为 `full_mode`。同一批次暂停恢复不重复初始化；持续配置 `false` 时，每个后续新批次均全量重建。只有对应 `batch_published` 才表示新结果生效。

## 2026-10-15 历史文件改写与 v16 重建

计算版本追加 `transcript_content_v16`。修复原生文件保留前 4 KiB、原地改写后变长时被误认为追加的问题：此前夜间可能从新 JSON 中间的旧 offset 开始，撤销时长并保留旧 SQL；单用户脚本每次完整扫描，因此两项可能不一致。

现在每次复用读取位置前，分块校验已消费全部字节的 SHA-256，包含大小和修改时间未变的文件。指纹保存在 `ai_usage_source_states.state_json.contentFingerprint`；缺少新指纹、文件替换或内容变化时，从头重建该来源。旧派生行和游标在同一事务失效，暂停后不能复用已经清空事实的旧游标。正常追加仅解析新增完整行，未换行尾部继续等待。扫描完成再次校验已消费内容及文件身份；扫描中被改写的来源撤销本次贡献、记录 `AI_USAGE_HISTORY_CHANGED_DURING_SCAN`，下一批次重新读取。其他会话继续处理。

首次可领取的 v16 夜间批次会通过版本升级重置原生读取位置，重新扫描当前保留且可读取的历史来源，并重建截止日期之前的历史结果。已暂停或失败的旧版本批次清空旧候选后重建；原正式表保留到新批次成功发布。**同日已经发布的批次不会因部署立即重开**，应等待下一个尚未发布的夜间批次；窗口结束时仍按断点继续，不能保证所有历史在一个窗口内完成。默认增量模式下，后续版本相同的批次做完整内容校验与增量解析；显式配置全量模式时，每个新批次均重新解析保留历史。

完整内容校验增加顺序文件读取量，使用固定大小缓冲区，不在文件扫描期间持有数据库写事务。AI 时长和 SQL 计算规则、`ai_usage_turn_facts` 原始记录及表结构不变。该修复作用于夜间缓存，已经交付的 v3 单用户脚本无需替换。

PM2 日志中，`history_rebuild_started` 表示版本升级重建已开始；同一 `batchId` 出现 `batch_published` 才表示新结果已经发布。两条日志均包含 `calculationVersion` 和 `targetThrough`，新版本末尾应为 `transcript_content_v16`。也可在业务数据库中查询（替换租户 ID）：

```sql
SELECT b.id, b.status, b.calculation_version, b.target_through, b.completed_at
FROM ai_usage_tenant_state s
JOIN ai_usage_batches b ON b.id = s.active_batch_id AND b.tenant_id = s.tenant_id
WHERE s.tenant_id = 1;
```

需确认 active 批次为 `published` 且版本包含 `transcript_content_v16`，再将同用户、同租户、相同时区和日期范围的正式表数值与脚本核对。脚本读取当前文件，正式表保存上次发布时的结果；发布之后新增或改写的数据仍要等后续批次。服务启动成功或显示已部署新代码，不能代替以上重建验收。

- “记录性 Hook”优先展示“具体业务记录 · 字段统计”，包括归档条数、质量评分、复核耗时、SQL 行数等已配置字段的求和／平均／极值和有效样本数。按 Hook、行为、版本、类型及单位隔离，支持字段键精确筛选、排序及分页。点击“记录明细”后，每个已开放字段单独成列，文本结果也可见，不再挤在一个通用 JSON 栏里。
- 新增 API：`skills`、`hook-field-statistics`、`hook-executions`、`hook-executions/:id/records`，均沿用实时权限校验和固定已发布批次。不在白天查询原始业务表。

- 按 Hook、按用户和记录明细弹窗使用同样的选择框；从字段统计打开明细时沿用已选方式，明细也可单独切换。名称／样本数排序不受切换影响；如正在按统计结果排序，则切换服务端排序字段并回到第一页，保留筛选条件，仍是全量排序。只切换展示不会查询原始记录或启动夜间重算。

## 固定整体概览（9 月 14 日调整）

- 四张卡片移到页签和筛选区上方，所有页签共用。独立组件与独立 `GET /api/ai-usage/summary` 请求，不随日期、用户、工作区、名称、本人／全员切换、分组、指标条件、排序或分页重新加载或改变结果。
- 权限范围不是业务筛选：管理员固定查看当前租户全员概览；普通用户固定查看本人概览。换租户、身份／权限变化、发布批次变化或确认刷新时重新加载，失败不显示旧范围数据。
- 会话次数固定为数据截止日 D 往前 29 天至 D 的去重会话数；DAU 为 D 当天的去重交互用户；MAU 为 D−29 至 D 的去重交互用户。卡片直接展示固定起止日期，不随下方筛选结束日变化。
- “累计发布 Skill 数量”为当前已发布统计批次中，首次成功发布时间不晚于 D 的全部可核验 Skill，按 Skill ID 去重；重复发布不累加，同名不同 ID 分别计数。不要求落在近 30 天或明细日期内，不按工作区分摊；只存在调用归因、没有 confirmed 发布记录的 Skill 不算发布。既有删除遮蔽与权限隔离仍生效，不将其解释为实时市场在架数量。
- 新接口只接受批次和授权范围作为概览依据，主动忽略明细筛选参数。只查夜间发布的投影与滚动活跃集合，不扫描原始消息、发布或 Hook 业务表，不开启新夜间任务。下方趋势／明细／分组仍使用原有筛选口径；概览失败不会使明细一并失败。
- 模拟概览：会话 601、累计发布 30、DAU 4、MAU 41。下方默认期间内没有新增发布，所以用户明细的期间发布数仍可为 0；普通用户样本累计发布为 15。

## DAU／MAU 与交互分析（9 月 12 日新增）

- DAU：所选结束日期 D 内，有实际用户消息交互的去重用户数。不是登录人数，也不直接使用旧 admin 看板的 `session_index.updated_at` 判定活跃；跨日时长本身不会凭空增加次日活跃用户。
- MAU：D−29 至 D（含首尾）的实际交互用户去重数；不是自然月人数，也不是 30 天 DAU 之和。页面即使只查看一天或七天，MAU 仍回看完整 30 日。
- 下方趋势／原有查询接口中的两项指标遵守租户、本人／全员、用户、工作区和 provider 筛选。相同用户跨会话、工作区或 provider 的重复交互只计一人；本人范围只会得到 0／1。顶部四卡现为独立固定概览，不受这些业务筛选影响。
- 夜间重建交互日分区时，顺带生成 `daily_active_users`（用户、工作区、provider 的每日去重存在记录）；随后从这些小型投影分页生成 `active_users` 的每日滚动活跃集合。保留成员身份是为了筛选后仍能正确去重，不在白天读取原始消息计算 MAU。
- 某个历史日期变更时，标记该日及后续 29 日重算；尚未到可发布日期的标记留给后续夜间窗口。无新增交互时，窗口到期仍能正确归零。处理有独立检查点，暂停／失败保留旧发布批次，全部完成才切换。
- 计算版本已升级。旧批次未生成活跃集合时显示“—／等待夜间生成”，不伪装成 0；已生成但确实无活动时才显示 0。历史交互覆盖仍可能为 `partial`。

| 页签 | 支持的分组维度 | 分组后的指标 |
| --- | --- | --- |
| AI 使用 | 用户、工作区、自然日、自然周、自然月 | 会话次数、活跃时长、Skill 发布与被调用次数、区间去重活跃人数 |
| Hook 执行统计 | Hook、用户、工作区、自然日、自然周、自然月 | 执行次数、成功、失败、未结束次数、平均执行耗时 |
| 记录性 Hook | Hook、用户、工作区、自然日、自然周、自然月 | 业务记录数、记录用户数、涉及工作区数 |
| Agent 模板使用 | 模板、用户、工作区、自然日、自然周、自然月 | 应用次数、应用人数、实际活跃人数、会话次数、活跃时长 |

自然周从周一开始；月／周仅汇总所选日期范围内的数据，不自动扩展日期。分组按 ID 而不是名称，同名 Hook／模板不会合并。Skill 发布没有 provider 归属，按 provider 分组时列入未知／不适用组，不猜测模型来源。

日期、用户 ID、工作区 ID、名称，以及相关页签的 provider／Hook 来源／记录类型先筛选；指标上下界在聚合后应用。活跃时长筛选的页面单位为分钟，API 单位为毫秒。合计覆盖全部匹配分组，重新去重用户与会话，不受分页影响；不提供 DAU／MAU 的简单求和。分组指标条件只作用于分组表及其合计，顶部卡片使用独立固定概览口径。

排序与聚合均在服务器对已发布投影执行，排序后才分页（每页 20／50／100 条），不是只排序当前页。API 只接受代码内白名单维度、指标与排序字段，不开放任意 SQL、表达式或自定义公式。查询日期最多 366 天。滚动成员集合需要额外存储，互动分析仍有 SQL 聚合开销；生产启用前需测试容量与时延，不能称为零开销。

## 数据生成与性能策略

| 数据 | 白天留存的依据 | 夜间处理 |
| --- | --- | --- |
| AI 时长 | Claude 主会话 JSONL 的真实用户消息、主助手回复和可核验完成标记 | 逐轮计算历史消息时间区间，按业务日期拆分；错误、缺失边界或无法确认完成的轮次不估算 |
| 在线请求诊断 | Claude SDK 继续写 `ai_usage_turn_facts` | 保留交互证据及采集终态；不生成时长事实，不回填或删除原表 |
| 会话、Skill 调用 | 已有 provider 消息表；Claude 原始 JSONL 与 display-command 侧文件；本地 Skill 绑定历史；`ai_usage_skill_context` 的请求/工具/来源元数据 | 已知归属范围内增量读取，关联去重并排除内部来源，只重算受影响的请求/工具组 |
| DAU／MAU | 复用已有用户交互依据，无额外逐消息写入 | 每日存在投影 → 30 日滚动成员集合，历史补数修正受影响日期 |
| Skill 发布 | 发布链路保存操作结果与首次成功发布证据 | 仅统计 confirmed；不把绑定导入时间当首次发布 |
| Hook | 既有 `hook_data_records`，补齐行为/版本/来源 | 发布版本中的字段白名单投影；按类型和定义版本聚合 |
| Agent 模板 | 既有 `workspace_agent_template_snapshots` | 应用投影与实际会话关联 |

不用 MQ/Redis，不另开微服务。业务表触发器只在原事务内维护“变更来源 ID + generation”，不复制消息正文、不进行聚合。必要的请求边界和 Skill 发布留痕有少量写入开销，不能宣称零开销。

调度器只在窗口内启动 `worker_threads`；Worker 单独连接 SQLite，在后台解析文件与汇总。业务和统计仍共享 SQLite 的写锁，需要上线前测量锁等待、IO、数据库体积和窗口内处理能力。

增量及恢复机制：

- 首次历史索引按来源 ID 分页；后续消费变更标记。每页默认 200 个统计键，先按索引取下一页，再仅对该页候选去重，避免每页重排整个日分区。
- JSONL 持久化完整行字节偏移、文件身份和前缀指纹；尾部半行留到后续批次。文件遍历也保存游标及本批次已见文件，窗口结束后可继续。
- 新原始文件出现时撤销旧数据库副本；原始文件确认缺失后撤销该来源并回退到仍保留的数据库消息。遍历未完成不视为文件删除。
- 本地事实的旧、新业务日期都标记为待重算。当前结果先复制到暂存表，只重算受影响日期，其他日期保留复制的结果。
- 全局 Worker 租约、每租户批次租约及持久化游标防重复执行；摘要更新与源游标同事务，旧租约不能发布。
- 新批次完整后事务替换正式明细，并同时更新成功状态。失败、暂停不替换上一成功结果；源数据较晚发生变化时保留下一次处理标记。发布需复制全租户结果，不再声称只切指针的常数成本。
- Hook 原记录删除立即通过删除遮蔽表阻断旧明细。删除 revision 不匹配时字段汇总回退到剔除已删除记录的白名单投影，不读取原始聊天。

这是非实时滚动读取，不是所有外部文件在同一瞬间的全局快照。页面的“数据截至”表示业务日期范围，不代表该日所有外部历史都已完整到达。

## Skill 调用口径（9 月 12 日调整）

- 只纳入原生 `Skill` 工具调用，以及用户实际提交、且可验证对应真实 Skill 的 `/名称` 命令。不识别 Read/Bash 读文件，也不从普通文本提及中猜测使用。
- `/help` 等命令不能仅凭斜杠计为 Skill。验证依据为业务时点有效的 Skill 绑定，或同一请求下匹配的原生 Skill 工具/SDK Skill 展开记录；只有文本候选而无依据时不计。
- 同一请求、同一分支、同名 Skill 的斜杠与对应工具调用合并；不同 `toolUseId` 保留独立计数。调用次数表示调用发起，不等于执行成功次数。
- 排除 Hook、Agent Graph、Top Skill 来源，包括可信标记的内部后续工具。按来源排除，而非把同名 Skill 永久拉黑。Hook 子代理标记仅影响注入之后的对应分支，之前的用户调用保留。
- 白天的 `ai_usage_skill_context` 仅记录可信租户/用户/工作区、请求 UUID、工具 ID、Skill 名称、时间、来源和可确认的子代理 ID；不存提示词或参数，不逐 token 写入。MCP 恢复继承原请求，不另造一次斜杠使用。
- JSONL 保存请求上下文与文件字节断点；数据库回退保留安全请求边界，夜间关联工具；同时间戳按既有 provider 消息序号判断先后，不按 UUID 排序猜测。display-command 侧文件仅补原命令名，必须匹配真实消息时间，不使用文件修改时间。
- 夜间先按页保存变更会话的元数据引用，再按请求/独立工具组重算。页游标与临时引用同事务保存，单个请求组原子替换；不会把整个会话证据塞入任务进度 JSON。迟到工具会替换原斜杠事实，并重算旧、新日期；优先采用真实工具发起时间。
- 计算版本已升级，下一次启用的夜间任务会重新索引旧定义；暂停的旧定义批次重建未发布部分，保留上一份已发布看板。

覆盖仍为 `partial`：历史来源/原消息丢失、旧目录名与命令别名不一致，以及 SDK 合并输入后无法确定工具所属请求时，不声称可完整关联。未知来源的明确原生工具保留，但不伪造其请求归属。发布者归因仍沿用可核验绑定；跨用户导入且缺少发布者平台身份的调用仍未补齐，不算给调用者，也不宣称租户共创总数已全覆盖。

## 会话归属冲突的隔离与恢复（2026-10-12）

夜间批次遇到 `SESSION_SUMMARY_SOURCE_SCOPE_CONFLICT` 时，按完整的租户／工作区／用户／提供方／会话身份隔离该会话，继续发布其他结果。被隔离会话的会话次数、时长、Skill 调用、生成 SQL、会话汇总及 DAU／MAU 贡献统一排除；独立的 Hook 业务记录、Skill 发布和代码提交不因同名会话 ID 被删除。原始事实和业务会话归属均不修改。

`ai_usage_session_issues` 保存冲突原因、统计归属 `expected_json`、索引归属 `actual_json`、首次／最近发现时间及 `open`／`resolved` 状态；`ai_usage_batch_session_exclusions` 保存各批次的隔离名单。同批名单只增不减，续跑不重复计数。管理员核实并修复原始归属后，后续窗口自动复查并重排相关历史日期，补算成功发布后才标记 `resolved`。仅修改元数据也会触发这条恢复链路，不依赖新增消息。

有隔离记录的批次仍为 `published`，`coverage_json.sessionScope='partial'`、`excludedSessionCount` 为去重会话数。看板显示“统计已更新，N 个会话因归属冲突暂未计入”，个人范围只显示本人数量。发布前再次检查所有保留会话；若归属此时变化，先重建受影响候选再原子发布，避免概览、明细和汇总口径不同。

PM2 收集的应用日志现在包含 `[AI usage] batch_started`、`Session scope conflict quarantined`、`batch_published`、`batch_paused` 和 `batch_failed`。隔离告警含批次、完整会话身份和两边归属；发布日志含排除数量。暂停的 `reason=window_ended` 表示窗口结束，`stop_requested` 表示服务收到停止请求。事实字段与身份不一致、工作区跨租户、数据库异常、租约失效等仍按失败处理，不会当成可忽略告警。

计算版本升级为 `session_scope_v12`：旧失败／暂停批次会重建未发布候选，保留上次成功的结果；部署后仍只在配置窗口内运行，不需要手工删除批次或统计表。

## 闲时配置

`.env.example` 已提供以下项目；默认关闭统计。确认运行环境、容量和业务策略后再配置实际部署环境并重启服务：

```dotenv
AI_USAGE_ENABLED=true
AI_USAGE_RUN_AT=02:00
AI_USAGE_WINDOW_END=06:00
AI_USAGE_TIMEZONE=Asia/Shanghai
AI_USAGE_DATA_LAG_DAYS=1
AI_USAGE_MAX_CONCURRENCY=1
```

时间格式为 `HH:mm`，时区必须是有效 IANA 名称。非法配置会记录错误并关闭调度，不默默改用另一时间。窗口结束暂停，保留检查点；服务启动在白天不会补跑，窗口内启动则尝试恢复。启动应用会按既有机制迁移新表；即使统计关闭，必要的业务事实留痕仍保留，`AI_USAGE_ENABLED` 控制的是夜间处理。

### 租户统计并发（2026-10-13）

`AI_USAGE_MAX_CONCURRENCY` 默认 `1`，允许正安全整数 `1..9007199254740991`，可设为大于 `1` 的值。它控制同时处理的租户数上限；设为 N 时，实际最多同时处理 `min(N, active tenants)` 个租户。例如配置为 `4` 而只有 2 个活跃租户，最多同时处理 2 个租户。零、负数、小数及超出安全整数范围的值均属非法配置。

并发由单个 statistics Worker 内的异步租户任务池实现：不同租户等待文件读取等异步 I/O 时可以交错推进；同步解析和 SQLite 事务仍在该 Worker 内串行执行。这不会让单个租户获得多核解析提速。共享数据库的全局租约保证 PM2 多进程部署时也只有一个统计任务池，各租户仍使用独立批次租约防止重复处理。

单个租户失败会记录该批次错误，其他租户继续统计。窗口结束、服务收到停止请求或全局租约失效时，任务池停止派发新租户，并等待所有已运行任务保存检查点或退出后再结束；租约失效的任务不能发布结果。

修改并发配置后需要重启后端服务。重启后查看 `/api/ai-usage/status` 返回的 `maxConcurrency`，确认进程已读取新配置；该字段是配置的租户数上限，不是当前正在运行的租户数量。

### 统计截止日期（2026-09-30）

`AI_USAGE_DATA_LAG_DAYS` 控制数据截止日，与任务执行时刻 `AI_USAGE_RUN_AT` 分开配置，默认 `1`，允许 `0..3650` 的整数。以执行窗口开始日为 T，按 `AI_USAGE_TIMEZONE` 计算：`1` 截至 T-1，`0` 包含 T 当天已读取的数据，`2` 截至 T-2。它改变截止日，不是只统计最近 N 天；已有历史和增量处理仍保留。

例如上海时间 9 月 30 日启动的窗口：`1` 的最后统计日是 9 月 29 日，`0` 是 9 月 30 日，`2` 是 9 月 28 日。跨午夜窗口仍以开始日为准。`0` 只用于验证当天已有数据，不代表全天完整结果，也不会开启实时刷新；批次 `coverage_json.partialDay=true` 表示发布时统计日尚未结束，`coverage_json.dataLagDays` 保存本批配置。

生成 SQL 行数在该窗口内扫描会话中的 AI 回复（原生会话优先、数据库会话记录作为回退），识别 SQL 片段并按物理行计数；不依赖 Hook 的 SQL 记录。相同消息按稳定标识更新，同一回复的相同 SQL 片段去重，不把用户输入计为生成量。旧明细、拆分表和看板仍通过同一候选批次原子发布。

测试可设 `AI_USAGE_ENABLED=true`、`AI_USAGE_DATA_LAG_DAYS=0`，并将 `AI_USAGE_RUN_AT` 和 `AI_USAGE_WINDOW_END` 设为覆盖当前时刻的窗口，重启后端。每个租户、每个执行窗口仍只成功发布一次：若该窗口已经完成，仅修改截止日不会重复执行；需将 `AI_USAGE_RUN_AT` 改为另一个尚未执行的时刻（且当前仍在窗口内），或等待下一窗口，不要删除真实批次。

未完成批次在截止偏移变更后会重建候选数据，不混用旧检查点；缩小范围时仅从候选结果排除较晚日期，源数据和已发布结果在新批次成功前不变，之后扩大范围仍可恢复。配置仅在重启时读取。本地 `.env` 保持默认 `1`，没有自动开启任务或改动真实统计数据。

跨日示例：9 月 11 日 23:58 发起，9 月 12 日 00:03 完成。9 月 11 日分到 2 分钟、9 月 12 日分到 3 分钟。12 日凌晨任务发布前一天的 2 分钟；13 日凌晨发布后一天的 3 分钟。如果首次运行时终点尚未确认，不预估时长；终点之后补齐，会重算相关历史日期。查询两天合计仍为 5 分钟，不根据下一次提问补空闲时间。

多轮并发按独立历史轮次相加，不做区间并集；错误、取消、未完成或缺少完成证据的轮次不贡献时长，不用当前时间补终点。在线请求表中的 pending／failed／unsupported 等是采集诊断，不再决定文件时长覆盖。切换业务时区或计算版本会在后续夜间重新索引，并在完成前保留旧批次及其时区。

- 历史 SQL 指标类型有固定数值适配；其他未配置类型显示字段不可用，不复制原始 `data_json` 或会话正文。

### 时长异常记录隔离

`duration_isolation_v13` 引入逐条时长异常隔离；v15 切换历史文件时间边界后，仍沿用跨日切片、并发求和及异常隔离。索引阶段对异常历史边界只舍弃该轮时长，保留起点有效的交互；来源去重后、聚合前校验每条时长事实，异常 JSON、非数字／负数／非整数、无效边界或累加溢出只跳过当前贡献。正常累计不被覆盖或归零。会话汇总中的异常完成时间桶也只影响该桶。

PM2 中搜索 `[AI usage] duration_record_skipped`，可看到批次、租户、阶段、记录标识和原因，不输出消息正文或原始 JSON。每阶段最多记录 20 条详细警告；`batch_published.skippedDurationRecords` 和批次 `coverage_json.skippedDurationRecords` 保存本批扫描时跳过的完整数量，`progress_json.durationAnomalies` 按阶段计数。它们是该次扫描的诊断数量，不是整个历史范围中仍待修复记录的存量。

原始事实不删除，源记录修改后按现有增量机制重算。版本升级会重建旧候选及原始事实对应分区，发布仍为原子替换。数据库锁、租约丢失、窗口关闭、归属冲突和陈旧报表格式不按普通坏时长吞掉；沿用原有失败／暂停／冲突隔离流程，保留上次已发布快照。


### v15：AI 时长改从主历史文件重建

夜间从可信租户／用户／工作区的 Claude 主会话 JSONL 中识别每轮真实用户消息，累计其时间戳到该轮最后主助手回复时间戳的区间。完成证据包括明确 `end_turn`、`system/turn_duration`、成功 result 和 `completed-replies.jsonl` 对应回复标记。后几类只确认完成，不用标记落盘时间扩大终点，也不直接累加 provider 的 duration 字段。统计范围内独立轮次相加，按原自然日规则切片；不取会话首尾、不用下一次输入或文件 mtime 代替完成。

fork 继承、元消息、Hook 恢复、子代理内部轮次和工具返回不新增时长。主轮次内部的工具执行、MCP 等待直到最终主回复仍处于该区间，子代理耗时不另加。错误、未结束和缺完成证据的轮次保留覆盖诊断，正常轮次继续累计。SQL 可使用原有数据库消息回退，但时长不会因为存在数据库文本副本或旧请求表就猜造历史边界。

这是边界来源变更：原采集采用服务端请求登记时间与运行时 Stop／主回复接收时间，现采用历史 user／assistant 消息时间；环境准备、输入排队、缓冲及 Stop 后置动作的时间位置可能不同，新旧结果不保证完全一致。`ai_usage_turn_facts` 及在线写入保留，夜间仅将其用作互动证据和采集诊断，不再产出 turns 时长，不与文件时长双计；不向该表回填或删除原行。共享的 Skill 采集连接、聊天权限、并发控制和 MCP 恢复流程不因本次切源改变。

计算版本 v15 使下一个可认领批次回扫现存主历史，并移除 `source_key='turn:…'` 的旧派生时长，包括原请求行已丢失的孤儿事实。历史互动证据保留，时长覆盖依据改为新来源。未完成旧版本批次重建候选，已公开快照一直保留到新明细、宽表、主题表和会话汇总同事务发布。当天已成功发布的计划不会因部署立即再跑。文件不可读、归属冲突和缺失历史不能承诺补齐全部数据。


同一逻辑轮次的重复历史文件按整轮选择优先来源，随后才按日期取切片；失败／较短修订会重排所有来源涉及的旧日期，避免保留旧副本的跨日耗时。首选文件消失后可恢复备用来源。新增 `idx_ai_usage_turn_sources` 索引仅作用于派生表 `ai_usage_fact_rows`，支持整轮来源选择；`ai_usage_turn_facts` 的表结构没有变化。
