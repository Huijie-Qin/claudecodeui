# 技能市场：运营与管理员使用视角

日期：2026-09-16

定位：从用户目标出发梳理本次待实现功能，不展开已有基础操作和技术实现。不代表以下能力已在生产环境上线。

配套阅读：[功能分类与完整交互流程](skill-market-功能分类与完整交互流程.md)｜[技术改造清单](skill-market-待实现功能设计.md)｜[交互原型](prototypes/skill-market/index.html)。

介绍时可直接使用文末的[双视角演讲稿](#7-介绍演讲稿从运营和管理员两个视角展开)，以第一阶段为主，配合原型讲解约 6–8 分钟。

## 0. 本期先做什么

第一阶段只上线：会话描述创建 Skill、片段库、用例管理、静态检查与后台串行测评、有限次自动优化。下文模板、贡献、版本管理及发布治理均为后续规划，不要求运营先学习或配置。

- 运营：点“技能创建”输入需求 → 自动保存 → 直接调用 → 保存用例 → 运行全部/自动优化。
- 系统管理员：维护平台共享片段、保障测试环境与运行额度。普通用户可看可用片段但不可维护。
- 首期创建不填写技能标识；creator 生成合法 name，服务端防冲突校验。运营仍可直接编辑 Markdown。
- 首期验收使用[第一阶段原型](prototypes/skill-market/phase1.html)；[整体原型](prototypes/skill-market/index.html)的模板、贡献等是后续规划演示。

## 1. 先分清业务身份和操作权限

“运营”和“管理员”是两种使用视角，不是互斥的两个账号类型。运营创建 Skill 后成为该 Skill 的负责人；取消指定 Skill 管理员角色。负责人身份不代表拥有平台片段或模板库维护权。

| 本文身份 | 主要关注 | 权限来源 |
| --- | --- | --- |
| 普通运营 | 描述生成、调整/调用、用例与测评优化；后续模板及贡献评审 | 工作区访问/编辑权与 Skill 查看权 |
| 运营兼技能负责人 | 除上述能力外，维护所负责 Skill 的人员、分类、发布和贡献处理 | 创建时成为负责人，或被转移为当前负责人 |
| 模板管理员 | 准备运营可直接使用的生成模板 | 对模板库的明确维护授权，沿用当前租户范围 |
| 系统管理员 | 维护全平台公共片段 | 系统管理员权限；不自动成为每个 Skill 的负责人 |

只读工作区的运营可以浏览，但不能创建/改文件/运行优化。负责人治理权限也不能代替工作区编辑权限。模板管理员不自动获得全平台片段维护权；负责人不自动获得模板或片段维护权。

## 2. 运营视角：我需要完成什么

### 2.1 功能地图

| 我的目标 | 从哪里开始 | 我需要做什么 | 系统完成什么 | 对应流程 |
| --- | --- | --- | --- | --- |
| 快速做一个新技能 | 聊天“技能创建” | 直接描述需求并发送，不填标识 | 生成 name、校验并自动保存 | C0 |
| 让技能更贴合需求 | 当前会话或我的技能文件编辑 | 继续描述调整要求，或直接改 MD | 会话修改检查后保存；更新本地内容 | C2 |
| 加入常用要求/能力名称 | 文件编辑“快捷插入” | 选片段、Skill 或 MCP 名称 | 插入普通文本，不启用工具 | A3 |
| 验证实际效果 | 普通会话 | 直接调用 Skill，查看回答/文件 | 按原聊天展示完整执行 | C3 |
| 把一次调用变成回归样本 | 调用完成后的消息底部 | 点击保存为测评用例 | 提取本次输入/输出，直接保存 | C3、D |
| 补充业务场景 | 我的技能测评 | 手工添加，或点击 AI准备场景 | 按统一格式保存到同一文件 | D2、D3 |
| 看技能是否符合预期 | 我的技能测评 | 点击运行全部，查看未通过项 | 静态检查、串行运行、自动判定 | E |
| 让 AI 修正技能 | 我的技能测评 | 点击自动优化，看输出/文件对比 | 全量前测、改文件、全量后测 | F |
| 把修改贡献给原技能 | 我的技能提交贡献 | 写说明、核对文件变化、提交 | 建立请求，交由评审和合并 | G1 |
| 帮别人评审 | 市场 Skill 贡献 Tab | 看多个文件 Diff、评论/Approve | 记录对当前内容的评审 | G2 |
| 发布我负责的技能 | 我的技能操作区 | 本人测评通过后确认发布 | 校验当前内容并更新市场报告 | H2 |
| 查看市场是否有新内容 | 我的技能更新提示 | 核对本地与远端差异 | 按导入对照时间判断、成功后同步 | I2 |

以上流程编号对应第一份文档。运营不需要理解容器、任务队列、评分 Agent 的部署或 JSON 状态字段，只有需要直接查看/编辑用例源文件时才接触 JSON。

### 2.2 场景一：从业务想法到一个可使用的 Skill

以“创建门店销售分析技能”为例：

1. 我在会话底部点击“技能创建”，输入区变为描述需求的区域，不弹模板或技能标识表单。
2. 我写“帮我把门店销售数据整理为周报，说明退款、异常和数据来源”。按钮从点击到发送前持续高亮，失焦也不退出。
3. 再次点击可退出并保留文字；空描述发送就地提示，不丢输入。发送后系统在独立环境调用 skill-creator，期间不能重复提交。
4. AI 参考公共片段，生成合法名称并校验文件，同名不覆盖。无需我配置库或运行环境。
5. 生成成功即保存到“我的技能”，会话展示实际名称；没有确认保存。创建模式退出，随后可继续调整或 /name 直接调用。
6. 失败/取消时说明原因，保留需求供重试，不留下半成品。

**后续模板路径：** 模板中心、我的技能“模板创建”、会话独立的“使用模板（后续）”进入模板填写。通用模板也不再要求填写名称和标识，由 creator 自动生成；选中模板时按钮高亮。其他专用模板字段暂不变。已有手工创建仍沿用原表单。

**我不必做：** 创建模板、配置片段匹配规则、手动启用工具、切换到另一个专用生成页面。

### 2.3 场景二：直接调用，并把结果保存为用例

1. 我在普通聊天中输入 `/store-sales-analysis 分析这份测试订单`，附上允许使用的材料。
2. 我仍看到熟悉的聊天：回答、工具调用、子任务、生成文件。没有“先试用技能”的按钮，也没有独立调试模式。
3. 整次调用完成后，消息底部出现“保存为测评用例”。我觉得这次业务输入值得以后反复验证，就点击保存。
4. 系统直接保存输入和结果参考，不再要求我确认验收标准；按钮显示已保存，并可查看用例。
5. 我继续聊天，或者去我的技能 → 测评看到新增行。用例也能在 `evals/evals.json` 找到。

**需要理解：** 保存下来的原输出只是预期参考，不保证原输出一定正确。发现错误预期可在用例编辑中修正；不是让后续回答逐字复述这次回答。

**失败时：** 调用尚未完整、资料不适合共享、关键附件缺失或没有编辑权限，系统说明原因，不假装保存成功。重复点击不会产生重复样本。

### 2.4 场景三：不依赖聊天记录，也能自己补场景

我进入我的技能 → 测评，在“添加验证场景”中选择：

- **添加场景：** 填输入、希望达到的结果，可选补充检查要点和测试文件，点保存就生效。例如“没有订单数据时不能编造销售结论”。
- **AI准备场景：** 让 AI 基于现有 Skill 和已有用例补充场景。合法生成后直接出现在表中，没有待确认草稿列表。

我可以编辑已有用例，也可以删除从未发布的用例；曾随 Skill 发布的用例显示不可删除的原因。需要修改其预期时可以编辑，但旧测评就不再证明当前定义通过。

**运营需要处理的只是必要信息：** 缺业务口径时补充标准；不合法字段按提示修复。不需要填写 runId、版本号或手动维护一份数据库用例。

### 2.5 场景四：检查当前技能是否满足预期

1. 在测评页点击“运行全部”，页面不跳转；提示本次使用启动时固定的 Skill、用例和资料副本。期间修改可以保存，不会影响任务，我看到逐条进度。
2. 系统先做文件和资源的静态检查，再串行运行全部用例；不需要我逐个点击开始。
3. 一个业务场景不通过不影响后续正常场景继续检查。异常、无法确定和未运行会单独显示，不混为通过。
4. 我点击某一行查看详情：顶部是输入和预期，下面按会话格式展示完整实际输出、工具、子任务和文件；判定及依据单独展示。
5. 如果只是想观察效果，此时不会改变 Skill 文件，也不会发布。
6. 我离开或刷新后可以回来查看同一任务；需要结束时点击停止，已完成结果保留。

**我如何理解结果：**

| 页面结果 | 对我的含义 | 下一步 |
| --- | --- | --- |
| 通过 | 本次这个场景满足预期 | 继续使用，或按权限发布 |
| 不通过 | 输出有明确未满足要求的部分 | 看依据，自动优化或改正文/用例 |
| 无法确定 | 证据不足以得出结论 | 补充可验证标准或资料后重跑 |
| 运行/评分异常 | 环境、工具或评分过程未正常完成 | 根据提示处理后重跑，不能当业务通过 |
| 未运行/已停止 | 没有完整验证这一条 | 需要时再运行全部 |
| 结果已失效 | 文件、用例等已变，旧报告不对应当前内容 | 基于当前内容重新运行 |

### 2.6 场景五：让 AI 自动改进技能

1. 我点击“自动优化”，设置最大迭代次数（默认 3，可填 1–10 的整数），再点“开始优化”。取消不启动。
2. 系统先完整前测；已全部通过就结束，执行 0 次迭代，不修改文件。
3. 有失败时 AI 对照预期与实际修改并自动保存，再完整复测。仍未通过且没到上限就继续；一次优化尝试加全量复测计一次，没有差异也计数。
4. 我留在测评页看“已执行 X / N 次迭代”，无需跳转会话。全部通过提前结束；达到上限仍失败会明确提示，不代表技能通过。
5. 详情左边是初始前测，右边是最新复测（标注轮次），均展示完整会话输出，包括工具、子任务、文件，不仅是摘要。
6. 我可查看 Skill 开始前与最终已保存状态的文件 Diff，无需确认采用。异常、证据不足、人工停止会结束；解决问题后可再发起。

**我必须知道的三件事：**

- 无并发编辑时修改自动回写；若我在期间修改了文件，任务继续在副本执行，冲突产物保留但不覆盖我的新内容。已经写入的修改在复测失败或停止后仍保留，页面明确告知。不会暗中回滚，也没有历史版本恢复功能。
- AI 不能靠改掉用例预期、删除难例或开放生产工具来获得通过。
- 优化只改本地，不会自动更新市场。共享发布仍由负责人显式执行。

### 2.7 后续场景六：改好了别人的 Skill，提交贡献

1. 我在本地调整某个市场导入的 Skill，保存修改后点击提交贡献，写清用途和原因。
2. 我核对全部变更文件，左侧选文件，右侧看前后 Diff，确认后提交。不要求先测评。
3. 从市场该 Skill 的贡献页查看自己的请求状态和意见，不再有顶部贡献中心。
4. 其他人要求调整时，我修改本地内容并显式更新贡献；旧认可失效，需要重新评审。
5. 有权限的人合并后即更新市场内容；我看到已合并，不再额外等一次发布操作。

**我不能做：** Approve 自己的请求；仅凭本地编辑权合并；把未测评当成贡献提交失败原因。贡献合并后市场显示“未测评”，不是自动借用我本地的报告。

### 2.8 后续场景七：我只是来帮助评审

1. 在技能市场打开具体 Skill → 贡献，可以看该 Skill 的全部可访问请求，不要求别人先指派给我。
2. 打开请求，逐个文件查看 Diff，发表评论、建议修改，或对他人的当前内容 Approve。
3. Approve 不代表自动发布，也不会让我拥有合并权；只有负责人执行合并。
4. 作者更新内容后，我的旧认可失效，重新查看后再决定是否认可。

### 2.9 场景八：我是自己创建的 Skill 的负责人

运营创建成功后初始为该 Skill 的负责人，额外获得以下操作：

| 目标 | 操作位置与流程 | 必须注意 |
| --- | --- | --- |
| 发布当前成果 | 本人完成当前内容测评 → 点击发布 → 核对并确认 | 不能用他人的报告；改完文件必须让报告重新适用 |
| 处理他人贡献 | 收到的贡献或市场贡献页 → 看 Diff/意见 → 合并 | 正常路径有他人认可；负责人也可直接合并，无测评 |
| 交接负责人 | 版本管理 → 选择新负责人 → 核对转移 | 原负责人失去隐式治理权，不自动成为管理员 |
| 调整分类 | 版本管理 → 修改分类并保存 | 只有负责人可做 |
| 停止市场分发 | 沿用下架操作 | 新增贡献/报告记录和本地文件保留，无历史版本页 |

“我创建过”与“我目前负责”不同：负责人转移后，权限以当前负责人为准。

### 2.10 普通运营不需要面对的内容

- 维护模板结构、片段分类体系、片段版本或引用关系。
- 每次生成后确认保存、每次新增后确认验收标准、每次优化后确认采用。
- 配置串行队列、启动 Claude 容器、创建独立评分 Agent。
- 为了测评跳到另一聊天页面，或在专门调试状态与普通聊天之间切换。
- 手工保存多套用例或通过历史版本理解技能更新。

减少这些操作不取消必要的权限检查、格式提示、业务信息补充和市场发布确认。

## 3. 管理员视角：准备公共能力与管理技能

此处区分系统管理员的公共库维护与技能负责人的治理职责，不再设指定 Skill 管理员。界面根据实际授权显示操作，不用一个笼统的管理员开关开放全部功能。

### 3.1 系统管理员：维护运营可复用的片段

**目标：** 把重复出现的业务规范沉淀为固定正文，让运营或 creator 使用。

1. 进入技能区域 → 片段管理，新增片段，填写名称、说明和 Markdown 正文。
2. 检查内容能否跨所有租户共享，不写客户私密信息、生产凭据或租户专有配置。
3. 保存后普通用户可查看，文件编辑可快捷插入，模板管理员可选择其正文预置到模板。
4. 需要更新时直接编辑当前片段，不新建业务版本。
5. 不再适用时核对并删除；删除只影响当前库可用内容，不回改已经生成的 Skill 或已经复制到模板的正文。

**管理员需要注意：** “规范片段”不等于安全控制，例如写了 SQL Check 要求不代表平台自动启用了 SQL 检查。没有已插入 Skill 的实时引用跟踪，不承诺“一改全生效”。

**不是这类管理员的职责：** 自动替所有 Skill 发布、认可自己的贡献、读取所有租户私有测评轨迹。额外权限必须另行获得。

### 3.2 模板管理员（后续）：让运营只填业务信息

**目标：** 预先组织模板，减少运营每次描述和配置的负担。

1. 进入模板中心新建模板，明确名称、描述及用途。
2. 配置运营真正需要提供的信息，例如业务范围、输出风格、分析口径；设置字段类型、必填与合理默认值。
3. 配置合适的预置片段，查看模板将带入的正文。
4. 保存前修复重复字段、保留标识冲突、默认值不匹配等问题；保存后运营可查看并在会话使用。
5. 修改模板只影响后续生成，不自动修改已有 Skill；删除后不再可选，但已生成文件保留。

**设计准则：** 能给可靠默认值的就给默认值；不要把运行环境、评分器参数、片段选择负担塞给运营。首期直接创建与后续通用模板的 name 都由 creator 生成，不需运营填写；其他专用模板暂保留原字段。

**权限范围：** 授权模板维护不自动授予全平台片段 CRUD。模板仍沿用当前授权/租户范围；如果以后也要全平台共享，需要单独决定，不在本次自动扩大。

### 3.3 负责人：版本管理与发布

“我的技能 → 该技能 → 版本管理”取代原管理 Tab，仅负责人可见，显示当前技能全部贡献请求；没有跨技能贡献收件箱，也不新增历史版本。

1. 查看请求时，左侧选择变更文件，右侧看修改前后 Diff，结合评论和当前认可判断。
2. 只有负责人可以合并；有认可时正常合并，没有认可也可确认直接合并。任何人都不能认可自己的请求。
3. 合并即更新市场发布，不需要测评；成功后当前内容显示“未测评”。
4. 普通直接发布仍需要负责人自己的适用测评报告通过；贡献合并是另一条路径。
5. 转移负责人、修改分类保留在本模块；取消指定技能管理员和相应配置。
6. 普通用户仍可在市场技能贡献页提交、跟踪、评审。平台管理员不会因库维护身份获得合并权。

### 3.4 权限如何区分

| 能力 | 普通运营 | 当前技能负责人 | 系统管理员 |
| --- | --- | --- | --- |
| 查看/使用公共片段 | 可以 | 可以 | 可以维护 |
| 编辑与测评本地 Skill | 按工作区权限 | 同样按工作区权限 | 不自动拥有所有工作区权限 |
| 市场贡献查看/非作者评审 | 按技能访问权限 | 可以，但不能自我认可 | 不额外扩权 |
| 我的技能“版本管理” | 不可见、不可访问 | 查看当前技能全部请求 | 只有同时是负责人时可访问 |
| 合并与发布 | 不可以 | 可以 | 只有同时是负责人时可以 |
| 转移负责人/修改分类 | 不可以 | 可以 | 不因系统角色获得 |

### 3.5 管理侧异常该如何处理

| 情况 | 管理员看到什么 | 正确后续 |
| --- | --- | --- |
| 发布条件不满足 | 缺本人当前适用报告或内容已变 | 由实际发布人重新测评，不绕过门禁 |
| 贡献没有有效认可 | 可继续等待评审，也可直接合并 | 负责人核对内容后明确确认直接合并 |
| 远端内容变化 | 基线冲突，需要重新核对 | 处理差异、更新候选并重新评审，不静默强推 |
| 远端结果暂时不明 | 待核实 | 先确认状态，不反复点击发布/合并 |
| 权限不足/已撤销 | 明确拒绝当前操作 | 由当前负责人处理，不能用旧页面或他人凭据绕过 |
| 旧公共片段有误 | 可以编辑库，已用内容不会联动 | 如需修改某个 Skill，按其本地编辑/贡献流程处理 |

这些是必要的业务反馈，不要求为本期另建复杂的运营监控后台。成本配额、隔离环境和证据保留期属于首期必要的技术实现/部署配置，不混入运营日常创建表单。

## 4. 一个跨角色的完整例子

以下只描述拟实现的交互，不表示新增通知渠道或自动任务授权。

| 顺序 | 角色 | 行为 | 交付给下一角色/阶段 |
| --- | --- | --- | --- |
| 1 | 系统管理员 | 创建“销售统计口径”固定片段 | 公共正文可查看/使用 |
| 2 | 模板管理员 | 创建“门店分析”模板，配置业务字段和预置正文 | 运营可在会话选择的模板 |
| 3 | 运营小林 | 首期直接描述；后续可选模板并填写，发送 | 已自动保存的本地 Skill；小林为负责人 |
| 4 | 运营小林 | 普通调用并保存用例，补一个无数据场景 | 同一份 evals/evals.json |
| 5 | 运营小林 | 自动优化 | 初始前测/最新复测、迭代次数与结束原因、已保存修改和文件 Diff |
| 6 | 负责人小林 | 本人适用报告通过后确认发布 | 市场 Skill 与公开报告 |
| 7 | 其他运营小周 | 修改自己授权工作区内的导入副本，提交贡献 | 带全部文件 Diff 的请求，无测评门禁 |
| 8 | 非作者小陈 | 查看并 Approve 当前贡献 | 一位有效非作者认可；小周不能自己认可 |
| 9 | 负责人小林 | 在版本管理中合并请求 | 立即更新发布；市场显示未测评 |
| 10 | 运营小林 | 看到市场有更新，核对本地差异后同步 | 成功同步后才更新导入对照；本地报告重新判断适用性 |

非作者小陈可以评审，但不能合并；只有负责人小林执行合并。小林也可在没有他人认可时直接合并，但仍不能 Approve 自己的请求。

## 5. 两种视角共用的页面文案与理解

| 用户看到的词 | 应理解为 | 不应理解为 |
| --- | --- | --- |
| 模板/片段只读 | 不能修改公共定义，可使用 | 不能用它生成或编辑自己的 Skill |
| 我的技能 | 当前工作区里的本地技能 | 每个用户有一套与同目录隔离的用例数据库 |
| 运行全部 | 后台逐例执行与判定，不改 Skill | 跳聊天、并行跑所有用例或自动发布 |
| 自动优化 | 初始前测 → 有限次修改落盘与全量复测，全部通过提前结束 | 等待采用、只跑失败例、无限循环或达到上限就是通过 |
| 查看详情 | 完整可见输出与独立判定 | 几句摘要、隐藏的模型内部推理或可再次执行的聊天 |
| 已保存修改 | 本地文件已经改变 | 市场已经发布；后测失败会自动还原 |
| Approve | 对他人当前贡献的认可 | 获得合并权或已经发布 |
| 合并 | 直接更新市场发布内容 | 只是保存到负责人本地，之后还必须测评 |
| 未测评 | 当前市场内容没有适用报告 | 不能提交贡献，或可以借用旧报告当通过 |
| 待更新 | 市场时间晚于本地导入对照 | 只比较本地最近编辑时间 |

## 6. 从用户体验出发的验收问题

### 运营验收

- 能否不创建模板、不手选片段，仅补充业务信息就生成并直接得到 Skill？
- 能否在原聊天继续微调、直接调用、一次点击保存用例，而不进入专用调试状态？
- 能否自己或让 AI 补场景，不确认草稿且与文件内容一致？
- 能否只看一张表理解运行进度，在详情看完整输出，在左右两列看优化差异？
- 能否知道优化修改是否已保存、是否已发布、结果是否已失效，不依赖技术术语猜测？
- 能否在不是负责人时维护本地副本、测评、贡献并评审他人，同时不会误获得发布权？

### 管理员/负责人验收

- 公共库维护权限是否与 Skill 发布/合并权限分开，普通用户是否能看但不能改库？
- 修改片段/模板后是否明确只影响未来使用，不产生“所有技能会自动更新”的误解？
- 普通用户是否看不到版本管理，旧技能管理员授权是否失效，只有当前负责人才能访问和合并？
- 直接发布是否要求实际发布人本人当前测评通过，贡献合并是否明确免测评？
- 是否禁止所有角色认可自己的请求，候选改动后旧认可是否失效？
- 远端状态未知、权限撤销、发布基线冲突时是否明确停止和提示，而不是误报成功？

这份视角文档不增加新的权限；具体完整交互与异常分支以[功能分类文档](skill-market-功能分类与完整交互流程.md)中的同名流程为准，技术接入与待验证限制见[待实现功能设计](skill-market-待实现功能设计.md)。

## 7. 介绍演讲稿：从运营和管理员两个视角展开

使用建议：按“为什么做 → 运营怎样用 → 管理员怎样支撑 → 本期边界”讲述，不按页面逐个念功能。以下正文可直接口述；斜体的演示提示不需要念出来。本次展示的是方案与模拟原型，不是已上线能力。优先打开第一阶段原型，避免把后续规划误讲成本期交付。

### 7.1 开场：我们希望解决什么问题

大家好，今天我想从运营和管理员两个视角，介绍一下这次技能市场的优化设计。

我们这次的目标，不只是让大家更方便地创建一个技能，而是让技能在使用之后，能够被持续验证，再由 AI 根据验证结果进行改进。尽可能把反复运行、比较结果、修改内容这些工作交给 AI，让运营主要关注两件事：我想解决什么业务问题，以及什么样的结果才符合业务要求。

第一阶段，我们先把这条链路做完整：描述需求、生成技能、实际调用、积累验证场景，再进行测评和自动优化。模板、贡献和新的发布管理流程先不加入本期。下面展示的是这套流程的设计原型，生成和测评结果目前都是模拟的。

### 7.2 运营视角：从“描述需求”到“让 AI 改进技能”

*演示提示：打开会话，点击输入框底部“技能创建”，填写业务描述。*

先假设我是一名运营，每周都需要整理门店销售周报。我不需要先学习模板怎么配，也不需要填写一个技术性的技能标识。我只要在平时使用的会话里点击“技能创建”，然后描述：“帮我根据门店销售数据生成周报，要扣除退款、说明异常，并列出数据来源。”

点击之后，这个按钮会持续高亮，让我知道当前写的是创建需求，而不是普通聊天。发送后，系统会调用 skill-creator 生成技能，检查名称和文件，并直接保存到“我的技能”。不需要生成后再点一次确认保存，也不会因为同名而覆盖已有技能。

生成之后，我还可以在同一个会话里说：“再增加一个与上周对比的部分。”AI 就继续调整这个技能。如果我希望自己精确修改，也可以直接编辑 Markdown。我们减少的是不必要的操作，不是拿走运营的编辑能力。

*演示提示：直接调用刚生成的技能，展示结果底部“保存为测评用例”。*

接下来，我会像平时一样直接调用它，给它一份测试数据，看看真实的业务效果。这里没有另外一套调试页面，也不需要先进入“试用模式”。回答、工具调用、子任务和生成文件，都沿用已有的会话展示方式。

如果这次输入值得以后反复验证，我就点击“保存为测评用例”。系统把这次输入和输出参考直接保存下来，不再让我走一遍确认验收标准的流程。除此之外，我也可以在测评页面手动添加场景，或者让 AI 帮我准备场景，添加后直接生效。

这里有一个重要区别：保存一次输出，不代表这次输出天然正确。比如“销售额 100 元、退款 10 元，净销售额应该是 90 元”，这就是可以验证的业务预期；如果原回答算错了，就应该修正用例里的预期，而不是让 AI 学着继续算错。缺少数据时不能编造结论，也可以作为一个验证场景。

*演示提示：进入“我的技能 → 测评”，展示表格、“运行全部”和某条用例详情。*

有了场景之后，点击“运行全部”，系统会固定启动时的技能、用例和输入资料，先检查文件和资源，再在后台逐条运行。期间我修改技能，也不会影响这次执行。页面不会跳走，我只需要看这张表里的进度和结果。

判断是否通过，也不是要求 AI 每次输出完全一样的文字。可以明确计算或检查的内容，就按规则检查；需要理解业务含义的内容，由独立的 AI 评审结合预期和实际证据判断。结果可以是文字，也可以包含工具调用、子任务或者文件。

如果某个场景没有通过，我可以点“查看详情”，看到预期、完整实际输出，以及判定依据。遇到运行异常或者证据不足，系统会单独说明，不能把这些情况算成通过。

*演示提示：点击“自动优化”，展示最大迭代次数；启动后打开输出对比和 Skill 文件差异。*

如果希望 AI 接着改，我就点击“自动优化”，设置最多尝试几次。默认是 3 次，也可以在 1 到 10 次之间调整。

系统先完整测一遍。如果已经全部通过，就结束，不修改技能。存在未通过的场景时，AI 才会根据实际输出和预期的差距修改技能，再重新跑全部场景；只要还没有达到上限，就可以继续下一次优化。每次“尝试优化，再完整复测”计一次，最开始的前测不计入次数。

在详情里，我可以左右对比最初的输出和最新一轮输出，也可以查看技能文件到底改了什么。没有并发编辑时，修改会直接保存，无需逐轮确认采用；如果我期间改了工作区，调优会继续在独立副本完成，保留结果和差异，不覆盖我的新内容。

但自动化不意味着无限运行，也不意味着一定越改越好。达到上限仍未通过，系统会明确告诉我；异常或手动停止也会结束。已经保存的修改会保留，不会自动回滚，更不会自动发布。通过测评只说明这批场景满足了预期，不代表所有业务情况都没有问题。

所以，从运营视角看，日常操作就变成了：把业务需求说清楚，积累有代表性的场景，让 AI 去跑、去比较、去改；遇到业务口径不明确时，再补充必要的信息。

### 7.3 管理员视角：让公共规范可以被复用

*演示提示：先以运营身份打开“片段管理”，展示可查看但不可维护；再切换系统管理员，展示新增片段表单。*

再来看管理员。第一阶段，管理员最主要的产品操作是维护公共片段，而不是替每个运营逐个创建技能、确认用例或者审核每一轮优化。

可以把片段理解为一段可重复使用的业务要求。比如：“销售分析要扣除退款”“没有数据时不能编造结论”“报告需要说明数据来源和不确定性”。管理员把这些共性的要求整理成清楚的文字，放进片段库。

片段库面向整个平台共享。普通运营可以看到，也可以在编辑技能时通过“快捷插入”使用，但不能修改公共定义。管理员则可以新增、编辑和删除片段。

在生成技能时，AI 也会参考片段库，判断哪些要求适合当前任务。它不是把所有片段全部塞进技能，也不是要求运营每次先手动挑选。这样，运营只用描述业务需求，公共规范就有机会在生成过程中被复用。

这里有两个边界需要特别说明。第一，公共片段不能包含某个客户的私密数据、生产凭据或者仅适用于一个租户的秘密配置。第二，片段插入后就是技能里的普通正文，不是一直连接片段库的引用。以后修改片段，不会自动改掉之前已经生成的技能。

另外，文字规范不能代替真正的安全控制。比如片段里写了 SQL 检查要求，并不代表系统自动开启了 SQL Check。测试环境、工具权限和运行额度需要在技术侧保障，不让运营自己配置，也不因为管理员能维护片段，就默认允许他查看所有人的私有测评记录。

因此，从管理员视角看，重点是把通用规则准备好，明确共享和使用边界，让这些要求帮助更多运营，而不是增加一层层人工审批。

### 7.4 收尾：两种视角如何配合

把两种视角放在一起，这套方案的分工就很清楚了：运营提供业务目标和有代表性的验证场景，管理员维护可复用的公共规范，AI 承担生成、执行、对比和有限次数的优化。

第一阶段先把这条链路做通，让大家在熟悉的会话和“我的技能”里就能完成主要操作。模板、贡献以及负责人专属的版本管理和发布管理，会作为后续能力继续演进；取消技能管理员角色，负责人负责单个技能的治理，系统管理员负责公共库维护，两者权限分开。

我们希望最终减少的，不是运营对业务结果的判断，而是为了得到一个可靠技能所付出的反复操作成本。让人把精力放在需求和业务标准上，让 AI 尽可能完成验证和改进，这就是这次设计的核心。

### 7.5 现场演示顺序速记

1. 运营：会话“技能创建” → 描述需求 → 自动保存 → 继续调整。
2. 运营：直接调用 → 保存为测评用例 → 手工或 AI 补充场景。
3. 运营：测评表格 → 运行全部 → 查看预期与完整实际输出。
4. 运营：自动优化设置 → 迭代进度 → 初始/最新输出对比 → 文件修改对比。
5. 管理员：普通用户只读片段库 → 切换管理员维护 → 说明共享、正文复制与权限边界。
6. 收尾：重申首期范围和模拟原型性质，不现场展开后续模板、贡献及发布流程。
