# 技能自动评测与优化：运营优先方案

日期：2026-09-10  
状态：产品与技术设计，附离线交互原型；不是已实现的 AI 服务。

## 1. 目标与不变的边界

运营给出业务目标，AI 尽可能自动完成验证准备、试用、问题定位、正文修正与复测。运营可以直接编辑 Markdown；不要求学习 JSON、工具轨迹或评分协议。

保留已确认约束：Skill 无版本和历史版本入口；仅改造 CCUI，不改远端市场后端；其他发布渠道仍可使用；更新时间按远端时间与导入记录比较；片段固定正文、全平台共享且仅管理员维护；发布必须通过静态和动态检查，最终由当前负责人确认。**本地编辑者（含非负责人）可以测评、优化并采用自己的副本；正式验收和发布仍仅负责人可执行。**

本方案调整的是主流程，不撤销既有测评和贡献能力。细节以本方案为新增补充，静态检测和多形式输出的验收协议仍按完整需求及独立 AI 评审设计执行。

## 2. 从人工调度测评改为 Agent 自迭代

1. 描述业务目标或修改 Markdown。提供真实业务口径及脱敏示例；AI 不能自行决定“金额是否扣退款”等歧义。
2. 仅在缺少可信验收依据或业务标准变化时确认标准。已有固定标准直接复用；重新启动、普通正文改动或每轮复测不要求逐条再确认，只重新绑定当前内容运行。AI 新生成的探索场景可以自动执行，不必逐条由人批准。出现业务歧义时集中询问，而不是每发现一个失败就停止。
3. 查看最终改动并采用，再确认发布。采用写入本地正文，不等于发布；没有完整通过报告时不允许发布。

人工主要介入“业务目标/不可违反的要求”和“最终改动/发布”两端。用例编写、执行调度、证据读取、问题诊断、修正及回归交给 Agent。试用和手工维护仍可使用。取消只停止任务，不回滚已确认场景，也不覆盖技能文件。

本次明确调整旧规则：**未确认 AI 新场景可以参与内部探索，但不能自动升级为固定标准或发布证据。** 已生效用例的修改草稿仍不替换原标准；曾发布用例永久不可删除。无可信业务标准时允许先探索，不能给出“可发布”结论。

## 3. 界面与信息分层

### 我的技能

保留文件编辑、单次调试、测评、管理四个页签，不另开技术工作台。

测评统一为一张表格，不再设置二级页签。页面标题为“自动改进”，上方只保留一句整体结论、固定必跑场景通过数、当前轮次与主操作；主操作随任务状态切换为“开始自动改进 / 停止检查 / 查看并采用结果 / 预览并确认发布”。启动弹框沿用业务目标，固定标准折叠展示，不要求重复确认；演示场景和预算折叠。

| 验证场景 | 期望表现 | 检查结果 | 问题与优化 | 操作 |
| --- | --- | --- | --- | --- |
| 基础检查 | 文件结构与资源符合要求 | 通过 / 失败 / 检查中 | 问题数量及简短说明 | 查看详情 |
| 每个已确认的业务场景 | 负责人确认的预期说明 | 通过 / 失败 / 无法确定 / 异常等 | 未满足的要求，或修正后的复测结论 | 查看详情；管理 |
| AI 探索场景 | AI 待验证的假设 | 待探索 / 通过 / 失败 | 自动寻找问题，不计发布验收 | 查看详情；缺标准时补充为验收草稿 |
| 独立验收 | 最终候选符合固定标准且没有观察到退化 | 待验收 / 通过 / 失败 | 完整回归、新样本、重复运行 | 查看详情 |
| 每个待确认草稿 | AI 或手工起草的预期 | 待确认 | 新 AI 草稿可参与探索，修改草稿不替换原标准 | 核对并确认；管理 |

表格上方操作平级展示，不再收纳到“更多操作”；“运行全部”只检查、不优化，“添加验证场景”展开下拉选项“AI准备场景”和“添加场景”，优化记录等操作直接展示。行内“管理”收纳编辑、删除；曾发布场景始终不可删除。草稿不计入必跑分母。非负责人可运行本地检查/优化，负责人共享的固定标准只读，自己的用例可维护；自己的结果显示“本地结果 · 不用于发布”，采用后可提交贡献。

“查看详情”弹窗先展示用户输入、预期和实际结果；规则检查与 AI 双评审、工具/subagent 记录、输出文件及完整证据折叠展开。基础检查行展开问题、文件定位和建议；优化记录按轮次查看。主表不堆放源码、rubric 和完整执行轨迹，也不用加权总分代表安全性。

正在检查、候选已修改待复测、内容或用例已变化时，不把上一轮通过标为当前通过。探索结果不混入正式通过数；独立验收失败，即使固定场景全通过也不能采用。停止、达到上限和异常显示原因，不提供绕过入口。窄屏保持表格内横向滚动，不撑宽整页。

市场测评使用同一表格布局，但只读取已发布报告的脱敏投影，无运行、草稿确认及管理入口。期望列仅说明标准由负责人确认，不公开私有预期正文；无匹配报告显示“未测评”，绝不回退展示本地报告。

进行中示例：  
“第 2 轮：正在重新验证。已补充退款扣减说明。”

需要介入示例：  
“材料不足时应该停止提问，还是允许给出明确标注的假设？请补充到技能要求或验证场景后重新检查。”

完成示例：  
“7 个必跑场景均符合预期。修复了 1 个问题。查看并采用结果。”

“完成”只表示对已确认场景验证完成，不宣称技能在所有任务中正确。存在观察项警告时仍应展示。市场只公开最终成功发布所对应报告的允许公开字段，不公开失败迭代、私人数据、评分标准或原始证据。

### 模板

管理员继续配置名称、说明、生成要求、自定义字段和预置常用要求。面向运营时只展示用途、技能名称及必需业务问题。

文件标识自动生成；技能说明沿用模板默认；选填项、模板预设正文放进“更多设置”。尽量控制在 2–3 个真正需要回答的问题，但不能隐藏必填项或跳过管理员声明的验证约束。

运营点击“生成技能”，只看到正在生成、完成、失败；skill-creator 和临时环境细节折叠。确认保存后可以编辑 Markdown，或直接进入检查并优化。生成成功不自动运行、不激活未经确认的验证标准，也不直接发布。

### 单次调试和片段

调试突出“试用一下”：输入任务、最终答复与文件，执行过程折叠。仍然一次任务结束、不持久化。编辑器入口改为“快捷插入”，弹框按“片段 / 其他 Skill / MCP 工具”三个 Tab 选择，搜索框不显示上方标题。片段保留预览并复制固定正文；Skill/MCP 无右侧预览，仅插入名称，不复制 Skill 文件、不安装依赖或授予权限；所有内容仍是可编辑的普通 Markdown，完整规则见主方案 §7.4。

## 4. 自动优化任务的阶段

| 阶段 | 系统动作 | 用户介入 |
| --- | --- | --- |
| 准备计划 | 分析目标、固定标准、现有报告；自动补充探索场景 | 仅缺少业务依据或业务歧义 |
| 固定输入 | 固定文件、场景、参考材料、评审配置与权限；创建隔离候选 | 无 |
| 检查候选 | 静态检查；通过后实际运行全部必跑场景；封存文字/文件/工具/子任务证据 | 无 |
| 判定与定位 | 确定性规则和独立 AI 评审分开运行，识别失败原因及可修复性 | 无 |
| 修正副本 | 优化 AI 只修改允许的技能内容，不改变评分依据 | 无 |
| 全量复测 | 新候选重新执行静态和全部必跑场景，检查回归 | 无 |
| 独立验收 | 冻结最终候选，以未用于优化的新样本及重复执行验证；完整回归 | 无，不能以探索通过代替 |
| 待采用 | 保存最后通过的候选、适用报告与差异 | 负责人核对后采用 |
| 待发布 | 再次核对权限、文件和远端状态，预览正式发布 | 负责人最终确认 |

可选 subagent 属于被测执行树，不是评分器。必须等主任务、子任务及写入全部结束，才可固定执行证据供独立评审读取。

优化 AI 接收失败说明、可公开给它的证据摘录、业务要求及候选文件，不直接获取隐藏验收数据、评分服务凭据或完整生产环境。提示词中的“请忽略规则”等被测输出始终当作数据。

## 5. 验证计划与防止迎合测试

- 测试按用途分为探索、固定验收和最终独立验收。新 AI 草稿可自动探索，未经可信业务依据确认不能产生发布资格。已有生效用例完整沿用，曾发布用例永久不可删除，其必需标准不能被 AI 删除或降级。
- 确认的计划不仅有名称，还必须含输入、测试材料/替身、规则与业务预期；AI 语义标准须说明满足、不满足、无法确定条件。缺材料时标记待补充，不能用期望答案冒充实际执行结果。
- 固定验收计划、参考数据规则、工具许可、评分器配置在任务内固定。它们变化就结束旧任务，不能在同一轮放宽阈值。探索服务可在这些边界内自动追加输入实例，但不改变标准。原型较保守：启动时固定探索副本，用户修改草稿也会令原任务失效。
- 优化 AI、执行器、评分器是不同职责与上下文；评分器只读，不能运行候选代码或修改评分标准。双评审意见不一致、无法确定和服务错误均不能当作通过。
- 所有轮次重复执行完整必跑集合，不能只重跑刚修复的用例。采用前必须有针对最终候选的完整通过结果。
- 自动改进正式落地必须具备独立验收：新样本在候选冻结后由验收服务选择，其输入、参考答案不提供给优化器。失败样本一旦用于诊断就视为已暴露，下一次最终验收必须更换样本。原型只模拟此阶段与失败拦截，不具备真实隐藏集或泛化验证能力。
- 没有足够已确认材料时允许内部探索，但最终停止在“需要补充”；减少干预不等于凭空补齐业务事实。

## 6. 自动修正范围

首期自动修正限于候选目录中的 Markdown 正文和文档引用。不自动改技能标识、负责人、协助人、分类、测试输入、参考答案、已确认场景、工具权限、容器配置、凭据或发布目标。

新增/修改可执行脚本、启用真实写入工具、增加外部依赖属于扩展权限，首期不能自动执行。报告中说明需要负责人或研发处理。

每次补丁需要路径规范化、目录边界、符号链接、体积和内容校验。技能输出、工具结果及生成文件不能被当成新的系统指令。优化器没有真实工作区写权限，只有隔离候选权限。

## 7. 停止条件与预算

- 固定条件和探索检查通过后进入独立验收；独立验收通过才停止于待采用，不继续“打磨到预算耗尽”。
- 达到轮次、耗时、工具调用或费用上限：停止，不给出成功结论。建议默认最多 3 轮，实际费用/耗时上限由平台策略配置，不硬编码模型价格。
- 连续两轮没有改善或出现回归：停止并说明待解决的问题。可修复问题数量和失败集合用于决策，不用总分抵消安全失败。
- 无法判断业务意图：等待补充；补充后生成新的固定计划再运行。
- 服务/模型/环境异常：与业务失败分开。重试有上限且计入预算，不允许无限重试。
- 用户取消：发出取消信号、阻止新工具调用、终止相关执行树、回收临时环境；取消与完成竞争时以服务端任务状态为准。
- 权限撤销、文件变更、远端变化、场景变化：旧结果失效，不能采用或发布。

各租户任务并发、单用户并发和全局预算单独限制。调度器每步启动前预留预算并检查取消状态，结束后记录真实消耗。后台重启后不盲目重复昂贵调用。

## 8. CCUI 内的技术落地

复用现有 workspace-skills 的文件读取、摘要和路径保护；复用技能编辑器与 Markdown 查看组件；复用已有市场服务完成导入/发布/回读。但不能直接复用普通聊天容器的实际工作区挂载、生产凭据或持久 HOME。

新增能力均属于 CCUI：

- Optimization Coordinator：持久任务状态机、权限/租户边界、预算、排队、取消和恢复。
- Plan Builder：复用固定业务标准，生成可自动运行的探索材料；不得自行激活正式标准。
- Acceptance Service：管理新样本及可信判定依据、重复执行策略、独立验收；不向优化器泄露未使用的验收样本。
- Candidate Store：不可变候选与补丁，按任务/轮次隔离，不是 Skill 版本功能。
- Evaluation Runner：独立测试环境；复用计划中的静态规则、实际动态执行和独立评分。
- Optimization Worker：根据问题生成受限补丁；不能写原始工作区或评分数据。
- Adoption/Publish Guard：按内容摘要、计划摘要、权限与远端事实校验适用性。

建议持久记录为 optimization_jobs / optimization_rounds / optimization_candidates，关联既有 eval_runs、suite 与审计。字段至少包含 tenantId、workspaceId、skillId、initiatedBy、ownerAtStart、authorityEpoch、baseContentDigest、suiteDigest、fixtureDigest、judgeProfileDigest、remoteUpdatedAt、remoteContentDigest、status、stopReason、预算预留/实际消耗、取消标记、执行租约和幂等键。

拟新增 API（均不是当前已有接口）：

- POST /api/skill-optimizations/plans：生成内部探索计划，不执行、不激活标准；可由协调器内部调用。
- POST /api/skill-optimizations：负责人提交业务目标、已有标准标识和预算，返回异步任务；无需逐轮确认计划。
- GET /api/skill-optimizations/:id：授权后的摘要与进度；私人证据另设受控读取。
- POST /api/skill-optimizations/:id/cancel：幂等取消。
- POST /api/skill-optimizations/:id/adopt：核对后采用候选，不发布。

任务通过数据库事务/条件更新和租约推进，不能只依赖前端计时器。执行失败有可恢复状态；读进度不触发执行。重复采用不能重复写文件。证据留存期限、敏感数据清理、审计和额度策略遵守租户配置。

## 9. 内容并发与最终发布

开始前检测未保存编辑、市场待更新、缺失的受保护发布场景和正在发布的任务。存在冲突时先处理，不自动覆盖。待确认草稿本身不阻止探索；修改草稿仍沿用原固定定义，新 AI 草稿仅进入探索集合。

运行时只写候选。用户继续编辑不会被阻止，但旧任务在检查点被标记失效；采用时再次核对基础摘要，保证最后一刻也不能覆盖新编辑。正式采用应以 workspace-skills 既有内容并发保护作为底层条件写入。

检查完成后先采用到本地，关联最终候选的完整通过报告。采用保留 importedRemoteUpdatedAt，不伪造市场同步时间。新检查失败或未采用时，不允许从旧报告中挑一个通过结果直接发布；可重新完整检查当前正文恢复资格。

发布仍需要当前负责人确认，按照既有远端并发限制处理。外部渠道仍可发布，CCUI 不能保证远端原子 CAS；因此发布前再读取，发布后回读并核对实际内容。不一致进入待核实，不自动覆盖重试；远端更新没有适用报告时显示“未测评”。

下架不删除任务审计/报告；这些记录不是历史 Skill 版本，也不提供恢复旧版本入口。

## 10. 原型范围与落地顺序

原型覆盖固定标准复用、AI 草稿内部探索、两轮修正、独立验收、停止/次数上限/无改善/缺标准/业务歧义/服务异常、新样本失败/重复运行不稳定、候选对比、采用与最终发布，以及冲突失效保护。模板表单已简化，Markdown 仍可编辑。

所有执行结果、修改文字与消耗数字均为预设模拟。初始示例的“通过”及第一次失败不代表当前 Markdown 真实有错或已修复。原型不实现持久任务、真实成本、容器、隐藏验收集、语义定位、任意补丁或实际资源回收。

推荐落地顺序：

1. 先完成可靠的静态/动态测评及固定报告契约，验证现有 CCUI 的隔离执行能力。
2. 接入固定业务标准、AI 自主探索与集中澄清，并完成运营文案和证据摘要。
3. 上线仅 Markdown 的受限优化循环，带预算、全量回归、独立验收、任务持久化和取消。
4. 接入采用并发保护与现有发布检查，小范围运营试点。
5. 收集一次成功率、人工介入原因、回归率、平均轮次/成本及误判，再决定是否扩大修正范围。

不得用离线原型验收代替真实服务、安全隔离或权限验证。

## 11. 三类测试数据与可信预期

### 11.1 探索集合：负责发现问题

由 Plan Builder 根据 Skill、业务目标、允许使用的参考资料和已有失败类型生成。覆盖正常请求、缺失信息、边界输入、交付文件、工具不可用和可选子任务失败。平台先做格式、资源可用性、隐私和预算检查，再自动运行；不需要负责人逐条确认。

每条保存 scope=exploration、来源、input、fixtures、hypothesis、证据要求、首次发现轮次。hypothesis 明确是待验证假设，不称为标准答案。AI 可以增加、去重或归档探索场景，但不能借此删除固定验收条件。手工草稿和已有正式用例的修改草稿默认不自动加入探索；原型只自动使用新增 AI 草稿或内置模拟探索样本。

探索失败先区分 Skill 错误、假设错误、材料缺失、环境异常。只有业务依据支持的 Skill 错误才交给优化器修改。原型用预设结果表示这个分支，不实现真正的根因识别。

### 11.2 固定验收集合：负责守住业务底线

来源优先级：负责人批准的业务规则/脱敏真实案例、可验证的计算或测试工具、管理员批准且负责人确认适用的模板标准，最后才是待确认的 AI 建议。运营不必写测试代码：输入“退款要扣减，不混算不同币种，交付分析报告”，提供样例，AI 转为规则，负责人首次集中确认业务含义。

首次没有标准时可先探索。探索后集中给出缺口，例如“退款按支付日还是退款日归属？”，负责人回答后生成或修正正式用例草稿。正式激活仍按已有逐条确认机制，不因点击“开始自动改进”批量确认。后续内容优化沿用已经确认的标准，不重复打扰。

每条业务预期需要 provenance：依据类型、引用材料、确认者/时间及适用范围。纯 AI 推断且无法核实的业务事实不能作为正式必跑判定。固定标准在整个任务中不可变，变更必须由负责人确认，旧任务/报告失效。

### 11.3 独立验收集合：负责检查是否只记住了例子

由验收服务在最终候选冻结后选择，与优化器分离。新样本必须来自已批准的数据生成约束或保留的真实案例；其正确性沿用同一业务规则，不允许另一个 AI 临时发明新的业务口径。没有可信生成器或保留样本时标记“缺少独立验收材料”，不伪造泛化结论。

例如批准的规则是同币种“净额=销售−退款”。优化样本为 100−10=90；验收服务可生成 240−35=205、80−80=0，并由确定性计算器得到答案。允许自动换数字，不允许擅自改变跨月退款口径。开放式报告使用新的脱敏材料，仍按固定标准检查事实支持与不确定性表述，而不是与唯一参考文案做相似度比较。

新样本属于测试输入实例，不是 AI 新增业务标准。正式存储沿用父 caseId，instanceId 区分执行样本，不生成 Skill 版本。发布后保护固定 caseId；不把每个随机样本都变成运营必须维护的永久用例。验收样本及证据按测评留存策略保留，不能在审计期内因探索清理而误删。

## 12. 如何判断一次任务符合预期

先执行后评分。被测 Agent 只接收任务输入、许可材料和工具，不接收参考答案、隐藏样本或评分器指令。任务树结束、文件写入终止后固定 evidenceBundle，评分器只读。

| 对象 | 优先采用的判定 | AI 适合补充的判断 |
| --- | --- | --- |
| 数字/计算 | 根据测试数据确定性重算；币种、单位、精度、容差按固定规则 | 解释是否与数值一致 |
| 文本 | 必填事实、禁止泄露、引用来源可解析 | 是否完成用户意图、结论是否有依据、缺失信息处理是否合理 |
| 文件 | 路径、可读取、真实类型、结构、公式/数据核对 | 报告逻辑、图表解释、交付完整性 |
| 工具调用 | 授权范围、入参、结果、错误处理、禁止副作用 | 是否合理使用工具、失败后是否如实说明 |
| subagent | 主子任务关联、终态、证据完整、结果确实被汇总 | 分工结果是否被正确综合 |

工具调用和 subagent 本身不是加分项；未要求某工具且结果正确时，不因没有调用它而判错。特定工具确为业务/审计要求时才配置必需调用。不同但等价的合法执行路径应被接受。

确定性检查优先；AI 评分仅覆盖不能机械判定的语义项，按固定 rubric 输出 met/not_met/uncertain/error、理由及证据引用。两次 AI 评审必须都满足，才令该必需语义项通过；这只是保守一致性规则，不等于两次独立实测或真实正确性的证明。

评分器上线前，负责人/领域专家标注少量有代表性的历史输出，包含正确、事实错误、夸大结论、缺资料等；测量误放行与误阻断。校准未达业务风险要求时不能将其作为唯一硬门禁，改用可信规则或完善依据。具体标注规模和可接受误判率由业务风险确定，本方案不虚构已验证阈值。评分配置修改后必须重新校准并重新评估候选。

## 13. 从失败证据到可执行修改

协调器先分类，再决定是否启动优化器：

| 分类 | 自动动作 | 是否询问人 |
| --- | --- | --- |
| 文件结构、引用或明确指令遗漏 | 生成受限 Markdown 补丁，重新静态检查与回归 | 否 |
| 可信业务断言失败 | 给优化器失败证据与对应业务规则，修正通用做法 | 否 |
| 无依据的探索假设 | 标记待核实，不把假设强写进 Skill | 仅影响目标正确性时 |
| 评审不一致/证据不足 | 有预算时重新提取证据或按策略复核；不得把不确定改成通过 | 无法安全解决时集中询问 |
| 环境/工具故障 | 有上限地重试或使用已批准的替身，记录异常 | 缺测试资源或授权时 |
| 新权限/脚本/生产写入需求 | 拒绝自动扩大权限，生成建议 | 是 |

给优化器的反馈示例（内部协议，不让运营填写）：

```json
{
  "caseId": "TC-net-sales",
  "kind": "business_assertion_failed",
  "inputSummary": "同币种销售 100 元，退款 10 元",
  "expected": "净销售额为 90 元",
  "actual": "最终答复与报告均为 100 元",
  "evidenceRefs": ["E-FINAL", "E-FILE:table.row1"],
  "businessRuleRef": "approved/net-sales",
  "diagnosis": "Skill 只说明汇总销售，没有要求扣减退款",
  "allowedPaths": ["SKILL.md", "references/requirements.md"],
  "suggestedChange": "补充通用退款计算和交付前交叉核对要求",
  "forbiddenChanges": ["固定预期", "用例身份", "权限", "发布目标"]
}
```

补丁不能硬编码“本次答案是 90”。需要表达可泛化步骤，比如读取销售/退款、核对同币种、计算差额、把计算结果同时写入回复与报告。补丁后先做路径和安全检查，再重跑所有固定必跑场景与探索集合。旧轮次的通过结果不能与新轮次拼接成完整通过。

## 14. 独立验收与完成条件

候选在优化阶段通过后立即冻结。以下条件是逻辑与，不采用总分加权抵消：

1. 静态检测无阻断项，证据与执行树完整，无越权或生产副作用。
2. 最终候选完整重跑固定必跑集合并通过；原失败点已修正。
3. 新样本验收通过；判定依据来自固定业务规则而不是优化器自行修改的答案。
4. 关键场景真实独立重复运行，未观察到退化；平台建议首期关键场景至少 3 次，具体次数按风险及预算配置，所有必需项每次均通过。双评分不计作重复运行。
5. 在固定输入/环境/模型下与原始候选比较，无已通过条件退化。若基线与最终均通过且没有可证明改进，保留原内容，不做“为了优化而优化”的补丁。可选无 Skill 对照用于判断增益，不作为所有业务的首期强制条件。
6. 文件、业务标准、参考数据、工具策略、模型与评分配置、权限和远端事实摘要均匹配；未达到以上条件不得采用为合格结果。

以上是有限样本、指定环境中的证据，不承诺普遍正确或统计意义上的稳定率。报告应记录重复次数/通过次数、样本覆盖、未测范围和警告，避免只显示“100 分”。

独立验收失败后，本任务保守停止，不在同一批隐藏样本上反复修补刷分。后续任务可利用已暴露失败类型改进，但必须轮换新的最终验收样本，并沿用同一任务族的累计预算，防止重新启动绕过成本上限。一般失败在循环内自动处理，不要求人逐次决定。

生产建议最多 3 轮优化，另预留独立验收预算；费用、耗时、总调用数同时限制。原型最多 6 个模拟额度：两轮检查及一次修正用 3 个，最终回归/重复/新样本用 3 个。原型仅模拟一次额外重复，不代表已经实现生产建议的 3 次关键场景执行。

本轮只更新设计和 HTML，不改业务后端。现有代码核对结果：

| 现有位置 | 可复用部分 | 本方案仍需新增 |
| --- | --- | --- |

| server/services/top-skill-jobs.js | 已有 generate/optimize 异步入口、tenant/user/workspace 归属检查 | 不能直接当作自迭代引擎：当前为进程内 Map、queued/running/succeeded/failed，缺少本方案持久轮次、独立验收和预算状态机 |

在既有认证/租户上下文中新增 jobs、rounds、candidates、test_instances、evidence_bundles、acceptance_runs 等持久记录。用例标准和探索假设分表或强类型 scope 隔离；服务端汇总时只允许 approved acceptance 条件产生发布资格，不能信任前端 transmitted passed 标志。

运行上下文至少固定 contentDigest、contractDigest、suiteDigest、fixtureDigest、runnerImageDigest、modelConfigDigest、toolPolicyDigest、judgeProfileDigest、owner/authorityEpoch、remoteUpdatedAt 和 remoteContentDigest。执行器结束后保存产物摘要及完整性状态；优化器只能读取可见探索/回归反馈，不能访问未暴露验收集合。

原有 POST /api/skill-optimizations/:id/adopt 可保留。正式实现可让“确认改动并发布”在一次界面中呈现两项结果：先条件采用到本地，再走远端发布。两者不是原子事务，发布失败必须说明“本地已采用、市场未更新”，不能假装全部回滚或自动重复发布。原型继续分为采用与发布两个明确按钮。

## 16. 验收指标与上线次序

先选择少量真实运营 Skill 试点，对每项记录原始内容与固定测评基线，人工只标注校准集和必要业务口径。离线验证隔离/权限、评分可靠性之后，才允许 Agent 自迭代。

衡量“有效”至少看：目标任务实际成功率变化、回归率、误放行率、独立新样本通过情况、人工介入次数及原因、平均轮次/耗时/成本。不要把探索用例数量、评分次数或 UI 测试通过数当作 Skill 能力指标。记录“无改进，保留原内容”也属于有效结果，不强制每次都有补丁。

当前可演示：正常两轮优化后独立验收、第一次即通过、缺标准先探索再提示补充、草稿不阻塞探索且不自动激活、新样本失败、重复运行不稳定、预算不足、取消与并发失效。尚未实现：真正 AI 自主生成样本、真实隔离执行/补丁、可信参考答案计算、判分校准、保密样本、重复运行统计、无 Skill 对照、持久任务及真实发布门禁。

上线前需配置而非由原型假定的事项：允许使用的测试数据、模型与评分配置、关键场景列表、费用/时限/并发配额、工具白名单、证据留存及清理策略。默认不新增生产权限；未配置关键资源时显示待补充，不降级放行。

## 17. 本地测评与正式验收的权限分离（本次确认）

### 17.1 权限矩阵

“我的技能”表示当前工作区内可用的技能，不等于“我负责发布的技能”。本地编辑权限与市场负责人身份分别判断；管理员身份也不自动获得 Skill 发布权。

| 操作 | 有本地编辑权限的非负责人 | 当前负责人 |
| --- | --- | --- |
| 本地测评、AI 探索与自动优化 | 可以，受测试资源授权与预算约束 | 可以 |
| 查看自己的原始证据、取消自己的任务 | 可以 | 可以 |
| 采用 AI 修改 | 仅写入自己明确选择的本地副本 | 写入负责人的本地工作副本 |
| 新增/修改/确认固定发布标准 | 不可以；可随贡献说明提出建议 | 可以，沿用发布用例永久保护 |
| 新增/编辑/确认/删除自己的本地用例 | 可以，仅影响个人测评；共享验收用例只读 | 可以维护自己的用例，正式发布仍需完整验收 |
| 负责人私人样本、未公开证据 | 不因本地编辑权限而自动开放 | 仍按数据授权读取 |
| 提交贡献 | 可以，提交当前个人副本 | 保留既有直接发布流程 |
| 对贡献进行正式验收、合并并发布 | 不可以 | 可以，必须亲自发起正式测评 |
| 转移负责人、配置协助人、分类管理 | 不可以 | 可以 |

没有本地编辑权限的工作区成员不能因能看到技能就发起任务；开始、每轮执行和采用均复核成员关系、工作区权限、候选基础摘要与负责人变更。

### 17.2 结果隔离与贡献流程

本地记录包含 scope=local、tenantId、workspaceId、skillId、initiatedBy、localCopyId、contentDigest、可用测试集合摘要等。只有本人在对应工作区读取原始证据；scope 由服务端确定，客户端不能提交 release 来升级。负责人正式运行得到独立的 scope=release 记录。

本地成功不替换正式报告，不更改市场测评，不修改负责人、协助人、分类或发布保护集合。原始正式报告也不能作为另一用户当前副本的运行结果显示。即使用户后来成为负责人，旧 local 报告仍是 local，必须重新正式测评。

推荐路径：导入/编辑个人副本 → 本地测评与自动优化 → 查看差异并采用 → 提交贡献 → 负责人对固定提交重新正式测评 → 确认合并发布。提交时只固定贡献文件，负责人正式报告初始为空；贡献者的本地摘要若附带，只作参考，不作为通过证明。贡献评审规则和负责人最终决策不变。

### 17.3 测试材料不随权限放开

本地运行只可使用明确授权的共享测试定义、脱敏材料、测试工具及个人探索输入。负责人私人验收样本和隐藏集不提供给其他本地用户。缺失必要材料时显示“未覆盖/需要授权”，不是把跳过项算通过，也不因此授予额外 MCP 或生产权限。没有可用固定用例时仍可先 AI 探索；正式标准需要负责人补充，其他人不能自行修改预期来完成发布验收。

本地复核可以使用同样的静态/动态检查和重复运行方法，但其语义是“我的副本在可用材料下的结果”，不是负责人正式独立验收。界面将最后一行标为“本地复核”，正式流程仍标“独立验收”。

本地用户可以手工新增用例或让 AI 起草，填写名称、输入、预期、必跑属性及可选 AI 判定标准。保存为个人草稿，由本人确认后生效；可编辑或删除自己的本地用例，确认修改/删除后个人旧报告失效。不能通过本地接口修改、删除或替换负责人共享用例，曾发布用例的永久保护不变。

本地表格同时展示“负责人共享 · 只读”和“我的本地用例”，两类已生效用例一起参与本地评测；个人草稿单独展示，仍不计入通过分母。caseId 使用个人范围的独立身份，不与共享 caseId 混用。个人用例属于 tenant/workspace/skill/user/localCopy 范围，切换用户不共享私人用例或草稿。提交贡献不自动激活个人用例为正式标准；若建议负责人采用，需另行核对业务依据、创建正式定义并重新正式测评，不能沿用本地通过结论。

### 17.4 当前原型与真实工作区

原型用 tenant/workspace/skill/user 组合键隔离非负责人的文件、导入对照时间、本地报告及待采用任务。保存、同步、采用和贡献读取本人副本；负责人工作文件与报告不被覆盖。切换演示身份不会改写运行发起人，也不会显示或采用别人的任务。示例成员默认都具有工作区编辑权限；模型支持撤销 editorIds 权限的测试。示例固定用例均为可共享的虚构材料；标记 localVisible=false 的用例和负责人草稿不加入其他人的测评。

这不是生产授权实现。真实 CCUI 若一个工作区目录由多人共享，单加 userId 并不能隔离实际文件：必须建立显式个人候选目录/localCopyId，或在用户确认后采用到其有权写入的独立工作区，不能直接写回共享负责人目录。市场安装可见性、工作区成员管理及删除本地安装仍沿用原型既有单工作区示意，并非完整多工作区模拟。

生产任务/API 增加 local/release 两种 scope，分别鉴权；本地运行不读写正式评审状态，采用不调用远端发布。发布门禁必须同时校验 release scope、当前负责人发起、内容与条件摘要匹配以及完整通过。原型保守使用单任务队列，正式实现可按用户/工作区/租户配额调度，不必让其他用户的个人测评占住正式发布锁。
