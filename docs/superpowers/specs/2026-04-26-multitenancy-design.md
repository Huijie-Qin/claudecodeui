# Multi-Tenancy Design

Date: 2026-04-26
Status: Approved for planning

## Goal

Add first-class application-level multi-tenancy to CloudCLI UI so one running instance can serve multiple tenants while keeping workspace and session access controlled.

The first implementation phase focuses on Web UI flows. External API key and `/api/agent` automation entry points are out of scope for the multi-tenant security promise in this phase.

## Decisions

- Use an application-managed tenant model, not one process per tenant.
- Persist tenants, users, tenant membership, workspaces, workspace ACLs, and session ownership in the database.
- Users can belong to multiple tenants.
- A tenant is the entry boundary. A user must belong to a tenant before seeing anything in it.
- A workspace is the resource boundary. Workspaces are private by default and may be shared explicitly with same-tenant users.
- Workspace sharing does not share agent session or chat history.
- New workspaces must live under an application-managed path: `WORKSPACES_ROOT/<tenantId>/<ownerUserId>/<workspaceSlug>`.
- Users can choose a tenant on first login. Later logins restore the last selected tenant if still valid; otherwise they return to tenant selection.
- First phase includes a minimal system administrator UI and supports user join requests, but complex approval workflow can follow later.

## Scope

In scope:

- Tenant, user, and tenant membership persistence.
- Workspace records and workspace ACL persistence.
- Current tenant selection in the Web UI.
- Strong path isolation for newly created workspaces.
- Owner-managed workspace sharing whitelist.
- Permission checks for project list, files, Git, shell, agent WebSocket, and session history routes.
- Private per-user session indexing.
- Minimal system administrator UI for tenant/user/membership management.
- Join request entry point for users.
- Focused backend permission tests and key frontend tenant-selection tests.

Out of scope for phase one:

- Migration or import of existing globally discovered historical workspace/session data.
- Full provider credential isolation. Claude/Codex/Cursor/Gemini auth and global provider config continue to use the current host-level setup.
- External API key and `/api/agent` multi-tenant isolation.
- Tenant administrator role.
- Workspace-level session sharing.
- Adding arbitrary existing filesystem paths as workspaces.

## Data Model

The existing `users` table can be migrated or wrapped to behave as `t_user`. The design uses table names below to make the boundaries explicit.

### `t_tenant`

Stores tenant lifecycle.

Fields:

- `id`
- `code`, unique stable tenant identifier
- `name`
- `status`, for example `active` or `disabled`
- `created_at`
- `updated_at`

### `t_user`

Stores login identity. This can extend the current `users` table.

Fields:

- `id`
- `username`
- `password_hash`
- `is_system_admin`
- `is_active`
- `created_at`
- `last_login`
- existing user preferences such as Git config and onboarding status

### `t_tenant_user`

Stores the user-to-tenant relationship.

Fields:

- `tenant_id`
- `user_id`
- `role`, initially `member`
- `permission`, initially `view` or `edit`
- `status`, for example `active`, `disabled`, or `pending`
- `created_at`
- `updated_at`

Rules:

- A user must have an active membership to enter a tenant.
- `view` allows entering the tenant and viewing resources shared to the user.
- `edit` allows creating and managing the user's own workspaces in that tenant.
- Tenant-level `edit` does not grant access to every workspace in the tenant.

### `t_workspace`

Stores application-managed workspaces.

Fields:

- `id`
- `tenant_id`
- `owner_user_id`
- `slug`
- `display_name`
- `path`
- `status`
- `created_at`
- `updated_at`

Rules:

- `(tenant_id, owner_user_id, slug)` is unique.
- `path` is generated by the backend and must be inside `WORKSPACES_ROOT/<tenantId>/<ownerUserId>/`.
- The owner always has full workspace access.

### `t_workspace_acl`

Stores explicit workspace sharing.

Fields:

- `workspace_id`
- `user_id`
- `permission`, either `view` or `edit`
- `created_by_user_id`
- `created_at`
- `updated_at`

Rules:

- Only the workspace owner can change the ACL.
- ACL users must belong to the same tenant as the workspace.
- `view` grants read-only workspace access.
- `edit` grants file editing, Git operations, shell access, and launching the user's own agent sessions.
- ACL recipients cannot re-share the workspace.

### `t_session`

Stores application-level ownership for provider sessions.

Fields:

- `id`
- `tenant_id`
- `workspace_id`
- `user_id`
- `provider`, one of `claude`, `codex`, `cursor`, `gemini`
- `provider_session_id`
- `summary`
- `status`
- `created_at`
- `updated_at`
- optional provider metadata

Rules:

- Session lookup, rename, delete, continue, and history reads must match `tenant_id`, `workspace_id`, `user_id`, `provider`, and `provider_session_id`.
- Workspace sharing does not expose another user's session rows.

### `t_tenant_join_request`

Stores user requests to join tenants.

Fields:

- `id`
- `tenant_id`
- `user_id`
- `message`
- `status`, for example `pending`, `approved`, or `rejected`
- `created_at`
- `updated_at`

The first phase can expose submission and basic admin handling. Detailed approval notifications and workflow can come later.

## Authorization Model

Every protected Web UI request is evaluated in this order:

1. Authenticate the user.
2. Resolve the current tenant from request context.
3. Verify active tenant membership.
4. Resolve resource identifiers through the database.
5. Check workspace-level permission when a workspace is involved.
6. Check session ownership when a session is involved.

Permission summary:

- Tenant membership is required before any tenant resource is visible.
- Tenant `edit` allows creating workspaces in that tenant.
- Workspace owner has full access to the workspace and its ACL.
- Workspace ACL `view` allows reading project files and metadata.
- Workspace ACL `edit` allows files, Git, shell, and launching agent sessions in that workspace.
- Sessions are private to the creating user even inside shared workspaces.

## Bootstrap And Registration

The current single-user setup flow must become a system bootstrap flow.

First deployment:

1. If no active users exist, show setup and create the first `is_system_admin` user.
2. The first system admin can create tenants, create users, and assign tenant memberships.
3. The system must not create an implicit global default tenant for all users.

Later registration:

1. Public registration can create a normal user account.
2. A newly registered user has no tenant access until a tenant membership is granted.
3. The user can submit a join request for a tenant.
4. A system admin can approve the request by creating or activating a `t_tenant_user` row.

Startup behavior:

- Startup runs migrations and ensures required tables exist.
- Tenant availability and user permissions come from the database, not environment variables or static config.
- Runtime authorization should query the database or a short-lived cache that is invalidated when admin membership changes.

## Backend Components

### Tenant Context Middleware

Reads `tenantId` from request query, header, or WebSocket URL. It validates that the authenticated user belongs to the tenant and attaches `req.tenant`.

If no tenant is provided on routes that require it, return `400`.

### Workspace Access Service

Centralizes checks:

- `canViewWorkspace(userId, tenantId, workspaceId)`
- `canEditWorkspace(userId, tenantId, workspaceId)`
- `isWorkspaceOwner(userId, workspaceId)`
- `resolveAuthorizedWorkspacePath(...)`

Routes must use this service instead of trusting frontend paths.

### Workspace Database Module

Manages:

- Workspace creation.
- Workspace listing for owner and ACL recipients.
- Workspace rename/delete status.
- Workspace ACL reads and writes.

### Session Index Module

Manages:

- Creating or updating `t_session` rows when a provider session starts or reports a provider session id.
- Mapping UI session ids to provider session ids.
- Filtering session lists and history reads by tenant, workspace, and user.

### Admin Routes

Minimal system administrator API:

- List/create/update tenants.
- List/create/update users.
- Assign users to tenants.
- Update tenant-level permissions.
- Handle basic join requests.

Only `is_system_admin` users may access these routes.

### Tenant Routes

User-facing API:

- List current user's tenants.
- Submit a join request.
- Validate a selected current tenant.

### Workspace Share Routes

Owner-facing API:

- Read workspace share configuration.
- Update workspace share whitelist.

The route must reject non-owner attempts with `403` and reject non-tenant users in the ACL payload with `422`.

## API Shape

New or changed Web UI endpoints:

- `GET /api/tenants/me`
- `GET /api/tenants/:tenantId/validate`
- `POST /api/tenants/:tenantId/join-requests`
- `GET /api/admin/tenants`
- `POST /api/admin/tenants`
- `GET /api/admin/users`
- `POST /api/admin/users`
- `PUT /api/admin/tenants/:tenantId/users/:userId`
- `GET /api/admin/join-requests`
- `PUT /api/admin/join-requests/:requestId`
- `GET /api/projects?tenantId=...`
- `POST /api/projects/create-workspace?tenantId=...`
- `GET /api/workspaces/:workspaceId/share?tenantId=...`
- `PUT /api/workspaces/:workspaceId/share?tenantId=...`
- `GET /api/sessions/:sessionId/messages?tenantId=...`
- `WS /ws?tenantId=...`
- `WS /shell?tenantId=...`

Existing project routes should gradually use `workspaceId` as the primary identifier. Compatibility with `projectName` is acceptable only when `projectName` maps to a database workspace visible to the current user.

## Frontend Flow

Login flow:

1. User logs in.
2. Frontend requests `GET /api/tenants/me`.
3. If there is a valid saved tenant, enter it.
4. If no saved tenant exists or it is invalid, show tenant selection.
5. Store the selected tenant locally and in app state.

Workspace flow:

1. Sidebar fetches projects with `tenantId`.
2. Owner and shared workspaces appear together.
3. Each workspace includes an access marker such as `owner`, `edit`, or `view`.
4. Workspace owner sees sharing controls.
5. `view` users see write/run controls disabled.
6. `edit` users can use files, Git, shell, and agent chat normally.

Admin flow:

1. System admin can open an admin section.
2. Admin can create tenants and users.
3. Admin can grant users tenant membership and tenant-level `view` or `edit`.
4. Admin can review join requests in a minimal table.

## Data Flow

Workspace listing:

1. Backend validates tenant membership.
2. Backend loads workspaces owned by the user.
3. Backend loads workspaces shared to the user through ACL.
4. Backend returns a merged list with `accessRole`.

Workspace creation:

1. Backend checks tenant `edit` permission.
2. Backend validates slug.
3. Backend creates directory under `WORKSPACES_ROOT/<tenantId>/<userId>/<slug>`.
4. Backend writes `t_workspace`.
5. Backend returns the workspace record.

Workspace sharing:

1. Owner requests current ACL.
2. Owner submits whitelist.
3. Backend validates ownership.
4. Backend validates every target user belongs to the same tenant.
5. Backend replaces or patches ACL records.

Agent session creation:

1. User starts an agent in an authorized workspace.
2. Backend validates workspace `edit`.
3. Provider runs with the authorized workspace path as cwd.
4. When a provider session id is known, backend writes `t_session`.
5. Realtime events are delivered only to the starting user's WebSocket.

Session history:

1. Backend resolves the requested session row by `tenant_id`, `user_id`, `workspace_id`, and provider id.
2. Backend delegates to the provider history reader.
3. Backend returns normalized messages.

## Error Handling

- `401`: no valid authentication.
- `400`: missing tenant context on a route that requires it.
- `403`: authenticated but not allowed to perform the action.
- `404`: resource does not exist or is completely invisible to the current user.
- `409`: unique constraint conflict such as tenant code, username, or workspace slug.
- `422`: invalid business payload, such as sharing with a user outside the tenant.

Do not reveal the existence of another tenant's or another user's resources through error wording.

## Security Rules

- Frontend-supplied absolute paths are not authorization evidence.
- File, Git, shell, and agent operations must resolve paths from `t_workspace`.
- New workspaces must be created under the generated tenant/user path.
- `projectName` compatibility must map through an authorized workspace.
- `sessionId` alone is not enough to read or mutate session data.
- WebSocket connections bind user and tenant during handshake, and each workspace/session message is still authorized.
- Workspace ACL files should not be stored inside the editable project tree in phase one. Database is the authority.
- Provider credentials remain global in phase one and must not be presented as fully tenant-isolated.

## Testing

Backend unit tests:

- User receives only active tenants from `t_tenant_user`.
- Owner sees own workspace.
- ACL user sees shared workspace.
- Same-tenant non-ACL user cannot see the workspace.
- Other-tenant user cannot see the workspace.
- Owner and `edit` ACL user can write files.
- `view` ACL user and non-ACL user cannot write files.
- Shared workspace does not expose another user's sessions.
- File/Git/Shell path resolution refuses frontend-supplied absolute path escalation.
- Only owner can update workspace ACL.
- Workspace ACL rejects users outside the tenant.

Backend integration tests:

- Create tenant, user, membership, and workspace.
- Workspace path is generated under `WORKSPACES_ROOT/<tenantId>/<userId>/<slug>`.
- Share workspace with another same-tenant user.
- Shared `edit` user can edit files, query Git status, and start an agent session.
- Shared user cannot read owner session history.
- Tenant switching changes project and session visibility.

Frontend tests:

- First login without saved tenant shows tenant selection.
- Valid saved tenant enters the app automatically.
- Invalid saved tenant returns to tenant selection.
- Sidebar labels owner/shared access.
- Workspace share controls are visible only to owner.
- `view` access disables write/run controls.
- `edit` access enables collaboration controls.

Verification commands:

- Run TypeScript checks for frontend and server.
- Run focused backend database and authorization tests.
- Run focused frontend tenant-selection and workspace-access tests.

## Migration Notes

Existing globally discovered project and session history remains outside the phase-one migration. After this change, new workspace creation uses database records and generated paths. A later migration can add an import or claim flow for existing local projects.

For compatibility, startup can still watch provider directories, but Web UI project visibility must come from database-backed workspaces. Provider watchers may refresh metadata for authorized workspaces only.
