# Skill 贡献页与角色权限补充设计

日期：2026-09-08

状态：负责人发布权限、贡献页两个子 Tab、协助人可见其协助 Skill 的全部贡献请求已确认；具体交互默认值待评审。本次仅更新设计，不实施业务代码。

## 1. 设计范围

在“贡献”主 Tab 下，提供两个子 Tab：

| 子 Tab（建议名称） | 用户视角 | 展示内容 |
| --- | --- | --- |
| 收到的贡献 | 我作为目标 Skill 的负责人或协助人 | 与我的负责或协助关系相关的贡献请求 |
| 我提交的贡献 | 我作为贡献者 | 由我提交的贡献请求及其处理进展 |

两个子 Tab 是同一份 PR 数据的不同查询视角，不分别创建两份请求，不增加独立业务流程。负责人和协助人不再拆成第三、第四个子 Tab，而是在“收到的贡献”内部标记和筛选角色。

“协助人”沿用之前讨论的 Skill 协作者（collaborator）概念；“本次评审人”表示具体 PR 上被指派评审的用户，两者在数据上不能自动等同。

本设计补充 [Skill 市场 V2.0 需求设计说明书](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/skill-market-v2.0-需求设计说明书.md) 的贡献页面与权限规则，不表示整个 PR 方案已经完成详细设计或实现。

后续完整流程以 [发布、贡献与市场更新方案（无版本）](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/superpowers/specs/2026-09-09-skill-publish-contribution-design.md) 为准；本文件继续描述两个子 Tab 的页面范围。

## 2. 已确认的角色边界

| 身份 | 可参与的操作 | 发布边界 |
| --- | --- | --- |
| Skill 负责人 | 贡献、评审、最终合并并发布 | 唯一拥有该 Skill 合并发布权限的角色 |
| Skill 协助人 | 修改贡献草稿、提交 PR、参与评审 | 不能合并或发布 |
| 贡献者 | 提交自己的变更，查看和跟进自己的请求 | 提交人身份不赋予合并发布权限 |
| 管理员 | 按已有管理权限管理平台或租户 | 管理员身份本身不赋予 Skill 合并发布权限；同时是该 Skill 负责人时才可发布 |

评审通过不等于发布。需要负责人执行最终合并发布；不再保留原 V2 中“租户管理员 override merge”的例外。

已进一步确认：负责人自身变更可直接发布，不强制提 PR；协助人的认可不是必需合并条件，但 CCUI 发起的直接发布和合并都必须通过自动测评，负责人不能跳过。

角色属于具体 Skill 或具体请求，同一个用户可以同时是某个 Skill 的负责人、另一个 Skill 的协助人，以及其他请求的贡献者。列表所在子 Tab 不是权限来源，后端仍须按当前用户与目标 Skill、请求的实际关系鉴权。

协作范围继续限定当前租户。片段库全平台共享不改变贡献请求的租户边界。

## 3. 收到的贡献

### 3.1 接收范围

- 负责人：目标 Skill 当前负责人是我，该 Skill 的贡献请求进入此视图。
- 协助人：已确认可查看自己协助的 Skill 的全部贡献请求，不限于明确指派给自己的请求。建议对其中明确指派给自己的请求另标记“待我评审”。
- 默认不扩展为租户内所有请求，也不因为系统管理员或租户管理员身份而展示全部请求。
- 同时符合多个接收条件时，每个 PR 只展示一次；角色展示优先为“负责人”，可另外标记“本次评审人”。

### 3.2 列表与筛选（建议）

列表字段：贡献标题、目标 Skill、贡献者、我的角色、请求进展、最近活动时间。

筛选项：

- 我的角色：全部、负责人、协助人。
- 请求状态：进行中、已合并、已关闭、全部。
- 评审任务：“待我评审”作为快捷筛选，不另建子 Tab。
- 关键词：贡献标题、目标 Skill 名称及贡献者。

默认显示进行中的请求，按最近活动时间倒序排列，同时间按 PR ID 稳定排序。这里的“收到”不代表未读；首期不把数量角标设计成未读消息数。

### 3.3 操作（建议）

列表统一提供“查看详情”；详情内展示完整文件差异、变更说明、评审记录及当前状态。

- 负责人可参与评审，在满足合并条件后执行“合并并发布”。
- 协助人按评审权限发表评论、表示认可或要求修改；不展示合并发布按钮，直接请求合并接口也必须被拒绝。
- 评审权限由 Skill 角色及具体指派关系决定，不能单凭出现在列表中就获得所有评审动作权限。
- 请求已合并或关闭时仍可查看历史，但不提供重复合并。

合并前仍需重新校验当前负责人身份、请求状态、当前目标的远端更新时间和适用的检查条件。没有对应结果时，不以“已经查看过”推断评审通过，也不以列表标签代替服务端校验。

## 4. 我提交的贡献

查询范围：当前租户中 `authorId` 为当前用户的已提交请求。尚未提交的草稿继续留在“我的技能”，不计为贡献请求。

列表字段：贡献标题、目标 Skill、当前负责人、本次评审人、请求进展、最近活动时间。没有指派评审人时明确显示“未指派”，不把所有协助人都展示成已指派评审人。

- 建议默认显示全部请求，支持进行中、已合并、已关闭筛选及标题/Skill 搜索。
- 打开请求查看与接收方相同的详情、差异和评审记录。
- 被要求修改时可修改自己的草稿、补充说明并追加请求提交记录；新提交内容或目标市场内容的变化使旧测评与旧认可不再适用于当前提交，必须重新测评。
- 提交人能看到评审进展，但不会因为自己提交而获得合并发布按钮。
- 撤回、关闭等动作按完整方案执行：建议作者可撤回、负责人可拒绝，发布中或结果待核实时先处理发布任务；首期关闭后以新请求继续，不直接重新打开。

如果用户同时是提交人和目标 Skill 的负责人或符合接收条件的协助人，同一 PR 可以出现在两个子 Tab 中。这不是重复提交；任何操作都作用于同一 PR。自己的评论不视为独立评审认可，也不能替代自动测评。

## 5. 请求进展与页面状态（建议）

PR 生命周期沿用原方案的 `open / merged / closed`；评审结果、测评结果与 PR 生命周期分开保存。

进行中的请求可根据真实状态展示“待测评”“测评未通过”“待评审”“需处理意见”“市场内容已变化”“待负责人合并”等进展提示；“待负责人合并”仅在对应合并条件满足时显示，不代表自动发布。自动测评已经确认为首期硬门禁，没有真实通过结果不得显示可合并。

- “收到的贡献”与“我提交的贡献”各自保留筛选、搜索和分页状态。
- 切换当前租户后重置列表和分页，丢弃旧租户未完成请求，避免串租户展示。
- 负责人转移、协助关系或评审指派变化后，刷新时按当前关系重新计算接收范围；操作请求始终实时鉴权。
- 已提交历史能否继续查看，以当前租户访问权限及请求访问规则为准，不依赖过去的列表缓存。
- 首次默认进入“收到的贡献”，允许用户切换到“我提交的贡献”。
- 空接收列表：“暂无与你相关的贡献请求”；空提交列表：“你还没有提交贡献请求”；筛选无结果单独提示。
- 加载失败展示错误与重试入口，不显示成“没有请求”；如增加角标，角标与列表必须使用相同的权限和统计口径。

## 6. 接口与实现边界

后续列表接口应支持接收视角和提交视角的服务端筛选。当前用户从认证上下文获取，当前租户由后端校验；客户端不能通过任意 `userId` 查询他人的个人请求列表。

- 接收视角根据当前负责人或协助关系查询；评审指派用于任务标记和筛选，不缩小协助人的可见范围。
- 提交视角根据当前用户的提交人身份查询。
- 过滤、去重、排序、分页、总数均在同一授权范围内计算，不先拉全租户请求再由前端隐藏。
- 两个视角复用同一详情与评审接口，不新增“接收副本”或“提交副本”数据表。
- 已确认只能改 CCUI：PR、本次固定提交内容与测评记录由 CCUI 保存，不要求远端新增接口；外部直接发布仍保留，限制与冲突处理见完整方案。
- 当前 `submit` 仍属于直接发布兼容接口；实现时需明确新 PR 接口语义，不能仅把现有按钮改名为“提交贡献”。

本次不改动现有 Skill 发布代码、工作区权限，也不实现测评、通知或真实 Git 仓库分支。

## 7. 验收要点

1. “贡献”主 Tab 下只有“收到的贡献”和“我提交的贡献”两个子 Tab。
2. 我负责的 Skill 收到其他用户的贡献后，请求出现在“收到的贡献”，角色显示为负责人。
3. 我协助的 Skill 的全部贡献请求均可进入接收视图，包含未指派给我的请求；“待我评审”仅筛出明确指派给我的请求。
4. 我提交的请求出现在“我提交的贡献”，不会混入其他用户提交且与我无关的请求。
5. 多个接收条件命中同一请求只显示一次；同时满足接收与提交条件时，可在两个视图看到同一 PR。
6. 协助人和仅有管理员身份的用户不能合并发布；只有目标 Skill 当前负责人可执行最终操作。
7. 审批、要求修改、补充变更及合并后的状态在两个视图中保持一致。
8. 切换租户、变更角色和权限后，不泄露已无权访问的列表、详情或数量。
9. 筛选、分页、空状态与网络错误可区分；保存与发布不因仅浏览页面而被触发。

## 8. 待确认及后续细化

协助人接收范围已经确认：所协助 Skill 的全部贡献请求可见，不限于指派给自己的请求。具体评审任务仍可通过单独标记和筛选区分。

后续已确认负责人可直接发布、协助人认可非强制、隔离自动测评为首期门禁、下架保留贡献、测评和操作记录、仅改 CCUI 且保留外部发布。门禁仅约束 CCUI 发起的发布/合并，外部发布的当前内容没有适用测评记录时统一显示“未测评”，这一范围与文案均已确认。本次固定候选、远端内容变化冲突、旧评审/测评失效及发布恢复等技术细节在完整方案中设计；部署能力和未确认默认值仍以完整方案的待定项为准。

2026-09-09 补充：Skill 不区分版本，不建设历史版本查看、回滚或版本对比；贡献记录不是正式版本。市场导入待更新只比较当前远端更新时间与成功导入时保存的远端更新时间，本地编辑时间不参与。完整字段、迁移和发布冲突处理见无版本主方案。
