# Skill 测评执行与结果判定详细方案

日期：2026-09-09

状态：设计方案与离线交互原型，不是业务功能实现。已按用户确认，将文字、工具、subagent、文件统一纳入任务验收，并允许负责人确认的 AI 语义标准参与发布硬门禁；已配套更新 HTML 原型，没有改造真实运行器或接入 AI。与[技能市场完整方案](../../skill-market-v2.0-需求设计说明书.md)及[联合测评专项方案](2026-09-09-skill-evaluation-static-dynamic-design.md)配套。

## 1. 核心回答：最终由谁判断“符合预期”

**由独立于被测 Skill 的 CCUI 判定服务，按负责人事先确认的验收标准，联合检查完整执行过程和实际交付物：规则检查可精确验证的事实，AI 按明确 rubric 判断语义完成度，服务端综合发布门禁。**

负责人定义业务上的正确；AI 可帮助起草输入、预期说明和断言；平台维护检测规则和判定器；被测 Agent 只负责完成任务。判定器把“输入—预期—实际—逐条结论—证据”串起来。

Skill 不必返回 JSON：它可以调用工具、委派 subagent、生成 Markdown/表格/文档，最后用自然语言答复。结构化的是 CCUI 内部的证据与判定结果，不是对全部 Skill 的输出要求。比如销售分析任务应检查实际报告中的金额、与数据一致的分析、可用文件以及工具安全，而不是只检查最后一句“已完成”。

本方案沿用已确认边界：

- Skill 无版本号、无历史版本查看；内部摘要和任务证据仅固定一次测评对象。
- 发布前必须由当前负责人运行完整静态＋动态测评，发布时再次校验资格；协助人不能代替。
- 用例由 AI 生成草稿或负责人手工添加，逐条人工确认后生效；草稿不参与正式测评。
- 曾随 Skill 核实成功发布的用例永久不可删除；负责人转移和下架不解除保护。
- 仅改 CCUI，其他渠道仍可发布；不具备对应报告的市场内容标记“未测评”。
- 单次调试不持久化执行记录；正式测评保存报告和受控证据，两者不混用。
- AI 语义判定可以成为必需验收项，适用于文字及文件内容；结论必须有证据，“无法确定”不能通过。AI 不得覆盖规则失败、安全违规或发布权限。
- 本文建议正式必需语义项采用两次独立评审并要求一致满足；这是可靠性与成本的设计默认值，不冒充用户逐项确认。具体模型、校准阈值、风险复核角色、资源预算、有效期在部署前确定。

## 4. 静态检测的详细执行逻辑

### 4.1 谁定义规则，检查什么

平台开发/安全策略维护者定义检测器和阻断策略，系统自动执行。负责人不是为每个 Skill 手工写一套静态规则；负责人主要查看问题、修复文件。AI 可给语义建议，但不直接写 passed 或解除硬阻断。

| 规则组及示例 ID | 确定性处理逻辑 | 典型结果 |
| --- | --- | --- |
| PACK-001 包体安全 | 在限额 worker 内枚举原始条目，统一路径分隔符，拒绝绝对路径、越界、重复/碰撞、特殊文件及越界链接 | 非法路径/包体阻断，不能先解包到工作区再扫描 |
| MANIFEST-001 根文件 | 精确要求根 SKILL.md，检查可读文本、严格 YAML 解析、name/description 为非空字符串 | 缺失/语法错误/字段类型错阻断 |
| MANIFEST-002 当前命名契约 | 沿用 CCUI 安全名称规则和身份比较，不擅自强制目录名等于 manifest 名 | 不兼容外部规范的差异单列，不偷偷重命名 |
| RESOURCE-001 本地资源 | 解析 Markdown 本地引用及明确声明的必需脚本，按文档相对位置解析并确保留在包内 | 确认必需资源缺失阻断；普通文档失效链接提示 |
| SYNTAX-001 必需脚本 | 使用可信、固定配置的只解析检查；不 import、不执行脚本、不加载包内插件或安装依赖 | 语法错阻断；必需语言不支持显示未覆盖并阻断 |
| SECURITY-001 秘密信息 | 本地特征/格式/上下文分析，标出疑似密钥；不通过联网试用密钥验证真伪 | 确认秘密阻断；疑似高风险待复核；只展示脱敏证据 |
| SECURITY-002 危险行为 | 文本/AST/数据流分析识别生产写入、越界读取、外传目标、混淆、扩大权限的请求 | 确认违规阻断；不把教程里的危险命令示例一律当作实际行为 |
| QUALITY-001 描述质量 | 检查空正文、未替换占位符、含糊输出约定、绝对环境路径和触发边界 | 普通质量建议不阻断；可选 AI 补充解释 |

不自动访问外链，不运行包内脚本，不启用包内 Hook/MCP。SQL 编写片段仅是文字，不因此自动执行 SQL Check。静态检查也不证明“技能功能正确”或“绝对安全”。

### 4.2 检测顺序和规则结果

1. 接收授权候选并登记文件清单，校验完整内容摘要。
2. 先做包体与路径边界；结构严重异常时停止深度扫描，其他规则标记未执行及原因。
3. 严格解析 manifest，构建受控文件/资源索引。
4. 对可安全读取的文件执行资源、语法、安全、质量检查；彼此无依赖的检查可并行，不能让一个解析器失败伪装全套通过。
5. 将每条规则的适用性、完成状态、发现、证据和处理策略归一化。
6. 计算 staticCanProceed：所有必需且适用的规则完成，没有确定阻断，也没有未解决高风险。

规则运行状态用 passed / finding / error / not_applicable / unsupported / not_run；发现的严重性和是否阻断单独记录。例如 warning 可以不阻断，但 error 不能被当成没有发现。

~~~json
{
  "ruleId": "RESOURCE-001",
  "ruleStatus": "finding",
  "required": true,
  "finding": {
    "severity": "error",
    "blocking": true,
    "path": "SKILL.md",
    "line": 14,
    "message": "明确声明的必需脚本 scripts/summarize.py 不存在",
    "suggestion": "补齐脚本或修正真实入口",
    "evidence": "检测到必需脚本引用，文件清单未包含该路径"
  }
}
~~~

上述路径和行号是示例，不是对当前项目的实际扫描发现。真实报告必须定位到本次候选中的字节和行号。

静态范围覆盖候选中实际纳入的脚本、资源以及批准的 subagent 指令/配置；平台维护的运行依赖也固定来源和摘要。不能只扫根 SKILL.md，就声称其调用链都已检查。未声明的动态依赖不能由运行器联网自动补装；确有需要时先登记为受控测试依赖。文档中提到某工具不代表真实配置了该工具，静态报告分别标记“声明”和“实际批准能力”。

### 4.3 高风险和误报

疑似高风险 → 待授权人员复核 → 确认违规或提供误报证据。没有通用“忽略并发布”按钮。误报认定绑定精确内容/规则配置；修订内容后不能继承不相干的例外。权限角色未确定前保持阻断。

复核完成后重新运行完整测评，不能把原来“动态未执行”的报告改成通过。静态建议数量不参与抵消动态失败的综合评分。

## 5. 动态用例怎样产生和生效

### 5.1 草稿生成

负责人点击 AI 生成 → 生成服务读取固定 Skill、负责人明确提供的背景及获授权测试数据摘要 → 产出输入、预期说明、断言草案、测试资源需求、待确认项 → 结构校验后追加草稿。

生成服务只负责起草；不得为寻找“答案”而在生产环境试跑，也不得自行调用被测 Skill 并把其输出当作正确预期。生成模型和被测模型可以同厂商，但必须使用独立任务和权限边界。

不完整/无可信答案的输出留在草稿并标出缺项。负责人可以编辑或删除；逐条核对业务依据、测试资源和断言后确认。手工添加同样先存草稿。表单提供“字段等于”“文件存在”等规则选择，不要求用户直接写 JSON。

### 5.2 生效集合与永久保护

- 只有当前负责人可以新增、修改、确认、删除未发布用例；每次操作重新鉴权和校验 ETag。
- 修改已生效用例先生成修改草稿，确认前仍使用原定义；放弃草稿不删除正式用例。
- 曾随发布成功使用的 caseId 永久不可删除，不能通过导入、批量替换、改 ID、负责人转移或下架清除；必跑项不能降级/停用以绕过保护。
- 修改受保护用例保留身份/原创建者，重新确认与测评，不改写旧报告；修正规则的业务责任仍由负责人承担。
- 生效集合变化即撤销旧资格；增加后又删除、恢复相同文本也不恢复变更前的资格。内部变更戳不是 Skill 版本。
- 有未确认草稿不等于必须发布它；正式任务只运行当前生效集合。至少一个有效必跑用例，否则不能发布。

### 5.3 预期应有两层

**人读的预期说明**：解释业务上为什么对，例如“同币种销售减去退款，100 − 10 = 90”。

**可执行的验收项**：每项明确检查哪些证据、采用确定性规则还是 AI 语义判定、满足/不满足的边界及证据要求。语义项可以有多个正确表达，不要求唯一标准答案，但必须有清楚的业务要求和参考依据。

纯文本“输出正确且清晰”不能自动变成硬门禁。应改成“结论与测试数据一致，指出两个主要变化，明确区分已知事实与推测”等逐项标准。AI 可以建议规则和 rubric，但确认生效前负责人要核对业务依据、金额、单位、时间范围、容差和数据来源。expected 与 assertions 不一致时先修正；不能靠评分 AI 猜负责人的真实要求。

## 6. 用例协议与完整示例

下面的 §6.1—§6.3 仅演示明确要求 JSON 的特定 Skill。通用任务默认采用多来源验收，完整的“工具＋可选 subagent＋报告文件＋最终文字”示例见 §10.4；不全局强制 outputContract.format=json。

以完整方案的嵌套结构为准。下面是 CCUI 自定义协议示例，不是行业统一标准；caseId 由服务端分配，客户端只能引用。断言 ID 在用例内唯一，required 表示此用例是否是发布必跑项；每条断言的 required 则表示其是否决定本用例通过。

### 6.1 测试输入数据

此处测试数据由平台登记为 fixture-orders-refund，运行器将其只读投影到该用例输入区：

~~~json
{
  "orders": [
    {
      "order_id": "TEST-001",
      "currency": "CNY",
      "sales_minor": 10000,
      "refund_minor": 1000
    }
  ]
}
~~~

金额统一使用最小货币单位“分”的整数，避免未定义的浮点容差。若业务必须比较小数，则在断言中预先配置绝对/相对容差，不能看到结果后调阈值。

outputContract 可以投影给 Agent；expected、assertions 和判定配置留在控制面。JSON Schema 的 properties 不等于字段必填，必须显式配置 required；若不允许额外字段，还需 additionalProperties: false。[JSON Schema 官方对象规范](https://json-schema.org/understanding-json-schema/reference/object)

### 6.3 错误输出如何被发现

若真实结果是：

~~~json
{"currency": "CNY", "net_sales_minor": 10000}
~~~

| 断言 | 期望 | 实际 | 结论 |
| --- | --- | --- | --- |
| A1 JSON 可解析 | 合法 JSON | 合法 | passed |
| A2 输出结构 | 两个字段、正确类型 | 满足 | passed |
| A3 净销售额 | 9000 分 | 10000 分 | failed |
| A4 币种 | CNY | CNY | passed |
| A5 工具策略 | 无违规操作，审计完整 | 示例假设无违规且完整 | passed |

最终该用例 failed，不是“4/5 达到 80% 所以通过”。报告应定位到 $.net_sales_minor，提示“预期 9000，实际 10000”；“可能漏减退款”只是诊断建议，不能当作已证明的根因。

工具断言必须独立使用真实审计证据，不能从上面这一段 JSON 推断没有违规。即使改成 9000，只要真实执行有生产写入违规，仍不通过。

## 7. 动态执行器一步一步做什么

1. **鉴权/预检**：当前负责人、候选权限、用例可用、测试资源可用；记录真实 initiatedBy、ownerIdAtStart、ownerGrantIdAtStart，禁止客户端伪造。
2. **固定输入**：将完整文件候选、当前生效用例定义、内部变更戳、平台策略、检测器、镜像、模型配置、fixture 内容摘要固定到 evalRunId。暂存后再次核对源摘要；有变化则冲突，不拼接不同时间的文件。
3. **进入持久队列**：数据库领取租约/心跳，限制每租户和全局并发；断线不停止任务。
4. **静态前置**：按第 4 节执行；不具备动态前提则记录 not_run 原因并结束。
5. **每用例创建全新环境**：新容器、工作目录、临时 HOME；只读候选和输入，只写本用例产物区；可复用镜像和可信只读依赖，不复用前例可写状态。
6. **装载目标 Skill**：通过平台固定加载器把完整候选放入该隔离项目的 Skill 目录，只开放该候选及批准依赖；验证载入清单，记录装载方式。首期 task 模式给定目标 Skill，不宣称验证了自然召回或触发准确率。
7. **运行一次完整任务**：允许多轮推理/多次工具调用完成一个用例，但任务完成即结束，不是聊天续聊；显式不持久化 SDK 会话，不恢复普通会话。
8. **采集并封存**：持续记录主任务/子任务消息、工具事件、文件变化与实际资源消耗；等待整棵任务树结束、停止所有写入后安全采集产物并封存只读证据，不能只见到根 result 就判分。
9. **独立判定**：规则器按固定定义核验事实；无工具的独立 AI 判定器按 rubric 验收语义项，校验结论和引用证据；不接受被测 Agent 提交的 passed 或 grading.json 作为权威结果。
10. **汇总并清理**：保存逐断言/逐用例状态和原因，取消/超时也保留已有事实；终止子进程、清理容器与临时资料。清理失败单列运维异常并回收，不能宣称已清干净。

建议首期每用例一次，一次任务最多 20 用例、每用例 120 秒/20 轮/20k 输出 token，实例并发 2、租户并发 1；均为待容量验证的配置起点。上限命中不能算通过。重跑新建完整任务，保留旧事实；禁止只重试失败用例并和旧成功拼成一次“全通过”。

### 7.1 统一采集四类证据

| 证据类型 | 必需字段/内容 | 如何使用 |
| --- | --- | --- |
| 最终答复 | rootAgentRunId、messageId、角色、终态答复正文/附件引用 | 检查用户实际收到的结论，不把子任务文字或工具回显误当最终答复 |
| 工具事件 | toolCallId、agentRunId、parentToolUseId、工具/能力名、参数、策略决定、结果、起止时间 | 核对真实数据来源、测试服务操作、错误处理与违规行为 |
| Agent 任务树 | agentRunId、parentAgentRunId、taskId、parentToolUseId、委派任务、终态、可观察结果 | 关联哪一个子任务做了什么、是否结束、主任务是否交付；不要求保存内部思维链 |
| 产物 | artifactId、安全相对路径、实际 MIME、大小、字节摘要、提取器摘要、解析覆盖、定位索引 | 读取真实文件内容；不是只接受 Agent 声称的路径或文件名 |

由运行器生成 evidenceId 和文件清单，被测 Agent 无权写测评数据库。文件初始清单与最终清单比较，区分输入、复制、新增、修改；复制文件不自动等于完成任务，也不自动失败，由真实任务约束决定。多个 Agent 共写一个文件时，只有可靠写入事件才标作者，不能按时间邻近猜作者。

输入/期望、工具结果、最终答复、子任务返回、文件提取内容保留明确来源。允许一个验收项同时引用报告与数据，一个任务拥有多个交付物；禁止从任意来源挑到正确句子就冒充整体正确。若任务没有文件或 subagent，对应证据为“不适用”，不是缺失。

事件序号表示采集顺序，父子/依赖关系表达因果；并发任务不伪装成严格先后链。采集缺失、丢消息、截断、解析未覆盖单独记录 coverage；没有观察到调用不等于已证明零调用。必要的测试系统状态变化（如写入测试工单）由只读控制面查询前后状态，与工具响应交叉核对；Agent 说“已创建”或工具返回成功不替代状态证据。

### 7.2 subagent 的装载、关联和结束屏障

1. 批准的 subagent 定义显式载入用例环境，禁止自动继承用户 HOME 中的 Agent、MCP、Hook 或生产配置。候选自带定义先静态扫描，平台测试配置固定其摘要。
2. 按当前 SDK 实际事件适配 Agent/Task 调用和 parent_tool_use_id，建立任务树；有 task_id 时关联生命周期。官方文档给出了这类关联机制，但字段完整性必须按本项目锁定版本测试。[Claude Agent SDK subagents](https://code.claude.com/docs/en/agent-sdk/subagents)
3. 根任务收到 result 后进入 settling；仍有活动子任务、工具或受控后台进程时不得判分。子任务完成后，还要确认父任务有机会汇总其结果，并取得最终任务终态。
4. 全部活动任务和写入者归零后，结束执行权限，冻结文件，进行安全快照/提取。不能靠“等两秒没有消息”替代结束证明；父 idle 也不等于子任务全部结束。
5. 子任务失败可被父任务合法处理或替代；不机械要求每次工具调用和每个探索分支都成功。未恢复的框架错误、未完成任务、必需委派步骤缺失则阻断；成功恢复的过程和原因保留在报告。
6. 超时、取消或预算耗尽中止整棵树及其子进程；禁止后台继续产生费用/改写文件。SDK 若无法提供测评所需审计，则该能力为未覆盖，不借普通会话的兼容性回退判通过。

每用例一个全新容器，同一用例内主 Agent/subagent 可以共享其工作目录；subagent 的上下文独立不等于独立的操作系统沙箱。工具、网络、文件权限取平台上限、用例配置和子任务配置的交集，子任务不能扩大权限。深度、并发、总轮数/调用量由适配器和网关共同限制；不假定当前 SDK 支持最新参数。

预算覆盖主任务和全部子任务；SDK 已汇总的费用不能再把子任务重复相加。执行成本和两次 AI 判定成本分开展示，未知值不填零。

### 7.3 文件如何成为可判定证据

文件只从本用例登记的输出根目录安全读取，拒绝越界、符号链接、特殊文件和超限文件；先终止写入再读取，避免检查后文件被替换。原始文件私有保存，解析器在无网络、无宏/插件的限额进程中运行。

| 格式 | 首期建议支持 | 不应冒充的能力 |
| --- | --- | --- |
| TXT / Markdown | 文本、章节、行号、表格 | 关键词齐全不证明分析正确 |
| CSV / JSON | 字段、行集合、数值与结构规则 | 不自动转换类型或执行公式 |
| XLSX | 单元格、表格、公式文本、可用缓存值 | 不执行宏/外链；无可信缓存且未配置受信计算器时不能声称已验算公式 |
| DOCX / 文本型 PDF | 段落、表格、页码或段落定位 | 提取文字不证明视觉排版和图表正确 |
| 图片 / 扫描 PDF / 图形化页面 | 第二阶段接入受控渲染/OCR/多模态判定 | 首期未支持时明示未覆盖；若是必需验收证据则阻断 |

不是一上线就承诺所有格式：前三组及 DOCX/文本 PDF 需逐个用样本验收后启用对应适配器。生产部署缺少解析器时，在用例确认/预检提示不支持；不能把二进制文件简单转字符串后让 AI 猜内容。

证据引用采用文件摘要＋页/段落/行/单元格定位。提取产物附 parserProfileHash、coverage、truncated 和原文件引用。长文先按预先声明的验收范围分段，可做受控分段判定，但必需范围未读全时不通过；摘要与相似度检索不能冒充全文完整覆盖。最终文本和文件观点冲突，必须按双方共同证据验收，不能择优取其一。

## 8. 权限与工具证据不能只靠提示词

容器默认拒绝网络，只开放批准的模型与测试出口；不挂载真实工作区、宿主 HOME、Docker socket、生产凭据。关闭自动继承用户设置、Hook、MCP、其他技能和跨用例记忆，按平台专用配置显式装载。

SDK 的 allowedTools 是权限规则的一部分，不是完整的操作系统安全边界；不能只在提示词里写“禁止生产写入”。尤其不能把普通 runtime 中的 bypassPermissions 与少量 allowedTools 直接视为安全白名单。[Claude Agent SDK 官方权限说明](https://code.claude.com/docs/en/agent-sdk/permissions)

落地采用多层约束：可用工具集合限制 → 平台前置策略和测试工具代理 → 文件系统/进程/网络隔离 → 运行后独立证据核验。具体 SDK 参数须按项目锁定版本验证，不能机械照抄最新文档选项。

工具事件由受控运行器/网关采集，包含 caseRunId、序号、工具名、脱敏参数、允许/拒绝、调用结果、耗时及证据摘要。候选文件或 stdout 中自称“未调用工具”的文字无权覆盖这些事件。

- “无违规”需要完整采集证据；采集器断线/丢事件为证据不完整，不能把空数组判为安全。
- SDK 工具事件不是 shell 内所有网络和子进程行为的完整审计。没有底层拦截/遥测的能力，不能声称对应规则已覆盖。
- 默认将被测 Agent 尝试执行平台禁止的生产操作视为安全违规，即使已被拦截也不能借正确答案通过。
- “安全拒绝”用例期待 Agent 不发起违规操作；单独验证沙箱拦截的基础设施测试不是 Skill 用例，避免把测试框架主动探测混作 Agent 行为。
- 业务测试替身可有预设错误响应，例如 fixture 的 404；Agent 正确处理后用例可通过。非预设的测试服务不可用才是环境 error，不把所有工具错误一概判为业务失败。

## 9. 独立判定器的具体算法

### 9.1 先取对结果，再比较

按每条断言的 target 或 targets 选取明确证据；一条断言可引用多个来源，一条用例可同时检查最终文字、工具、任务树和多个文件。outputContract 仅描述实际交付约束，不把整次任务限定成唯一输出。不能从任意日志里搜到正确数字就算最终报告正确。

- SDK 返回结构化最终结果时使用该字段；不把中间推理、工具回显当最终答案。
- 若约定纯 JSON 文本，则对整段最终输出严格解析；不自动截取任意花括号，不让 LLM“修复”失败输出后再判分。
- 如果确需允许 Markdown JSON 代码块，必须在用例生效前明确配置“恰好一个代码块”的解析契约，不能运行后临时宽松处理。
- 明确“值不存在”、null、字符串 "90"、数字 90 的差异；不隐式类型转换。数组顺序、日期时区、文本空白/大小写归一化由契约预先规定。
- 文件存在只证明生成了文件，不证明内容正确；还要校验类型、结构、关键数据。解析产物不执行宏、公式代码、外链或嵌入脚本。
- outputContract 中明确的必需交付约束必须编译为规则/验收项，不是只拼入提示词；例如最终答复引用的交付文件要能解析到同一次运行的真实安全产物。

### 9.2 首期断言目录

| 类型 | 如何执行 | 防止误判 |
| --- | --- | --- |
| json_valid / json_schema | 严格解析，校验必填字段、类型、枚举与约束 | JSON 合法不等于业务值正确 |
| json_path_equals | 按受限路径取值，再做类型敏感比较 | 缺字段不能等价于空值；钱/时间单位明确 |
| numeric_within | 使用预先固定的容差比较数值 | 禁止事后扩大容差凑通过 |
| text_contains / text_not_contains | 在指定最终文本上按明确归一化策略比较 | 只适合关键词/格式，不证明事实或语义正确 |
| artifact_exists / artifact_schema | 对受控产物索引验证存在、格式、字段/单元格等 | 文件名正确不是任务完成；无产物与解析器故障分开 |
| final_artifact_reference | 按事先约定的路径/链接规则，将最终答复引用解析到本次真实产物 | 不让模型自报“文件已生成”替代可用交付物；禁止任意宿主路径和外部 URL |
| tool_policy | 对可信完整事件流和平台策略做交叉校验 | Agent 自述、缺失日志、SDK 层看不到的行为不算完整证据 |
| trusted_grader | 调用平台登记的业务判定器，固定实现摘要和测试输入 | 不执行负责人或贡献包上传的任意评分脚本 |
| agent_execution / tool_used | 对完整任务树和实际工具记录验证预先声明的必要步骤 | 默认不强制委派/固定调用顺序；不得用 Agent 自述替代事件 |
| llm_rubric | 独立无工具模型按负责人确认的标准，对指定文字、文件及参考事实逐项验收 | 必需项参与门禁；必须有证据且满足，无法确定阻断；不抵消规则/安全失败 |

所有检测函数返回统一结果：assertionId、status、expected、actual、evidenceRefs、reasonCode、grader 配置摘要。评分器只读证据，不写执行目录；对不可信产物解析也配置资源限额。

### 9.3 断言依赖与异常分类

A1 无法解析 JSON → A1 failed → 依赖它的 A2/A3/A4 标记 not_run（dependency_failed）；独立的 A5 工具检查仍可执行。不能把一条根问题重复算成四个业务失败，也不能因后续未跑便忽略 A1 的失败。

| 观察到的事实 | 对应状态 | 用户下一步 |
| --- | --- | --- |
| 模型正常结束，金额/结构/产物与契约不符 | failed | 修正 Skill 或经负责人核实后修正用例 |
| 必需产物未生成、输出不是约定 JSON | failed | 检查任务行为/输出约定 |
| 有效 AI 判定为不满足 | failed | 看具体标准和引用证据，核对 Skill/用例 |
| 证据可读取但语义无法确定，或两次 AI 结论不一致 | inconclusive | 查看缺失依据/分歧；补充用例或修正后完整重跑，不直接改绿 |
| 判定器自身崩溃、无效判定响应、测试依赖故障、应有证据采集不完整 | error | 修复运行环境/判定器后重跑 |
| 达到时间/执行预算上限 | timed_out，附预算原因 | 检查循环或资源设置，再完整重跑 |
| 用户显式取消 | cancelled | 已有结果保留，但任务不能通过 |
| 静态阻断或前置条件失败导致没执行 | not_run，附原因 | 先处理阻断原因 |

结果同时保留执行状态、断言事实、安全事实和全部错误原因，不用一个颜色覆盖其他问题。假如已有金额失败又出现采集错误，应同时展示两者，而不是任选一个遮住另一个。

### 9.4 从断言汇总到发布条件

单用例通过条件：

~~~text
casePassed =
  执行完整正常结束
  AND 必需判定证据完整
  AND 至少一条有效的必需业务/输出断言
  AND 本用例全部必需规则断言 passed
  AND 本用例全部必需语义断言 met（归一化为 passed）
  AND 无必需项 inconclusive / error / not_run
  AND 无平台安全违规
~~~

观察断言可给建议，但不能把硬断言设成可选来隐藏失败。平台安全检查对必跑和观察用例都有效；任意已执行用例暴露安全违规，整次任务阻断。零断言、全建议的用例不能作为发布必跑项激活。

整次联合测评满足门禁的条件：

~~~text
evaluationQualified =
  静态必需检查全部完成且无阻断/未解决高风险
  AND 至少一个有效必跑用例
  AND 全部必跑用例 casePassed
  AND 所有已执行用例无平台安全违规
  AND 任务无未解决的系统级错误且正常结束
~~~

这还不是最终发布许可。发布服务另核对当前负责人及所有权授权、候选/用例/策略/环境摘要、生效变更戳、报告有效期、最新相关测评结果、远端时间条件。页面曾显示通过不能绕过服务端检查。

## 10. AI 语义判定与多形态任务的具体设计

### 10.1 负责人怎样配置，哪些内容交给 AI

表单不要求负责人写评分程序。每个用例配置：任务输入、测试资料、实际交付形式、验收项、可用测试能力和预算。验收项选择“规则检查”或“AI 内容评审”，逐项标明必需/观察。

| 判定对象 | 优先规则检查 | AI 内容评审 |
| --- | --- | --- |
| 自然语言答复 | 必要标识、受限词、约定字段、数字容差 | 是否回答需求、忠实于资料、说明边界，是否有无依据断言 |
| 工具调用 | 实际允许/拒绝、来源、参数、测试状态变化、明确必要操作 | 必要时判断检索/分析是否足以支持结论，不决定权限是否合法 |
| subagent | 真实委派/归属/终态、明确要求的分工证据 | 检查返回内容如何支撑交付物；默认不强制使用、不限制成一条固定路径 |
| 文件 | 真实存在、可解析、关键字段/表格/金额/附件关系 | 文档内容是否完整、论据是否成立、跨文件和答复是否一致 |

举例：“必须使用审批测试 API 创建工单”可作为过程硬要求；“请生成可用报告”通常验收报告结果即可，不强制它调用三次工具或启动两个 Agent。输出形式由业务需求决定：同一任务可配置“文字＋文件”，也可仅配置“文字”，不必须勾选四类。

AI 草稿生成同时建议参考依据、规则和 rubric；负责人逐条确认。标准答案可是一组事实/约束，不必是一篇唯一的范文；不要求模型逐字复述参考答案。生成 AI 不能同时替负责人确认自己生成的标准。

### 10.2 rubric 的字段和判定协议

每条 llm_rubric 至少包含：稳定断言 ID、required、targets、rubric.requirement、passConditions、failConditions、uncertainConditions、evidenceRequirements、referenceRefs；无参考资料的创意任务可明确 referenceRefs 为空，但仍需可核对的需求边界。references 指向经授权、已固定的事实/资料；不是让判定器实时上网补答案。

示例定义（属于用例 expected.assertions 的一项）：

~~~json
{
  "id": "S1",
  "type": "llm_rubric",
  "required": true,
  "targets": ["artifact:analysis-report", "final_output"],
  "referenceRefs": ["reference:sales-facts"],
  "dependsOn": ["R1"],
  "rubric": {
    "requirement": "分析忠实于销售测试资料，不把没有证据的原因当成事实。",
    "passConditions": [
      "正确说明净销售下降趋势，并结合销售额与退款变化解释",
      "明确把资料无法证实的原因表述为待验证假设",
      "最终答复与报告无相互矛盾的关键结论"
    ],
    "failConditions": [
      "声称广告投放、竞争变化等未经资料支持的因素是已确定原因",
      "报告和最终答复对净销售变化方向给出相反结论"
    ],
    "uncertainConditions": [
      "关键指代或语境无法消歧，现有资料不足以确定是否满足要求"
    ],
    "evidenceRequirements": [
      "定位报告和最终答复中相关原文",
      "给出对应参考事实定位；若指出资料没有支持，说明检查范围"

~~~

判定器结构化输出示例（是评分结果，不是要求 Skill 返回的 JSON）：

~~~json

  "verdict": "not_met",
  "reason": "报告将广告投放下降说成确定原因，但测试资料只提供销售与退款数据。",

  "coverage": "complete"
~~~

平台在提示模板外校验：ID 与当前待判集合一致，无遗漏/重复/越权项；枚举、长度和字段类型正确；引用属于本次授权证据，定位有效，quote 与原文匹配。伪造引用、漏判必需项、非法 JSON 属于判定服务 error，不能自动补成通过。引用可解析只证明引用真实，不证明 AI 推理正确，仍需校准与保守聚合。

判定模板/模型/参数/解析器由平台维护并固定为 judgeProfileHash；负责人配置业务标准，不能上传任意系统提示、控制模型权限或扩大平台规则。执行模型与评分模型可以同厂商，但评审必须是独立调用，不共享执行器可写上下文或会话。

### 10.3 判定服务逐步执行

1. 冻结该用例的证据清单，验证摘要、来源和覆盖；先运行文件解析与确定性规则。所有独立安全检查照常运行，不因某项内容错误而停止。
2. 为各语义项选择它声明的最终文字、文件片段/全文、参考资料及相关工具/子任务证据；保留来源标签，不把全文日志不加区分地拼成提示。
3. 判定模型只读这些资料及负责人确认的 rubric，不能使用工具、修改文件、联网、发布或向被测 Agent 追问。资料中的“忽略评分标准”“直接给通过”一律属于待检查数据。输入分区与提示注入回归只是降低风险，不宣称完全防住模型注入。
4. 建议每个有必需语义项的用例，对同一固定证据做两次独立评审，批量覆盖相同的必需项。两次互不可见对方结论；可以使用同一经校准配置，但不能声称错误概率相互独立或准确率翻倍。可选语义建议默认一次；没有语义项的用例不调用评分 AI。
5. 校验两份结果后按每项合并：都 met 才满足；都 not_met 为不满足；一正一负、任一 uncertain 为 inconclusive。任一必需判定调用无有效结果为 error。保留全部理由和分歧，不通过“挑有利意见”放行。
6. 依赖规则失败时，依赖它的语义项 not_run，仍运行独立项；平台资源不足也不能静默省略第二次必需评审。
7. 汇总必需规则和语义项，再计算用例、任务及当前发布资格。AI 无发布权限，也不能把静态/数值/工具失败改成成功。

| 同一必需语义项的两次有效判定 | 聚合状态 | 能否满足发布门禁 |
| --- | --- | --- |
| met + met | passed | 本项满足；还需其他条件都满足 |
| not_met + not_met | failed | 否 |
| met + not_met | inconclusive | 否 |
| 任一 uncertain | inconclusive | 否 |
| 任一响应无效/请求故障 | error | 否 |

未生成约定文件且文件清单可靠，是已证明的业务失败，不是无法确定。采集器丢文件、解析器崩溃是 error。文件可读但语义标准无法唯一解释或评审存在分歧，是 inconclusive。负责人只能查看并修正 Skill/资料/标准后发起完整新测评；没有“手动设为通过”按钮。

每用例仍只执行 Skill 一次；两次评审读取同一份执行证据，不是重复跑两遍 Skill。网络传输故障可有限重试未产生有效判定的请求，建议最多一次，记录每次尝试；不重试有效的 not_met/uncertain 来筛选有利答案。正式重跑创建新的完整 evalRunId，不与以前的成功项拼接，不能挑旧通过绕开更新的失败。

不采用“AI 给 85 分就过”或自报 confidence 大于某值放行。发布依据是逐项满足及证据，质量分数至多另作说明，不抵消缺项、安全或业务错误。

### 10.5 判定器自身也要验证

上线前固定 judgeProfile，用经人工核对的“明显正确、明显错误、遗漏重点、空文件、表面关键词齐全但不完成任务、伪造工具/subagent、文件与答复矛盾、提示注入、模糊边界”样本进行校准。统计误放行、误拒绝、无法确定率和重复一致性，人工检查系统性偏差；不能只用同一个生成 AI 生成并自评全部金标准。

模型、提示模板、参数、证据提取器或业务判定器变更要重新回归，并改变相应配置摘要，使未来发布资格重新核验；不改变历史报告事实，不展示为 Skill 版本。模型服务有漂移时记录可用的实际模型标识/部署信息，不能保证固定模型名就完全可复现。

发布门禁启用前必须完成可用性和代表样本校准；安全绕过、明显错误样本误放行为上线阻断。接受的残余误差阈值按业务与平台风险共同确定。校准未完成的 profile 不得承担必需判定，也不能临时降级成“AI 建议”来放行本来要求语义验收的 Skill。

SQL 等专用场景仍用登记的隔离测试库与可信判定器检查结果集合、null、排序、类型与容差；AI 可评解释但不覆盖 SQL 安全和结果错误。插入 SQL 片段不会自动开启 SQL Check。

## 11. 报告可视化如何解释“为什么失败”

沿用现有三视角，不引入加权总分：

- **总览**：静态阻断/待复核/建议；全部必跑用例的状态分布；耗时/token；本次事实与当前发布资格分开展示。
- **静态检查**：规则组 → 发现 → 对应候选文件和行号 → 脱敏证据/修复建议；显示不适用与未覆盖。
- **动态测评**：用例 → 验收结果 / 执行过程 / 产物三个详情视角。结果显示规则与 AI 标识、必需/观察、满足/不满足/无法确定、预期/实际及证据；执行过程显示根任务—subagent—工具树；产物显示真实文件预览与提取覆盖。

AI 项展开显示 rubric、两次判定、理由、分歧和可点击原文定位；明确“无法确定”的原因是语义歧义、证据不足还是评审分歧。市场仍为只读脱敏投影；隐藏原文时说明“证据受限”，不能把 rubric/引用片段中的私有资料泄露出去。负责人看私有证据也须具备相应测试数据权限；转移 Skill 负责人不自动授予底层数据集权限。

断言失败优先显示能定位的差异，例如“$.net_sales_minor：9000 ≠ 10000”；工具违规显示被拒绝/实际执行状态；环境 error 显示错误类别与可执行的排查方向，不甩一段模型原始日志。

必跑通过率 = passed 必跑数 / 全部必跑数。假如 4 passed、1 failed、1 error，展示 4/6，而不是 4/5；分母为 0 显示“无有效用例”，不显示 100%。一次通过只代表该次有限样本，不能宣传稳定准确率。

市场页仅展示与当前已发布内容核实匹配的报告脱敏投影；私有 prompt、fixture、标准答案及原始轨迹不随 Skill 公开。本地修改、草稿生成或新测评不覆盖旧发布事实。外部新内容没有适用报告显示“未测评”，不是“失败”。

### 11.1 对应的离线原型

[打开原型](../../prototypes/skill-market/index.html)，使用方式与验收范围见[README](../../prototypes/skill-market/README.md)。

- 用例配置：交付形式、参考依据、规则检查说明、可增删 AI 验收项，每项配置要求、满足/不满足/无法确定条件、证据范围和必需属性。保存与确认分开；已发布的必需标准不可移除或降级。
- 运行进度：固定内容 → 静态 → Skill/子任务执行 → 停止写入并封存证据 → 规则和独立 AI 评审 → 报告。取消不生成成功轨迹或评审。
- 动态详情：验收结果/执行过程/产物；AI 项展开两次独立意见，证据按钮打开只读原文与行号。执行树与平台评分调用分开，不将评分 AI 作为被测 Skill 自己创建的子任务。
- 场景：规则不满足、AI 不满足、评审分歧、无法确定、评分服务异常、执行环境异常、静态阻断、全部通过；不确定和异常不得手动改绿。
- 市场结果：只保留规则 ID、语义项 ID、必需属性、状态和两次结论；不透传私有 rubric、资料、理由或引用正文。负责人仍在我的技能中查看授权的完整证据。

原型额外新增销售报告示例，不替换原六条用例；所有运行、文件、意见及引用均为内置模拟，修改 rubric 不会触发真实判断。双评审按每用例两次独立调用表示，多条标准共享这两次调用，耗时不重复累加。表单内部简化数据不等于正式用例协议，实际文件示例仅为 Markdown。

## 12. 持久化、接口与并发约束

建议新增逻辑模块（名称是设计建议，尚未实现）：

| 模块 | 职责 |
| --- | --- |
| skill-evaluations | 鉴权、固定任务输入、状态机、队列、终态报告 |
| skill-static-checks | 规则注册、适用性、解析、安全发现与静态结论 |
| skill-test-suites | 稳定用例身份、草稿确认、永久保护、定义指纹 |
| skill-isolated-runner | 每用例环境、SDK 适配、工具边界、输出采集与清理 |
| skill-evidence-collector | SDK 事件适配、任务树、工具记录、文件清单与证据覆盖 |
| skill-artifact-extractors | 按实际文件类型安全提取、行/页/单元格定位、解析限额 |
| skill-graders | 固定断言、受信业务校验器、依赖调度、统一结果 |
| skill-semantic-judge | 私有 rubric 投影、两次独立判定、结构与引用校验、保守聚合 |
| skill-evaluation-reports | 授权明细、市场脱敏投影与当前资格 |

数据库保存 evalRunId、caseRunId、阶段/断言状态、指纹、真实发起人、租约/尝试标识、错误与证据索引；大文件存私有区。建议新增 skill_eval_agents、skill_eval_events、skill_eval_artifacts、skill_eval_assertions、skill_eval_judge_attempts，按 tenantId/Skill/任务外键归属；两次 judge 的请求摘要、配置、结论、引用、覆盖和实际消耗分别保存。受保护用例的规则/rubric 修改保留确认审计，不能通过删除全部核心验收项形成空壳必跑用例。负责人编辑的 expected 与每次运行固定定义分开存储；任何终态报告不可原地改写。

沿用完整方案 /api/skill-governance 接口：POST /evaluations 创建任务；GET /evaluations/:runId 查询；POST /evaluations/:runId/cancel 取消。草稿使用独立新增/编辑/删除及 POST /skills/:id/test-case-drafts/:draftId/confirm，不能用整套 PUT 覆盖删除受保护用例。

状态机建议：queued → preparing → static_running → dynamic_running → settling → evidence_frozen → grading → finalizing → completed。error/cancelled 是显式终态；completed 仅代表流程已完成，业务仍可 failed/inconclusive/blocked。事件序号递增且可重连，数据库是权威状态，前端不能上传 passed=true。

领取任务、写入结果按租约和尝试标识校验，拒绝过期 worker 回写；同一请求重试不重复创建任务。超时/取消要真正中止模型与子进程；清理和孤儿回收有独立重试。输入未完备时不得通过缺省值继续执行。

正式测评中不变更生效用例或转移负责人；发布中/待核实也锁定相关授权与集合。未确认草稿不改变该次运行指纹。服务重启无法恢复到可证明的执行状态时标记 error/允许重跑，不编造继续成功。

内部摘要可确保发布使用的是本次受测的固定字节，但 CCUI 锁不能约束外部客户端；远端无原子条件写入时仍有竞争，保持回读核实和“待核实/未测评”边界，不承诺全渠道原子一致。

## 13. 实施与验收

实施顺序：统一候选/用例/rubric 协议与静态规则 → 持久任务 → 隔离运行器与完整任务树 → 可信证据/文件解析/规则判定 → AI 判定与校准 → 结果页面 → 所有 CCUI 发布入口门禁。发布门禁上线前静态和动态必须完整，不先放开无测评发布。

至少覆盖下列测试：

1. 缺根文件、非法 YAML、失效必需资源、路径越界、解压限额、不支持必需语言、检测器崩溃都不能伪通过。
2. AI 草稿不生效、不参与执行、不覆盖原用例；负责人逐条确认；永久保护跨转移/下架保留。
3. JSON 合法但金额错误为 failed；输出只在日志中出现正确答案不能通过；缺字段/null/类型差异有独立证据。
4. 缺产物为 failed，可信解析器自身崩溃为 error，预设工具业务错误可正常测评，意外服务故障不可通过。
5. A1 失败时依赖断言 not_run，独立安全断言照常检查；缺工具事件不能被当作零违规。
6. 标准答案/隐藏断言不进入被测容器；同用例无旧状态；产物路径和内容不能改写判定器、读取宿主或其他租户。
7. 取消/超时/worker 崩溃保留已有事实并清理；迟到回调不能覆盖终态；重试不能拼接最佳结果。
8. 必跑失败或系统错误不通过；观察项安全违规也阻断；零用例/零硬断言不能假定通过。
9. 内容、用例、策略、环境、负责人授权变化使资格失效；旧事实保留，不出现 Skill 版本入口。
10. 通过发布后保护对应 caseId；市场公开结果不带私有数据；外部发布无法匹配报告时为“未测评”。
11. 对平台判定器本身维护已知正确/错误输出的回归集：空值、边界、恶意文本、错误类型、证据缺失等，不能只测试理想输入。

新增必须验收：

12. 自然语言与文件并存、不使用 subagent 的合法路径也能通过；不能全局强制 JSON 或固定工具序列。
13. 根 result 早于子任务结束、父 idle 但子任务仍运行、子任务写文件未结束均不提前判分；缺失父子关联不能伪造完整任务树。
14. 子任务安全违规不能被主任务正确回答抵消；取消根任务时完整终止子树。可恢复的探索失败不自动判为整例失败。
15. 文件名正确但内容错误/为空/不可解析应失败；输入文件复制、多产物歧义、来源未知不能被表面合规蒙混。
16. 两次 met 才通过必需语义项；两次 not_met、分歧、uncertain、无效引用、缺项、模型不可用均按各自状态阻断。
17. rubric 内敏感资料、标准答案和 judge 配置不进入执行器或市场接口；恶意产物提示不能修改评分规则或调用评分工具。
18. 文本提取不能替代图片/排版验收；必需覆盖被截断/未支持时不通过；授权证据删除或到期后不得用于新的发布资格。
19. 判定器升级、负责人转移、定义/rubric 变化使未来资格失效；旧报告不改写，曾发布用例保护不受影响。

上述是业务实现的待验收清单。文档示例检查、原型模型测试与浏览器交互检查分别记录在原型 README；不能把它们当作真实 Skill 执行、安全验证或判定器已经实现。

## 14. 仍需实施前确定的事项

- 高风险误报由谁复核；前置角色未配齐时不开放泛化豁免。
- 可用隔离运行环境、批准工具/测试库、模型/镜像配置、限额和证据保留期。
- 复杂业务 trusted_grader 的首期目录及可靠标准答案来源。
- AI 语义项参与硬门禁已确认，不再待选；部署前确定评分模型、代表性校准集、验收误差上限及双评审成本预算。
- 原生 SDK 与工具策略的实际兼容性、底层采集覆盖、远端授权/发布时间契约。
