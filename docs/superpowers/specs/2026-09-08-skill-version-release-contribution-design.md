## 1. 已确认规则与范围

| 主题 | 已确认规则 |
| --- | --- |
| 发布权限 | 只有目标 Skill 当前负责人可以发布、合并发布；管理员身份本身不能代为发布 |
| 负责人自身变更 | 允许直接发布，包括首次发布；不强制先给自己提交贡献请求 |
| 协助人 | 可以贡献、参与评审，不能合并发布；评审认可不是必需的合并条件，负责人最终确认 |
| 自动测评 | 首期就必须通过，负责人直接发布和贡献合并发布均不能跳过 |
| 测评组成 | 静态检测与动态检测共同测评，并提供可视化结果；具体方案见第 6 节链接 |
| 用例创建 | 以“AI 根据 Skill 生成用例草稿，负责人确认后生效”为主要方式；生成结果不能直接成为正式判定标准 |
| 测评环境 | 在隔离测试环境真实执行；默认不开放生产凭据和真实业务写入工具，依赖资源需配置测试环境或替身 |
| 贡献页面 | 仅“收到的贡献”“我提交的贡献”两个子 Tab |
| 接收范围 | 负责人和协助人均能看到其负责或协助 Skill 的全部贡献请求，不限于被指派的请求 |
| 协作范围 | 沿用当前租户边界；片段库全平台共享不扩大 Skill 或贡献可见范围 |
| 下架 | 保留 CCUI 中的正式版本和贡献记录；市场下架只取消分发，不删除本地文件 |
| 实现边界 | 只能改当前 CCUI，不能要求远端 data-agent 增加接口、表或事务能力 |
| 外部发布渠道 | 仍需保留其他渠道直接发布，不能假设 CCUI 是远端唯一写入方 |
| 门禁覆盖范围 | 已确认强制测评仅约束 CCUI 发起的发布/合并，不承诺覆盖其他渠道直接发布 |
| 外部版本文案 | 尚无对应测评记录的外部版本，面向用户统一显示“未测评” |

两个历史版本入口按同一条正式发布历史设计。“本地保存”“提交贡献”和“正式发布”不是同一个动作；片段仍只是普通 Markdown，不设片段版本、不参与引用追踪、不自动开启 SQL Check。

本设计与 [贡献页补充方案](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/superpowers/specs/2026-09-08-skill-contributions-design.md)、[片段方案](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/superpowers/specs/2026-09-08-skill-snippets-design.md) 配套。原 V2 中“远端存储 PR/快照”“所有发布必须先提 PR”“管理员可代为合并”不再作为本方案前提。

### 1.1 首期建议默认值

- 不引入真实 Git 仓库或面向用户的命名分支；本地文件是工作副本，提交时生成独立内容快照。
- 新建/上传 Skill 默认由创建/上传者担任负责人；旧本地无作者记录的 Skill 在首次登记时明确确认负责人，不能靠第一次查看自动认领。
- 一个请求可以追加多次提交，普通变更只有成功发布才产生正式版本号；历史导入和外部版本后补验证纳管是明确标注来源的例外，不代表重新发布。
- 贡献者只能修改自己的请求；协助人不是该请求草稿的共同写入者，可自行提交另一份贡献。
- 首期不自动合并过期基础版本，不提供发布成功后的全工作区自动升级。
- 首期不提供永久删除历史、批量版本清理、多人实时协同编辑或自动发布。
- 负责人转移暂不进入首期：当前发布实现按远端记录的创建者校验权限，尚未验证上游是否支持接任者发布；不能仅改 CCUI 负责人字段就承诺完整转移，详见实施边界。

### 1.2 必须正视的部署约束

CCUI 内部的发布入口必须经过同一套协调服务和持久数据库，但远端仍存在其他直接发布者。不能假设所有远端发布都通过 CCUI。

远端当前是分开的保存/更新与发布接口，没有已验证的条件发布、发布幂等键或操作状态查询契约。CCUI 可以严格校验自己提交的内容，但不能对独立的外部发布者建立全局锁。若外部客户端可在“更新包”和“发布”之间改写远端内容，就无法保证远端实际发布的包是 CCUI 测评过的包。

已有能力也应复用：[远端 API 文档](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/skill-market-api.md) 的 `preview` 支持 `queryVersion`，当前 `previewRemoteSkill` 已传该字段。因此应优先按发布响应返回的确切版本读回，而不只比较最新版本。实施前仍需验证该参数确实读取不可变的已发布内容，以及完整文件树、二进制和必要文件属性能否无损获取；现有字符串预览不能证明这些能力。`download` 未约定版本参数，不能把它的当前包响应冒充指定旧版本。

因此，只能提供 CCUI 路径内的门禁、历史与异常检测，不应将其描述为覆盖整个远端市场的强制门禁。用户已确认接受这一范围，外部版本没有对应测评记录时统一显示“未测评”。该文案表示平台尚无该版本的测评记录，不推断外部渠道是否自行测试；内部仍保留发布来源和后补验证记录。若以后要求覆盖所有渠道，则必须调整远端能力或发布渠道约束，不能用本地锁冒充解决。

## 2. 统一对象与版本语义

| 对象 | 含义 | 是否进入正式版本历史 |
| --- | --- | --- |
| 工作副本 | 工作区现有 Skill 文件，可以反复保存 | 否 |
| 内容快照 | 一组相对路径与文件原始字节的不可变集合，包含完整文件树 | 单独快照不代表发布 |
| 发布候选 | 快照 + 目标 Skill + 基础正式版本 + 提交来源 | 否，测评和发布绑定它 |
| 贡献请求 PR | 贡献者针对目标 Skill 提出的变更申请 | PR 自身不占正式版本号 |
| PR 提交记录 | 同一请求的一次不可变候选内容，显示“第 N 次提交” | 否，可在 PR 内追溯 |
| 自动测评记录 | 对指定候选、规则/检测器、用例集、策略和执行环境的静态检查与真实动态执行结果 | 与后续正式版本关联 |
| 正式版本 | 已确认发布成功的候选快照及发布审计记录；历史导入/外部纳管单独标明来源 | 是，CCUI 版本号单调递增；不伪造缺失历史 |
| 发布任务 | 执行远端保存/更新/发布并确认结果的持久任务 | 任务失败或结果未知不算正式版本 |

### 2.1 Skill 身份与版本号

- CCUI 分配稳定的 `governanceSkillId`，与租户绑定；名字、本地目录、远端 ID 都不能代替该身份。
- 远端 `remoteSkillId/remoteVersion` 是分发映射，仍保存，但不作为 CCUI 历史连续性的唯一依据。
- 新 Skill 第一次发布为 v1，此后每次成功发布加一；失败、取消、未知结果及保存草稿不增加正式版本。
- 纳管已有市场 Skill 时保留当前可验证的版本号 N 作为历史基线，后续从 N+1 开始；可按 `queryVersion` 尝试恢复之前的已发布包，没有旧包的 v1～vN-1 不伪造。
- 外部新增版本先记录为“外部发布观察”，不自动变成 CCUI 测评通过的正式版本；负责人完成补充测评并确认纳管后，才进入新的治理基线，明确标记为“外部发布后验证”，不能追溯宣称发布前已通过门禁。
- 下架后重新分发可能得到新的远端 ID/版本号，但 CCUI Skill 身份与正式版本序列继续保留，不重置为新 Skill。
- UI 正式版本统一显示 CCUI 版本号；上游版本只在兼容诊断中显示，避免重新分发后出现两个相互矛盾的“v1”。

### 2.2 本地基线

本地绑定增加 `governanceSkillId/baseVersion/baseSnapshotHash`，与现有远端绑定字段分开保存。

例如正式最新版 v5，本地来自 v3 且有修改，显示“基于 v3 · 有本地修改 · 最新 v5”，而不是把本地修改称为 v4。每次保存只更新文件，不改 `baseVersion`。未纳管的纯本地 Skill 不显示虚构的正式历史。

发布成功不自动覆盖任何人的工作副本。只有当前副本与成功候选完全一致时，才可安全更新对应基线；若期间又有编辑，保留内容及原基线并提示需要同步，不把脏副本标成干净的新版本。

### 2.3 快照内容

- 包含根 `SKILL.md`、脚本、资源及其他允许发布的文件；不只存 Markdown，也不存逐行 diff 代替文件。
- 路径规范化并稳定排序，按路径、字节长度、原始字节摘要及需要保留的文件属性计算树摘要；ZIP 外层目录、压缩时间戳不参与内容身份。
- 禁止路径穿越、越界符号链接、重复规范化路径；复用当前归档大小、文件数、深度、manifest 和空文件检查。
- 片段正文已经在 Markdown 中，不查询片段库，也不保存片段来源。
- 用例集、评审、权限和运行凭据不混入发布包；快照不会冻结外部 API、模型服务或实时业务数据，历史内容可追溯不等于外部行为完全可复现。

### 2.4 状态分离

治理 Skill 状态建议为 `unpublished / published / unlisted`，远端同步状态另用 `matched / external_changed / remote_missing / unknown` 表示；PR、测评和发布任务各有自己的状态。

已经发布的 Skill 即使出现十个待评审 PR，正式版本仍保持可用，不将整个 Skill 改成 `in_review` 后从市场隐藏。只有确认下架或远端明确删除才改变分发可用状态。外部更新未验证时也不能把上一次快照的测评结果当成当前远端包的结论。

## 3. 两个历史版本入口

### 3.1 技能市场

只读展示正式版本时间线、变更说明、提交来源、发布人、发布时间、测评摘要及文件差异。可以查看任一已保存版本的完整文件，不展示未发布候选和 PR 私有草稿。

历史页默认对比选中版本与其父版本，也支持选择两个正式版本对比。首期不额外增加“安装任意旧版本”的市场操作。

### 3.2 我的技能

复用同一历史列表，额外标记本地基础版本，并提供当前工作副本与指定历史版本的差异查看。负责人可以从某个历史版本发起回滚发布，其他成员只查看历史或通过正常贡献流程提出变更。

“回滚发布”不直接改写本地文件。若以后增加“恢复到本地”，应是另一个带覆盖确认与备份的操作，不能与发布回滚共用含糊的按钮。

### 3.3 单个版本详情

展示版本号、父版本、完整文件、内容摘要、发布说明、发布人、原贡献者、关联 PR、回滚来源、测评报告，以及远端分发状态。旧版本不可覆盖编辑；修复旧版内容也必须产生新候选和新发布。

历史基线若没有当年的测评记录，明确显示“历史导入，未记录测评”，不能补标为通过。下架后仍从有权访问的“我的技能”或贡献详情访问 CCUI 历史，市场列表不恢复已下架卡片。

兼容外部发布时，同一历史服务额外返回独立标记的外部观察项，显示远端版本、首次观察时间、测评状态及后补验证记录，不假装它们已经获得 CCUI 正式版本号。市场当前远端包与最新治理版本不同且没有对应测评记录时，测评状态统一显示“未测评”；“外部更新”另作来源/同步提示，不能把旧版通过标识贴到新版上。后续运行测评后显示该版本实际的测评状态，不将测评失败也归为“未测评”。

## 4. 负责人直接发布

### 4.1 首次发布

1. 本地新建/上传后明确登记目标 Skill 与负责人。登记不代表发布，市场尚不可见。
2. 负责人补充变更说明，可先由 AI 根据 Skill 生成用例草稿，再核对并确认至少一条必跑测评用例；没有可执行用例不得发布。
3. 保存当前编辑内容，后端校验工作区权限和文件，读取完整目录生成候选快照，基础版本为无。
4. 预览完整待发布文件与检查结果，确认本次候选；运行自动测评。
5. 测评通过后展示“发布 v1”确认页，再次检查当前负责人、候选、用例策略和本地内容是否仍匹配。
6. 负责人确认后创建发布任务；远端结果可确认时才记入 v1 并显示本次发布成功。远端可见性由其实际 publish 生效时点决定，可能早于 CCUI 最终确认，不能承诺两者原子切换。

纯本地旧 Skill 的首次登记必须显示“将作为新 Skill 发布”；如果已绑定他人的市场 Skill，不允许通过改目录或清空本地作者信息绕过贡献流程覆盖原 Skill。

### 4.2 发布更新

复用首次发布的候选、测评、确认流程，区别是必须指定当前正式基础版本，并展示它与候选的完整差异。

- 无内容变化时不生成空版本；发布说明不能单独制造新正式版本。
- 本地基础版本落后时，先处理上游变更，不能直接用完整旧目录覆盖最新版。
- 预览后本地文件变更，原直发候选进入“本地内容已变化”状态；需要重新准备候选并测评，不暗中把旧测评用于新内容。
- 发布确认必须绑定候选 ID、最新版本条件和测评记录。负责人直发只是省略贡献申请，不省略测评、差异确认和发布审计。

## 5. 贡献请求完整流程

### 5.1 提交

任何有当前租户访问权限的成员，可以在自己有编辑权限的工作区准备已纳管 Skill 的变更；仅有某工作区查看权限并不授予该工作区文件写权限。

1. 基于可获取的正式版本，在“我的技能”修改自己的工作副本。
2. 点击“提交贡献”，保存内容，生成候选快照；填写标题和变更说明，可从当前负责人/协助人中指派评审人。
3. 贡献者预览完整 diff 后提交，请求状态为 `open`；自动排队运行目标 Skill 的正式测评用例。
4. 请求立即进入目标 Skill 负责人及全部协助人的“收到的贡献”，同时进入提交人的“我提交的贡献”。测评未完成时可以先评审，但不能合并。

服务端从已有绑定确认目标身份和基础版本，不能信任客户端把修改自旧版的文件直接声明为“基于最新版”。首次上传副本缺少可靠基线时，需要用户选择基础版本并完整确认差异。

### 5.2 评审与追加修改

- 负责人和协助人可评论、表示认可、要求修改；贡献者可回复并修改自己的请求。
- 协助人认可不是合并硬条件。负责人看到未解决意见时应明确确认处理方式，但不能覆盖测评失败。
- 提交人对自己内容的说明不视为独立他人认可；由于首期不设强制协助人票数，不用“自审一票”制造门禁通过。
- 每次点击“更新贡献”生成新的不可变 PR 提交记录，并替换当前候选；之后的本地保存不会改变已经提交的内容。
- 更新内容或基础版本后，旧认可标为针对旧提交，旧测评不再满足当前合并条件；重新排队测评。
- 行级评论绑定提交记录、文件路径、新旧侧、行号及上下文摘要；新提交后无法可靠定位的评论显示“针对旧提交”，不错误挂到新代码行上。
- 修改标题、补充讨论不生成内容提交记录，也不单独使同一内容测评失效。

### 5.3 负责人合并并发布

1. 打开 PR 当前提交，查看 diff、评审意见和真实测评报告。
2. 服务端检查当前用户仍是负责人、PR 可合并、候选基线仍为最新、测评有效。
3. 负责人确认“合并并发布”，创建持久发布任务并锁定该请求当前提交。
4. 远端发布确认后，在同一 CCUI 数据库事务中写入正式版本、更新最新版本、将 PR 标记为 `merged` 并关联版本。
5. 两个贡献视图刷新为同一结果；所有其他工作副本保持原样。

“合并并发布”是一个用户操作，不增加“合并了但长期没有发布”的正常业务状态。执行期间可以显示“发布中”；失败或结果未知时不得提前显示“已合并”。

### 5.4 PR 状态、撤回与拒绝

业务状态仅为 `open / merged / closed`；测评状态、评审进展和发布任务状态分开保存。

- 进行中的展示状态可为待测评、测评未通过、待评审、需处理意见、基础版本过期、待负责人合并、发布中或发布待核实。
- 贡献者可撤回自己的 open 请求；负责人可拒绝并关闭目标 Skill 的 open 请求，必须填写原因；协助人只能提出意见，不能替贡献者撤回或替负责人拒绝。
- 已开始外部写入的发布任务未完成或待核实时，禁止更新、撤回、关闭或再次合并同一请求，先核实发布结果。
- 首期关闭为终态；需要继续时复制为新请求，保留原请求链接，而不是复用旧测评和审批。
- 已合并请求不可再次合并；后续修改提交新请求。

### 5.5 基础版本变化与多个并行请求

采用明确阻止过期候选的首期策略，不做自动三方合并。

例如 PR A、B 都基于 v3，A 发布为 v4 后，B 标记“基础版本已过期”。贡献者需要获取 v4，人工整合自己的修改，再生成基于 v4 的新提交并重新测评。

提供旧基线、最新正式版、当前贡献三个内容视角供比较；不会为了更新基线自动覆盖工作副本。仅修改 `baseVersion` 字段而不重新提交确认内容是不允许的。二进制文件冲突、删除/修改冲突也不自动选择一方。

## 6. 自动测评门禁

静态与动态联合流程、规则和用例格式、隔离运行器、结果可视化与数据接口详见 [Skill 静态与动态联合测评详细设计](/Users/theseus/Documents/Codex/2026-08-24/github-cli-gh-codex-pull-request/claudecodeui/docs/superpowers/specs/2026-09-09-skill-evaluation-static-dynamic-design.md)。该专项方案细化并更新本节；建议默认阈值仍待评审。

### 6.1 最小可交付能力

自动测评由静态检查与动态执行两阶段组成，也不等同 SQL Check。先固定完整候选并检查文件、结构、依赖与安全风险；存在阻断项时不进入动态阶段。之后在隔离环境中真实运行候选 Skill，由独立检查逻辑判断结果，生成同一份分层报告。只有静态自检通过不能发布。

建议首期采用负责人维护的确定性用例：输入任务、测试数据、期望输出断言、允许/禁止的工具行为、资源预算。支持文本包含/不包含、JSON 字段与结构、工具调用及产物内容等声明式断言，不让被测 Skill 自己返回一个 `passed=true` 就通过。

自然语言质量可增加模型评分报告，但首期不把尚未定义稳定评分标准的结果伪装为确定性通过。无法表达或执行有效断言的用例需要负责人补充测试约束，不能因“缺少测试”直接放行。

### 6.2 用例与策略管理（建议）

已确认以“AI 先生成草稿，负责人确认后生效”为创建用例的主要方式；以下用例数量、通过策略及具体交互仍为建议默认值，不因确认生成方式而自动视为全部确认。

- 每个 Skill 至少有一条负责人确认的必跑用例，必跑用例全部通过，且观测到的安全违规为零，才允许发布。
- 负责人维护生效用例集和判定策略；协助人可提出修改建议。贡献包中删掉测试文件不能删除平台必跑用例。
- 用例定义及策略变更保留内部修订记录与摘要。修改用例、断言、允许工具、测试数据或执行配置后，旧通过记录立即失效。
- 贡献者不能将失败用例设为可选或伪造测试结果；负责人也没有“跳过测评发布”入口。
- 不能把零条用例、运行中、取消、超时、资源不可用或部分执行显示成通过。
- 一般输出正确性只能覆盖用例表达的范围，“通过”不承诺所有真实业务场景正确或绝对安全。

#### 6.2.1 AI 生成草稿与负责人确认

建议交互流程如下：

1. 根据当前 Skill 的固定内容及用户明确提供的测试背景生成用例草稿，记录所依据的内容摘要；不自动读取生产凭据或真实业务数据。
2. 草稿包含输入任务、测试数据要求、预期结果和行为限制，辅助覆盖正常、边界与异常场景；缺少可靠预期或测试资源时标记待补充，不编造标准答案。
3. 负责人可以修改、删除或选择草稿，核对预期结果与检查规则，再显式确认加入正式用例集。支持手工补充，不将 AI 生成设为唯一创建渠道。
4. 后端检查当前负责人身份及用例集修订条件，确认成功后生成新的生效修订。AI 生成、重新生成或仅保存草稿不会自动生效，也不覆盖现有正式用例。
5. 用例生效不代表测评通过；仍须真实执行对应候选。生效用例集变化使旧测评结果不再满足当前发布条件，但保留原报告。

不能直接把被测 Skill 某次输出保存成正确答案，或让 AI 自己确认自己的预期。未确认草稿不参与正式发布门禁；正式断言与判定逻辑仍独立于被测 Skill。

### 6.3 测评结果绑定

有效通过记录至少绑定以下集合：候选 ID、完整内容摘要、PR 当前提交（如有）、基础版本、用例集摘要、策略摘要、静态规则及检测器版本、测试数据/依赖摘要、执行配置摘要，以及执行器版本、模型和运行镜像标识。必需检查的覆盖清单也必须完整，检测器异常或不支持不能当作通过。

发布时逐项核对当前值；不能只检查“这个 Skill 曾经测评通过”。PR 追加提交后，即使部分文件没变，也不能继续使用旧提交的认可与测评记录。

同一候选重试保留所有结果，最新一次非通过结果不能被选择更早的通过结果绕过。建议通过记录有效期为 24 小时，超期或执行环境改变需重跑；该时间属于可评审默认值。

### 6.4 隔离执行

- 新建独立测试工作目录、容器和运行身份，只装载当前候选与审核过的测试依赖，不复用用户正在工作的会话。
- 不挂载真实工作区、用户完整 HOME、宿主 Docker socket、生产密钥或其他租户目录；不能因 Docker 不可用而静默降级到宿主本地执行。
- 网络默认限制，只允许测评模型服务及批准的测试端点；工具使用测试账号、测试数据库或测试替身。真实业务写入默认拒绝。
- 用户设置的 Hook、SQL Check 开关、预装 Skill 和 MCP 不自动继承，避免污染测评或产生业务副作用。
- 候选内容与执行前后摘要一致；结果检查在独立控制逻辑中执行，测试期望、门禁状态和平台数据库不可由候选写入。
- 记录输出、工具调用、断言结果、token 与耗时；对日志中的凭据和敏感数据做脱敏，报告仅对有权访问该候选或版本的人开放。
- 建议初始预算：每用例 120 秒、20 个 Agent 轮次、20,000 输出 token，每次运行最多 20 个用例；实例并发 2、每租户并发 1。额度可配置，但不能将超额跳过标为通过。
- 执行失败或依赖缺失显示具体原因；重试必须使用同一候选或明确创建新候选。结束后释放专属测试容器和临时工作目录，不删除已提交快照或正式版本。

当前会话运行器提供 Docker/本地运行能力，但默认配置会挂载工作区并使用用户环境；它不是现成的安全测评环境。实现时必须新增专用隔离配置与门禁，不得仅换一个工作目录就宣称隔离完成。

## 7. 回滚与下架

### 7.1 回滚发布

负责人从历史版本选择“以此内容发起回滚”，基于当前最新正式版本创建一个候选，其文件内容取自选中的旧快照，记录 `rollbackSourceVersion`。

例如最新 v5 回退到 v2 的内容，仍须按当前用例和策略重新测评，负责人确认后发布为 v6；不覆盖 v2、不删除 v3～v5，也不让旧版曾经通过的结果绕过今天的门禁。

回滚候选评测期间又产生 v6，则旧回滚候选也过期，需重新确认针对最新版本的完整变化。任何回滚操作均不自动修改用户工作区文件。

### 7.2 下架并保留历史

首期建议下架由负责人执行；原稿管理员强制下架权限是否保留需另行评审，不从“管理员无发布权”直接推导结论。

- 负责人确认下架后，通过现有远端删除接口取消分发；删除成功或明确确认远端已不存在后，CCUI 中状态才改为 `unlisted`，保留治理 ID、全部版本、PR、评审和测评记录。超时先保留待核实任务，不把网络错误视为已下架。
- 保留“我的技能”的本地文件和治理绑定，记录远端映射已失效；不能沿用当前实现直接丢弃全部绑定，导致历史入口断开。
- 下架不产生新版本，也不要求运行测评；它与发布新内容不同。
- 下架期间允许查看已有贡献及历史，但禁止新提交和合并发布，提示先由负责人重新发布上架；既有请求不被批量删除。
- 重新发布上架需要新候选、当前测评和负责人确认，生成下一正式版本，可使用相同正文；这是“取消分发后重新上架”的显式操作，不受普通更新无内容变化的限制。
- 远端新建分发记录后建立新映射，原远端 ID 继续保留在历史发布记录中。若旧删除结果未知，不能先新建重复记录。

永久删除历史和历史保留期限不属于首期。下架后历史访问至少覆盖仍有当前租户权限的负责人、协助人、相关请求作者及持有该 Skill 本地绑定的用户；不因保留记录就把未发布贡献内容开放给无关用户。

## 8. 仅改 CCUI 的架构

### 8.1 职责分离

| 层 | 职责 | 不承担的职责 |
| --- | --- | --- |
| CCUI 页面 | 本地编辑、候选确认、历史、贡献、测评报告与发布结果 | 不自行判定用户拥有发布权限，不上传客户端伪造的通过状态 |
| CCUI 治理服务 | Skill 身份/角色、候选、PR、测评门禁、版本与审计事实 | 不把远端最新包当作所有历史版本的替代品 |
| CCUI 持久任务执行器 | 测评队列、发布阶段记录、重启恢复、结果核实 | 不盲目重试结果未知的远端发布 |
| CCUI 持久快照存储 | 完整不可变包、文件清单及测评报告 | 不放进用户 Skill 运行目录，不随工作区删除而级联清除 |
| 现有远端市场 | 通过当前保存/更新/发布/删除接口分发当前包 | 不要求新增 PR、测评、历史或事务 API |

首期建议一个逻辑 CCUI 治理实例：SQLite 与独立持久文件存储共置，任务执行器统一协调。多套独立 CCUI 数据库无法自动共享这些记录；不能直接在多实例间各存一份数据库后声称全局一致。多 Web 进程如需访问，应通过同一治理服务，不依赖跨主机共享 SQLite 文件锁。

### 8.2 外部变更检测与纳管（建议）

1. 进入详情、历史、准备候选或发布前，读取远端身份、版本及实际已发布包摘要，与最后确认的远端映射比较。
2. 发现不同版本或不同内容时，先保存可获取的外部快照及观察记录；没有对应测评记录时显示“未测评”，另提示“外部更新”。不覆盖既有正式快照，不自动改任何本地文件。
3. 暂停针对旧远端基线的 CCUI 发布和合并，提示负责人处理外部更新，而不是自动覆盖外部作者的内容。
4. 负责人可以把外部快照作为纳管候选，使用当前用例集真实测评；通过后再次核对远端仍是该包，确认将其纳入治理历史，来源为 `external_adopt`。
5. 纳管追加下一个 CCUI 正式版本、记录远端版本映射和后补验证时间；原有 PR 基线相应过期。它不是 CCUI 重新发布，更不能被描述为外部发布前通过了检查。
6. 负责人不接受外部变化时，可以在理解完整差异后准备恢复候选；同样需要新的测评与明确发布确认，不能让重试任务自动撤回外部更新。

发现版本跳变时，可按 `queryVersion` 尝试补读中间已发布版本，保存为来源明确的观察记录；接口不可读或无法验证完整性的版本保留缺口，不推测作者和实际发布时间。普通网络错误不等于远端已删除；只有明确不存在才更新分发状态，仍保留 CCUI 历史。

本方案不顺带禁止现有市场安装外部版本。没有对应测评记录时，安装入口统一显示“未测评”，不能伪称已通过；若以后要求安装也强制门禁，需要另行确认。未经纳管的外部基线不能直接拿旧版通过结果进入 CCUI 发布流程。

### 8.3 安全与角色一致性

- 治理请求带当前认证用户与租户上下文，后端验证租户成员身份；所有表查询、快照、报告、任务和下载均校验租户及资源权限。
- 发起直接发布、贡献快照必须拥有源工作区编辑权限；评审和合并已提交到 CCUI 的快照不要求负责人进入贡献者的工作区，也不授予该工作区文件权限。
- 负责人从 CCUI 权威记录读取，不能由正文 frontmatter、客户端 `ownerId` 或本地缓存覆盖。
- 既有远端创建者与本地用户需按验证过的账户映射匹配；不为第一次访问的管理员或安装者自动赋予负责人身份。
- 暂不支持只在 CCUI 改 owner 就转移发布权，也不伪造原创建者账户头绕过远端授权。若远端授权和本地负责人不一致，发布明确被阻止。
- 所有新增治理写入口之外，旧 `/publish`、`/upload-publish`、`/submit` 也必须接入同一门禁或拒绝旧式请求；不能留下绕过自动测评的兼容后门。

### 9.2 物理存储

快照和报告存放于服务专用持久根目录，路径按租户和资源 ID 组织，文件以临时写入、摘要校验、原子改名完成后再登记数据库。发布包及历史文件读取只从受控存储定位，不接收客户端任意路径。

- 元数据与文件必须一起纳入备份/恢复测试；仅备份 SQLite 不能恢复版本正文。
- 只对未被候选、PR、正式版本或任务引用的临时对象执行回收；正式历史首期不自动删除。
- 压缩包内容按相对路径计算身份，保留当前本地目录与远端包目录解耦规则；发布包装变化不修改 `SKILL.md.name`。
- 跨租户即使正文相同，也不通过可猜测的公开哈希地址共享下载权限。
- 存储不足时阻止新候选/发布并保留现有数据，不通过清除正式历史自动腾空间。

## 10. 发布一致性与失败恢复

### 10.1 CCUI 内可以保证的部分

每个 Skill 同一时刻只允许一个 CCUI 发布或下架任务进行。锁按稳定治理 ID 而不是工作区目录建立，并在数据库中持久化；网络等待不长期占用 SQLite 写事务。

发布确认包括 `candidateId + expectedHeadVersion + currentPrRevisionId（如有）+ evalRunId + idempotencyKey`。幂等键与租户、操作者、Skill 和请求摘要绑定，同键不同请求返回冲突。

任务准备事务内再次验证负责人、PR 状态、候选、基线和测评，记录租约并固定输入；此后只能发布该不可变快照，不能重新从正在编辑的工作区打包。进入外部写入阶段后，相关 PR 当前提交和关键门禁配置暂时锁定，不能在发布途中替换测评对象。

远端成功可确认后，写正式版本、推进 latest 指针、更新 PR 和完成任务在同一 CCUI 事务内完成。版本号以 CCUI 当前 latest+1 分配，禁止不同任务占用同一正式版本。

### 10.2 任务阶段

建议持久记录 `prepared → remote_saving/updating → remote_publishing → verifying → completed`，另有 `failed`、`uncertain`、`conflict`。

- 每个外部写请求发送前记录阶段；记录缺少成功响应并不意味着请求没有生效。
- 首次发布：固定候选包，调用现有 save，记录返回的远端 ID，再 publish，随后核对已发布内容。
- 更新发布：预检远端身份/版本/内容仍为预期基线，再 update、publish，并核对发布结果。
- 持久保存发布成功响应返回的确切远端版本 R，优先通过 `preview(queryVersion=R)` 核实已发布状态与完整内容摘要；不使用 `remoteVersion+1` 的猜测代替真实完成证据。版本指定能力必须先通过 P0 验证，不能用不带版本的 download 结果代替 R。
- 若 R 的完整内容与候选不匹配，或无法确认读到的是 R，不将候选记录为已成功发布，不将 PR 标为 merged，不自动覆盖对方包；分别进入 conflict 或 uncertain。
- 若有可靠发布成功响应且 R 的内容匹配，即便最新远端已变成 R+1，也可完成本次正式记录和 PR 合并；同时单独标记当前分发存在外部更新，暂停后续旧基线发布。不能只因最新包不同就否认已经证实的 R 发布事实。
- 租约超时或进程重启后，接管者先核实，不能直接重放外部写请求。旧执行者可能仍在远端处理中，本地 fencing token 无法阻止不支持它的远端生效。

### 10.3 异常处理

| 情况 | 处理 |
| --- | --- |
| 文件/权限/测评检查失败，尚未调用远端 | 明确失败，保持旧版本，修复后创建或重试合适候选 |
| 远端 save 超时，是否已创建记录未知 | 标记 uncertain；不再次 save 制造重复 Skill，不仅凭同名结果认定属于本任务 |
| update 已成功，publish 明确失败或未知 | 记录已写远端草稿与发布结果状态；不盲目回写旧包，可能存在外部更新 |
| publish 响应成功但该响应指定版本的内容读回不匹配 | 标记 conflict，展示实际观察，不标记成功，也不伪造测评覆盖 |
| 发布版本 R 已证实匹配，但最新远端已为 R+1 | 完成本次发布记录，另记录外部更新；不把 R 的测评标识用于 R+1 |
| publish 响应丢失 | 先按已知远端 ID 只读核实；外部也可能发布相同正文，不能只凭哈希相同认定本任务成功；证据不足保留 uncertain，不假定失败自动再发 |
| 远端成功，CCUI 最终事务尚未完成就重启 | 利用已持久化证据和读回核实幂等完成；缺少可靠证据则停在待核实 |
| CCUI 正式记录成功，本地绑定或页面刷新失败 | 明确“已发布，本地状态待刷新”，仅修复本地状态，不重复调用远端发布 |
| 检测到其他渠道新版本或删除 | 记录外部观察/分发变化，保留本地和历史，进入外部变更处理流程 |

负责人可以触发“重新核实”，不能点击“强制标记成功”绕过证据和测评。由于当前远端没有已验证的幂等发布/按任务查询接口，部分超时场景确实需要人工协调，不承诺全自动恢复或全局 exactly-once。

### 10.4 外部竞争的不可消除边界

远端预检与更新/发布之间不是一个事务。其他客户端可能在任意时刻写入，甚至在 CCUI 发布读回之后再次覆盖。CCUI 的后验核对能发现部分冲突，但不能阻止错误远端内容短暂出现，也不能保证观察到所有中间版本。

CCUI 必须只给自己保存的确切快照展示对应测评结果；市场重新读取的包摘要不同就撤下该包的“已通过”标识。严禁以“我们拿了本地锁”或“请求返回 200”宣称所有外部发布都受门禁控制。

## 11. CCUI 接口契约草案

建议新增 `/api/skill-governance` 命名空间，统一认证和当前租户校验；以下不是远端新增接口。涉及本地文件的请求另行校验工作区权限，纯历史/贡献请求不强制绑定某个工作区。

| 方法与路径（省略统一前缀） | 用途与权限 |
| --- | --- |
| POST `/workspaces/:workspaceId/skills/:name/register` | 新 Skill 或旧 Skill 纳管；验证来源/负责人，不能抢占已有远端绑定 |
| POST `/workspaces/:workspaceId/skills/:name/candidates` | 从本地完整内容准备候选，要求源工作区编辑权限，校验预览摘要和基础版本 |
| GET `/candidates/:id` 与 `/candidates/:id/diff` | 查询有权限的固定候选和差异 |
| GET `/skills/:id/versions`、`/skills/:id/versions/:version` | 正式历史及详情；外部观察单独标记返回，不混淆编号 |
| GET `/skills/:id/compare` | 对比两个授权的版本/候选；不接受任意文件系统路径 |
| GET `/skills/:id/test-suite`；PUT `/skills/:id/test-suite` | 查看用例；负责人修改生效用例/策略，乐观并发校验 |
| POST `/candidates/:id/evaluations`；GET `/evaluations/:id` | 创建和查看真实测评任务，重试受配额与候选访问权限约束 |
| POST `/skills/:id/releases` | 负责人直接发布候选；强制验证测评和条件，返回 202 及任务 ID |
| GET `/contributions?perspective=received\|submitted` | 两个子 Tab，服务端按当前用户角色或提交人过滤、去重、分页 |
| POST `/contributions`；GET `/contributions/:id` | 创建贡献与查询详情，目标候选/Skill/租户必须匹配 |
| POST `/contributions/:id/revisions` | 贡献者追加候选，带 expectedRevisionId，禁止发布中的替换 |
| POST `/contributions/:id/reviews`、`/contributions/:id/comments` | 对指定提交评审或评论；禁止伪造身份与位置 |
| POST `/contributions/:id/merge` | 负责人合并并发布，返回同类发布任务，不立即标记 merged |
| POST `/contributions/:id/close` | 作者撤回或负责人拒绝，校验状态与原因 |
| POST `/skills/:id/rollback-candidates` | 负责人从旧快照准备回滚候选，不自动发布或改本地文件 |
| POST `/skills/:id/unpublish` | 负责人下架任务，确认后取消远端分发、保留 CCUI 记录 |
| GET `/skills/:id/external-observations`；POST `/skills/:id/adopt-external` | 查看外部变化；负责人绑定通过的测评并确认后补纳管 |
| GET `/publish-jobs/:id`；POST `/publish-jobs/:id/reconcile` | 查看结果、发起只读核实；不盲目重发写操作 |
| GET/PUT `/skills/:id/collaborators` | 查看/由负责人维护同租户协助人，移除后不删除历史记录 |

新增/修改请求应携带版本条件或 ETag 防止表单互相覆盖；`reviewerIds` 是任务指派，不能改变协助人对全部相关请求的可见范围。作者、负责人、测评通过状态、版本号、发布人和时间均由服务端推导。

常见错误需区分：401 未登录、403 无权限、404 不可访问或不存在、409 基线/内容/状态冲突、413 超限、422 校验失败或测评未通过、428 缺少条件、429 配额不足、503 运行环境不可用。结果未知必须返回可查询任务及明确 uncertain 状态，不以普通“重试”按钮诱导重复发布。

## 13. 验收与实施顺序

### 13.1 核心验收

1. 本地保存十次不新增正式版本；一次可确认的发布成功只新增一个正式版本。
2. 负责人直发无须 PR，但无用例、测评失败/未知/过期、候选变化均不能发布；协助人与管理员不能代发。
3. 协助人没有认可也不自动阻止负责人最终确认，但测评门禁无人工跳过入口。
4. 两个贡献子 Tab 查询范围正确，同一请求只存一份，协助人可见所协助 Skill 的全部请求。
5. 提交后继续修改本地文件，不改变已提交快照；追加 PR 提交使旧测评和旧认可不再适用于当前提交。
6. 并行 PR 其中一个发布后，其他旧基线请求不能覆盖最新版，必须处理变更并重新测评。
7. 两个历史入口对同一治理 Skill 显示相同的版本内容；本地版本标签仅表示基础版本，不是保存次数。
8. 回滚以旧内容产生新版本并执行当前测评；下架保留版本/贡献/本地文件，重新上架延续治理身份。
9. 恶意候选不能写入正式数据、修改测试期望、获得生产密钥或跨租户读取报告；隔离不可用时失败关闭，不转宿主执行。
10. 重复点击、服务重启、远端超时和本地刷新失败不导致已知可避免的重复发布；证据不足明确待核实，不伪造 exactly-once。
11. 外部更新或删除不覆盖历史或本地文件；未经验证的外部包不复用旧包的通过标识，未知中间版本不伪造。
12. 在可检测的远端内容不匹配场景，PR 不被标为已合并；不可消除的外部竞争限制有清晰说明与结果状态。
13. 所有旧发布路由也校验门禁；客户端伪造 passed、version、owner 或跨 Skill evalRunId 均无效。

### 13.2 实施阶段

| 阶段 | 交付物与退出条件 |
| --- | --- |
| P0：契约与风险验证 | 验证 preview 的 queryVersion 是否读取确切不可变已发布版本、能否无损获取完整文件树/字节/必要属性，以及草稿与正式状态、发布返回字段和错误语义；验证容器隔离与模型/测试依赖配置；落实已确认的 CCUI 路径门禁范围 |
| P1：治理数据与快照 | 身份、角色、不可变快照、候选、正式历史、外部观察与安全下载；迁移验证不改本地内容 |
| P2：静态与动态联合测评 | 静态规则与覆盖、负责人用例管理、队列、专用隔离执行器、断言、可视化报告、结果绑定及配额；任一阶段不满足不得进入下一阶段发布 |
| P3：负责人发布闭环 | 候选→测评→确认→持久发布任务→读回核实→正式版本；旧发布入口封口、超时恢复测试 |
| P4：贡献与评审 | 两个子 Tab、提交快照、评论/认可、追加提交、基线冲突、负责人合并复用同一发布与测评链路 |
| P5：历史治理 | 回滚、保留历史的下架/上架、外部版本后补验证纳管、真实迁移与端到端回归 |

自动测评既然是首期硬门禁，P2、P3 必须共同完成后才能开放新发布，不能先上线无门禁直发再补测评。

测试分层包含：数据库事务与租户隔离、快照完整性、路由权限、任务状态机故障注入、容器隔离、前端角色/状态展示，以及两个用户、两个租户和一个外部发布者的端到端场景。仅 mock 远端不能证明其真实发布语义；P0 不满足时要明确保留限制，不能把模拟成功当作上线验证。

## 14. 尚待确认与实施前置条件

门禁只约束 CCUI 发起的发布/合并、外部版本文案为“未测评”均已确认，不再列为待定项。

1. **远端读回能力待验证**：已有 preview 的 queryVersion 契约，但指定版本的不可变性、完整字节/属性获取能力尚未验证；download 未声明指定版本支持。如果无法确认本次发布版本的完整包，只能显示待核实，需要重新确定可接受保证级别，不能只比 SKILL.md 就声称全包一致。
2. **测评默认值待评审**：至少一条必跑、必跑全部通过、24 小时有效期、声明式断言种类、预算与配额；这些不是用户逐项确认的数值。
3. **首次登记与负责人映射待落实**：新建/上传者默认负责，旧无作者本地 Skill 要显式确认；远端创建者无法映射或已离职时不能自动转给管理员。
4. **部署前提待落实**：CCUI 治理数据库及快照持久卷、唯一内部协调服务、测试镜像/模型服务、测试替身与备份容量。
5. **下架权限建议待评审**：首期建议负责人执行；原稿管理员强制下架是否保留是独立权限选择，不影响已确认的负责人独占发布权。

其余交互默认值可在不改变已确认产品规则的前提下迭代。若要求远端全渠道原子发布、全历史无缺失或严格全局幂等，则超出当前 CCUI 单方可实现的保证范围，必须调整外部接口或发布渠道约束。
