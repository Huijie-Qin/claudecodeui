# AI 看板：先计算完整，再更新正式明细

更新：2026-09-17。替代此前“版本分区 + 活动指针”的存储方案；指标定义、权限与业务日期不变。

## 处理方式

1. Hook 执行、记录性 Hook、Agent 模板查 `ai_usage_report_rows`；整体概览、AI、Skill、SQL 和代码提交查五张 `ai_dashboard_*_detail` 主题表。宽表继续保留对接和中间投影用途。正式表都只保存当前完整结果，没有 `partition_id`。
2. 夜间任务先把当前结果复制到 `ai_usage_report_staging`，在暂存区按受影响的日期重算明细、Hook 数值摘要、每日及滚动活跃集合。未变化的部分保留；首次运行从空暂存区开始。
3. 各计算页和进度同时提交。中途失败或闲时窗口结束，正式明细不动，下次恢复未完成的任务。
4. 旧候选全部计算完成后，只从旧候选投影宽表候选 `ai_dashboard_integration_staging`，再生成 AI、Skill 发布、Skill 调用、SQL 生成、代码提交五张表候选（AI 按用户／工作区／会话／日合并），不独立读取业务数据重算。全部准备好后，同一个事务替换该租户两张原有正式表及五张拆分表、更新成功时间及批次、清理候选。任一步失败整体回滚。看板按五表＋旧表分工查询，见 [拆分明细表](ai-dashboard-split-detail.md)。
5. 会话汇总同样只从原明细生成：原候选内补充 `session_usage`（Token、日志确认的响应结束时间等），`turns` 保留按完成时间归集的切片时长，再由同批原候选生成 `ai_session_summary_staging`。原表、会话表及其他投影同一事务发布。会话汇总阶段不再单独扫描日志或读取原始事实层，详见 [会话汇总表](ai-session-summary.md)。

例如旧结果是 50，新结果将是 40：计算期间仍显示 50；发布事务提交后显示 40。不会把“先删除、尚未写完”的中间状态暴露给看板。第一次计算未完成则显示尚无统计数据，不把未完成视为 0。

“完整”指本批已识别、目标日期以内的计算任务完成，不保证外部迟到数据已到齐。原有 partial/unavailable 覆盖标记，以及源记录删除后的安全遮蔽仍保留。

## 各类表的职责

| 表 | 职责 | 是否供看板取数 |
| --- | --- | --- |
| `ai_usage_report_rows` | 当前完整统计明细／投影 | 是，Hook／Agent；也是其他投影的来源 |
| `ai_session_summary` | 只从原明细派生的完整会话汇总，含 Token、Skill 列表和实际时长 | 不替换原看板取数；供会话对接使用 |
| `ai_dashboard_integration_detail` | 从旧表投影的固定字段专用明细 | 否，保留对接与中间投影职责 |
| `ai_usage_report_staging` | 未完成、未发布的新结果 | 否 |
| `ai_dashboard_integration_staging` | 同批新表候选，由旧候选生成 | 否 |
| `ai_dashboard_ai_detail`、`ai_dashboard_skill_publication_detail`、`ai_dashboard_skill_invocation_detail`、`ai_dashboard_sql_generation_detail`、`ai_dashboard_code_submission_detail` | 同批宽表的五类投影，不替换宽表 | 是，AI／Skill／代码产出及整体概览 |
| 五张对应 `*_staging` | 主题候选 | 否 |
| `ai_dashboard_split_state` | 整组五表的发布状态 | 仅用于批次与结构版本一致性检查 |
| `ai_usage_batches`、`ai_usage_tenant_state` | 执行进度、成功时间、当前任务编号等元数据 | 仅用于状态和一致性检查 |

暂存表的 `batch_id` 只标识正在计算的任务，防止任务数据相互覆盖；它不是正式明细的版本分区。已发布的历史结果行不保留，历史任务日志可以保留。

正式表结构见 [旧表 DDL](ai-usage-current-detail.sql)、[宽表 DDL](ai-dashboard-integration-detail.sql) 和 [五张主题表 DDL](ai-dashboard-split-detail.sql)。`stat_date` 对应看板起止日期；旧表 occurred_at 保持原有 ISO 格式，宽表／五表统一上海 `YYYY-MM-DD HH:mm:ss`。宽表时长仍为 INTEGER 毫秒，AI 主题表为 REAL 秒；API 转为原有整数毫秒字段，事件时间带明确 +08:00，避免另一时区电脑误读。

## 查询和导出

- 同一次报表请求的批次元数据、总条数、合计和结果页，在同一个只读事务中读取，防止独立 Worker 在多条 SELECT 之间发布。
- 五表必须对应当前批次且结构版本为 4，否则返回 `409 splitNotReady`；不回退宽表／旧表，不在读请求中执行迁移。Hook／Agent 不依赖五表就绪状态。
- 页面携带的批次若已被新结果替换，接口返回 `409 reportUpdated`，提示刷新后重试；不冒充旧结果，也不返回已丢弃的历史明细。
- 分页导出每页核对当前批次。异步任务在开始、生成后、标记可下载前再次核对。期间发布了新结果则导出失败，需要刷新重试，不生成混合批次的文件。
- 已完整生成的导出文件不因普通刷新失效，但仍受权限、原数据删除及到期规则限制。
- 单次查询和单租户发布各自原子化；不承诺所有租户、所有页面请求同时切换到同一瞬间。

## 迁移与运行边界

- 迁移前备份数据库。迁移在事务中只复制每个租户正在展示的已发布结果，去掉旧结果分区和映射表；有存活的统计 Worker 租约时拒绝迁移。
- 暂停中的旧格式任务重置工作进度，并重新标记事实和正式结果中的受影响日期，避免此前已经消费的变更标记丢失。计算定义或时区变化同样重新准备暂存结果。
- 不能让旧版后端继续访问已迁移的数据库；应在后端部署边界应用迁移。现有内存模拟预览与真实数据库分离，不需为此停止预览。
- 当前采用每租户完整暂存副本，增量采集和按日重算仍保留，但复制及最终发布需要遍历该租户全部结果。设结果行数为 R，复制／发布至少 O(R)，索引维护有额外开销；原结果、宽表和五类拆分数据均需对应暂存副本，另需预留 WAL／事务日志空间。大数据量下发布事务可能较长，应实测闲时窗口和磁盘余量。
- 此变更不会开启 `.env` 中未启用的定时任务，也不会把真实数据塞进可分发的模拟 HTML。
